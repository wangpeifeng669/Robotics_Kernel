# AOQ协议解析-AI-over-QUIC

**核心摘要**：AOQ（AI over QUIC）是阿里云为多模态 AI 实时交互自研的传输协议，基于 QUIC 深度定制，在百炼 Realtime API 中与 WebRTC、WebSocket 并列为三种官方接入方式。它针对 AI 交互"弱网实时、内容可靠有序、多载体强同步"的不可能三角给出了解法：全格式单连接承载、实时/非实时双模自适应、流级容错（60% 丢包仍可流畅对话）。端侧机器人与 App 原生场景值得重点关注，但需接受其闭源 SDK 与阿里生态绑定。

---

## 一、AOQ 是什么：先纠正一个常见误称

AOQ 的官方全称是 **AI over QUIC**——"跑在 QUIC 上的 AI 交互协议"，由阿里云自研，2026 年 7 月随百炼 Realtime API 正式宣发。部分二手资料（包括 AI 对话的转述）将其误称为 "Ali Optimized QUIC" 或与不存在的 "AOP（Audio-over-Packet）" 类协议混为一谈，实际以阿里云帮助中心为准。

它的定位一句话讲清：**多模态大模型实时交互的确定性传输底座**。当大模型从云端走向终端，端侧公网"最后一公里"的丢包、抖动、带宽骤降，与 AI 推理所需的实时双向数据流之间产生尖锐矛盾——WebSocket 太慢太卡，WebRTC 能到但交互形式单一，AOQ 想同时拿下三者。

在百炼 Realtime API 中，三种协议分工明确：

| 维度 | AOQ | WebRTC | WebSocket |
| :--- | :--- | :--- | :--- |
| 适用场景 | AI 多模态实时交互、弱网、混合数据传输 | 浏览器端互动、传统音视频通话 | 服务端集成、快速原型验证 |
| 浏览器兼容 | 不支持 | 原生支持 | 原生支持 |
| 接入难度 | 低 | 中等 | 极低 |
| 弱网对抗 | 极致 | 良好 | 差 |
| 数据类型 | 音视频 + 文本 | 音视频 + 文本 | 文本/音频/图像 |
| 建连速度 | 快 | 慢 | 慢 |
| 回声消除/降噪 | 内置 | 内置 | 无，需客户端自行处理 |
| AI 场景适配 | 原生为 AI 多模态数据特征深度定制 | 传统设计，AI 场景需额外适配 | 基础 |
| 端侧平台 | Android / iOS / HarmonyOS（另有 Linux Python 支持） | 浏览器、移动端 | 全平台 |

一个容易忽略的细节：**WebRTC 通道不支持实时 ASR 和 TTS 模型**（如 Qwen-Audio-3.0-ASR-Flash-Streaming、CosyVoice 系列），而 AOQ 和 WebSocket 全支持。也就是说，要在一条连接上同时跑 ASR + 实时对话 + TTS 的混合流，AOQ 是唯一全模态覆盖的实时协议。

## 二、为什么需要 AOQ：多模态交互的不可能三角

多模态大模型全双工通话场景，对传输协议提出了两个近似冲突的硬性要求：

1. **端侧弱网低延时**：地铁、电梯、高铁、地下车库等场景下，高丢包、大抖动、带宽骤降是常态。弱网卡顿和连接中断会瞬间击穿用户对 AI 交互的耐心。
2. **数据异构强对齐**：AI 交互混合了控制指令、音频流、视频流、长文本等异构载体。传统实时协议为保流畅常牺牲可靠性导致数据截断；多通道独立传输缺乏协同，极易出现口型、声音与字幕脱节。

这两个要求展开后构成经典的不可能三角：

| 协议流派 | 弱网实时 | 内容可靠有序 | 多载体强同步 | 用户感受 |
| :--- | :--- | :--- | :--- | :--- |
| 传统可靠协议（TCP/WebSocket） | ✗ | ✓ | ✓ | "太慢太卡" |
| 传统实时协议（RTP/WebRTC） | ✓ | ✗ | ✗ | "能到，交互形式单一" |
| AOQ | ✓ | ✓ | ✓ | "能到，交互丰富" |

TCP 的队头阻塞决定了弱网下延迟会膨胀到秒级；RTP 系协议为了实时性放弃可靠传输，控制指令和文本事件得另开通道，同步全靠应用层缝补。AOQ 的思路是：**用 QUIC 的流级特性打底，参考实时协议的弱网对抗手段，再针对 AI 数据的生产消费特点重构**。

## 三、技术底座：QUIC 给了 AOQ 什么

理解 AOQ 先要理解它为什么选 QUIC。QUIC（RFC 9000）是跑在 UDP 之上的传输协议，Chrome 出身，HTTP/3 的底层。它对 AOQ 的价值有四点：

1. **流级无队头阻塞**：QUIC 在单连接内原生支持多 Stream，各 Stream 独立确认、独立重传。一条流丢包不阻塞其他流——这正是"音视频流 + 文本指令流并行、互不拖累"的协议级基础。
2. **0-RTT 建连**：QUIC 结合 TLS 1.3 支持会话恢复时的 0-RTT，首个包就能携带业务数据。对"唤醒即说话"的机器人交互，建连耗时从 WebRTC 的数百毫秒压缩到接近无感。
3. **连接迁移**：QUIC 用 Connection ID 标识连接而非四元组，Wi-Fi 切 4G/5G 或跨基站时连接不断——移动机器人在商场漫游换 AP 的场景直接受益。
4. **加密内建**：TLS 1.3 强制内建，无明文传输选项，密钥协商与握手合并完成。

一个佐证其技术路线的细节：百炼网关的 AOQ 接口请求头为 `x-dashscope-rtc-transport: moq`，与 IETF 正在标准化的 MoQ（Media over QUIC）路线同源——AOQ 可视为在 MoQ 思路上面向 AI 多模态场景的工程化扩展，而非从零发明。

## 四、AOQ 的四大核心设计

### 4.1 全格式原生承载：一条连接跑完所有模态

单条 QUIC 连接内原生支持文本指令、语音消息、图片、大体积文件、实时流媒体的并行传输，无需按数据类型拆分多协议多连接。配套两个机制：

- **多模态时序强同步**：模型异步生成音频、视频、文本的速度各不相同，AOQ 通过全局时钟同步与关联映射机制完成强制同步，避免音画不同步、图文错位——这对数字人口型对齐、字幕跟随是刚需。
- **交互全链路加密**：控制指令、文件、实时音视频全时段密文传输，端云双向防劫持。

### 4.2 实时/非实时双模自适应：匹配大模型的输出节奏

大模型输出数据天然"快慢不均"——推理阶段有长尾延迟，生成阶段又可能爆发式吐流。AOQ 独创双模式机制：

- **实时模式（Real-Time Mode）**：面向麦克风、摄像头采集流等时效敏感数据，新鲜度和流畅性优先，允许丢旧包保时效。
- **非实时模式（Non-Real-Time Mode）**：面向完整性、顺序敏感且可提前发送的数据，可靠性优先 + 端侧超前缓存——服务端提前把模型要播的内容推到端侧缓冲，即使短暂断网也能续播，同时压低全链路延迟。

双模式可动态无缝切换。这个设计直击 LLM 流式输出"想快快不了、想稳稳不住"的痛点，是 AOQ 最有 AI 味的一笔。

### 4.3 极致抗弱网：升级 QUIC 内核 + 流级容错

AOQ 集成了专为实时媒体交互的弱网对抗增强，官方给出的硬指标是 **60% 丢包仍能对话流畅**：

- **0-RTT 极速建连**：增强 QUIC 的 0-RTT 特性，弱网环境下也能瞬间建立安全连接。
- **精准带宽估计与动态分配**：内置改进的带宽估计算法，感知网络瞬时波动后动态分配，优先保核心交互通道。
- **流级冗余保护与快速重传**：各模态独立建流，流维度隔离的前向冗余（FEC）+ 快速重传，不牺牲延迟即可消除弱网下的"滋滋"声与画面马赛克。

对比 WebRTC 的 GCC 拥塞控制（为视频大带宽设计，语音小流易被误判降级），AOQ 的带宽策略是围绕"低码率语音/小包流 + 突发文本事件"的 AI 流量画像定制的。

### 4.4 全球化部署：就近接入与全链路可观测

依托全球 Relay 节点和智能调度，客户端按真实 IP 分配最优接入点（鉴权响应直接下发 `clientRelayEndpoints` 数组）；从接入到传输全程可观测，按丢包、抖动等指标动态优化链路。对海外部署需求（机器人出海场景）有实际意义。

## 五、接入架构与工程要点

### 5.1 鉴权模型：API Key 不落端

AOQ 采用服务端代理鉴权，这是与 WebSocket 直连最大的工程差异：

```
客户端 App ──业务请求──> 业务 AppServer（持有 API Key）
                │
                │ POST /api/v1/webrtc/realtime
                │ Authorization: Bearer $DASHSCOPE_API_KEY
                │ x-dashscope-rtc-transport: moq
                ▼
           百炼网关 ──下发──> sid + aoqTokenForClient + Relay 接入点
                │
客户端 App <──临时 token── 业务 AppServer
    │
    └──持 token 连接 Relay Endpoint（QUIC/TLS，校验证书指纹）
```

要点：

- API Key 只存在业务 AppServer，客户端拿临时 token 连接，安全性优于把 Key 打进端侧。
- 每次新建连接前都应向 AppServer 请求新 token；会话（sid）有效期 7200 秒。
- 网关响应中包含 `clientRelayEndpoints`（接入点 IP + 端口）与 `clientRelayCertFingerprint`（TLS 证书指纹，防中间人），SDK 连接时直接配置。

### 5.2 SDK 形态与分轨传输

AOQ Client SDK 以闭源二进制包形态提供：Android（aar）、iOS（framework）、HarmonyOS（har），另有 Linux Python 版本。关键工程细节：

- **分轨传输**：Audio 轨负责上行麦克风 PCM 与下行模型 PCM，Data 轨负责 Realtime 协议事件（文本、指令、状态）。音频流与事件流隔离，互不阻塞。
- **Opus 编解码是独立插件**（`libPluginOpus.so`），不用 Opus 可不引入，SDK 体积可控。
- Android 侧 `minSdk 21`，支持 `armeabi-v7a` / `arm64-v8a` 双 ABI，嵌入式 Android 板卡可直接集成。
- SDK API 面很薄：`createEngine` 创建引擎 → `startAudioCapture` / `startAudioPlayer` 启动采播 → 回调监听 `onConnectionStatusChange` / `onDataMsg` / `onError`。音频采集支持外部注入（`isExternal = true`），可对接自研采音链路。
- 内置 AEC（回声消除）与降噪，端侧无需再挂 WebRTC APM 之类的音频处理栈。

### 5.3 支持的模型矩阵

| 模型类型 | 代表模型 | AOQ | WebRTC | WebSocket |
| :--- | :--- | :--- | :--- | :--- |
| 实时全模态 | qwen3.5-omni-plus/flash-realtime | ✓ | ✓ | ✓ |
| 实时语音对话 | qwen-audio-3.0-realtime-plus/flash | ✓ | ✓ | ✓ |
| 实时 ASR | Qwen-Audio-3.0-ASR-Flash-Streaming、Fun-ASR-Realtime | ✓ | ✗ | ✓ |
| 实时 TTS | CosyVoice 系列 | ✓ | ✗ | ✓ |
| 实时翻译 | qwen3.5-livetranslate-flash-realtime | ✓ | ✓ | ✓ |

## 六、机器人语音交互场景的选型判断

结合机器人研发实践（RK3588 / Android 板卡端侧 + 云端大模型架构），给出具体判断：

**AOQ 值得用的理由：**

1. **弱网是机器人常态**：商场、展馆的公共 Wi-Fi 拥塞严重，机器人移动中还会跨 AP 漫游。QUIC 连接迁移 + 60% 丢包生存能力，直接对应"导览机器人走到角落语音断断续续"这类真实故障。
2. **0-RTT 建连压缩 TTFA**：唤醒后建连近乎无感，省掉 WebRTC ICE/DTLS 协商的 0.5~1.5 秒，对"亚秒级首字响应"的体验锚点是实质贡献。
3. **内置 AEC/降噪减负端侧**：RK3588 上省下的音频处理算力可以留给 VAD 和意图识别。
4. **Android 板卡直接可接**：aar + arm64-v8a，与现有机器人 Android 主控天然兼容；Linux Python 版给 RK Ubuntu 部署留了通道。

**必须权衡的代价：**

1. **闭源 SDK + 生态绑定**：AOQ 是私有协议，出网关即黑盒。选择它意味着传输层与阿里云深度绑定，未来切换云厂商或做私有化部署时这部分要重写。对有国产化/私有化交付要求的机器人项目，这是硬伤。
2. **无浏览器支持**：Web 配套（远程运维面板、Web 端调试工具）仍需走 WebSocket/WebRTC 另建通道。
3. **Linux 侧仅 Python SDK**：机器人业务若为 C++ 主进程，集成 Linux 版需走 Python 桥接或进程间通信，架构上多一层。
4. **能力尚未经大规模第三方验证**：60% 丢包等指标来自官方演示环境，实际项目应按自身网络画像做压测基线（参考 Qwen3-TTS Realtime API 约 5% 稳定性异常的实测经验，官方指标与生产表现可能有差距）。

**选型结论**：

- 纯 TTS 单向播报、后端对接、快速原型 → **WebSocket**，成本最低。
- Web/App 浏览器直连、已有 WebRTC 基础设施 → **WebRTC**。
- 移动机器人、弱网环境、音视频 + 指令混合流、Android 原生端侧 → **AOQ 值得压测验证**，尤其在阿里云百炼已是模型供给方的前提下，接入边际成本很低。

## 七、冷思考：自研协议的行业信号

AOQ 不是孤例。OpenAI Realtime API 走 WebRTC，LiveKit 系开源栈押注 RTP/SFU，阿里另起 QUIC 灶台——实时 AI 交互的传输层正在从"借用音视频会议协议"转向"为 AI 数据特征定制协议"。判断这一趋势的两个锚点：

1. **标准化窗口**：IETF MoQ（Media over QUIC）正在标准化，若成熟，"AI over MoQ"可能成为开放生态的通用底座，私有协议的价值窗口期取决于 MoQ 落地速度。
2. **数据特征差异是真实的**：AI 交互的流量画像（双向低码率语音小包 + 突发文本 token 流 + 异步生成的多模态内容强同步）确实与传统会议音视频不同，为它定制传输层有工程合理性，不是纯营销叙事。

对机器人厂商的启示：短期内"协议选型跟着模型供给方走"是务实策略（用谁家 Realtime API 就用谁家最优协议），中长期应把传输层抽象成独立模块，保留 AOQ / WebRTC / WebSocket 可切换的能力，避免被单一协议锁定。
