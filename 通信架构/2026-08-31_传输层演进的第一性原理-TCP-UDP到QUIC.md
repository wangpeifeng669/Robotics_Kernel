# 传输层演进的第一性原理-TCP-UDP到QUIC

传输层四十年的演进，本质是在回答同一个物理问题：IP 网络天生不可靠且带宽共享，可靠性应该构建在什么粒度上。TCP 把可靠与有序绑死在"连接级单条字节流"上，造就了队头阻塞这一结构性缺陷；QUIC 借 UDP 的壳在用户态重建可靠，把粒度降到"流"。理解这条主线，比记住任何协议名词都重要——协议没有绝对快慢，只有可靠粒度和会话模型是否匹配业务。

---

## 1. 第一性原理：物理网络的三条约束

所有传输层协议都是对同三条物理事实的回应，先钉死它们，后面的演进才不是名词堆砌：

1. **IP 不可靠**。路由器队列会满、无线空口会受干扰，丢包、乱序、重复是常态而非异常。任何"保证送达"都是端侧协议栈自己造出来的幻觉。
2. **带宽是共享资源**。一条链路上挤着无数条流，任何一端不发愁地猛灌，都会让所有人一起变慢。拥塞控制不是性能优化，是公共资源治理。
3. **延迟有物理下限**。一个 RTT 是光/电信号在物理介质上跑一个来回的时间，纽约到上海约 70ms 起步，协议设计上每省一个 RTT，都是用户可感知的体感提升。

传输层协议的全部设计空间，就是在这三条约束下回答三个问题：

- **可靠给到什么粒度**？整条连接、单条流，还是单个媒体帧？
- **谁来刹车**？内核协议栈、用户态库，还是应用自己？
- **会话绑在什么上**？IP 四元组，还是自定义的连接身份？

四十年演进史，就是这三个答案不断被推翻重写的历程。

## 2. TCP：把可靠与有序绑死在一条字节流上

TCP（1974 年定义，1981 年 RFC 793 定稿）的设计目标是"绝对可靠"：三次握手建连、序号 + ACK 确认、超时重传、滑动窗口流控、四次挥手断连。它交付的不是包，而是一条**无界限、严格有序的字节流**。

| 特性 | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接（三次握手） | 无连接，直接发 |
| 可靠性 | 确认、重传、去重，保证送达 | 尽力而为，丢了不管 |
| 顺序 | 按序号重组交付 | 不保证 |
| 拥塞控制 | 有（滑动窗口、慢启动） | 无，应用自己控速 |
| 头部开销 | ≥20 字节 | 8 字节 |
| 交付模型 | 一条字节流 | 一个个数据报 |

UDP（RFC 768）则是另一个极端：只在 IP 上加了端口和校验和，"发出去就不管"。两者不是竞争关系，而是**两种合同**——TCP 承诺"对、齐、不丢"，代价是建连慢、重传拉高延迟；UDP 只承诺快发，对不对由应用自己处理。

常见误区先破掉三个：

- "UDP 一定更快"——空闲网络上 TCP 也很快，UDP 只是少了握手和重传等待；
- "TCP 一定不丢包"——链路仍会丢，只是协议层帮你重传，应用看起来像没丢；
- "内网可以随便用 UDP"——交换机也会丢包乱序，只是概率更低。

## 3. 历史的第一次教训：拥塞崩溃（1986）

第一性原理的第二条（带宽共享）很快给出了惩罚。1986 年 NSFNET 发生**拥塞崩溃（congestion collapse）**，吞吐从 32 kbps 掉到 40 bps，掉了三个数量级。机制是正反馈：

```
路由器队列满 → 丢包 → 主机超时重传同样的数据
→ 带宽都在传重复包，有效吞吐趋近 0
→ 更多超时 → 更多重传 → 循环放大
```

Van Jacobson 1988 年的回应是慢启动、拥塞避免、RTO 指数退避。今天教科书里的 TCP，很大一部分就是为了回答"超时重传会不会把网挤死"。这个历史埋下了后面所有故事的关键伏笔：**TCP 的每个设计决定，都要向"全网公平性"交税。**

这里有一条重要的工程结论，破除"弱网换 UDP 就好"的迷思：现代 TCP 超时后会先刹车——快速重传只把拥塞窗口减半，RTO 超时则窗口掉回初始量级、退避时间 1s→2s→4s 翻倍。弱网里体感"这条流越传越慢"，对这一条流是灾难，对整网它其实在**让路**。而裸 UDP 不重传也不减速，继续按原速率猛灌——**没有刹车的 UDP 灌包，比会刹车的 TCP 超时更容易打满接入网**。IETF 专门写了 RFC 8085 要求长时占带宽的 UDP 应用自己做拥塞控制。

真正危险的不是 TCP 重传，而是叠加效应：**应用层短超时狂重连（retry storm）+ 大量用户同时超时 + 无线丢包被误判为拥塞 + 缓冲膨胀**。这些会把网关和最后一公里搞到不可用。

## 4. 队头阻塞：结构性缺陷的显形

TCP 的字节流模型在网页时代遇到了致命问题。接收端必须按序交付：

```
发送： [1][2][3][4][5][6]
网络： [1][2]  X  [4][5][6]     ← 包 3 丢了
接收： 应用只能拿到 1、2
       4、5、6 已经躺在缓冲区里，必须等 3 重传回来
```

后面的数据**物理上已经到达，逻辑上不能交付**——这就是队头阻塞（HOL Blocking）。从第一性原理看，根因是：**可靠与有序被绑在"连接级的一条字节流"这个过大的粒度上**。这不是调参能修好的，是数据模型问题。

HTTP 的三代演进，就是这个缺陷逐层显形又逐层转移的历史：

| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|----------|--------|--------|
| 底层传输 | TCP | TCP | UDP (QUIC) |
| 报文格式 | 明文文本 | 二进制分帧 | 二进制分帧 |
| 并发模型 | 串行/开 6~8 条 TCP 连接 | 单连接多路复用 | 单 QUIC 连接多流 |
| 队头阻塞 | HTTP 层（请求占线） | 解决了 HTTP 层，**TCP 层更严重** | 传输层跨流阻塞消除 |
| 头部压缩 | 无 | HPACK | QPACK（适配乱序） |
| 建连延迟 | 1~3 RTT | 1~2 RTT | 0~1 RTT |
| 网络切换 | 断连重握手 | 断连重握手 | Connection ID 无缝迁移 |

- **HTTP/1.1 时代**：应用层工程变通（CSS Sprites 精灵图、文件合并、域名分片），代价是开发复杂度；
- **HTTP/2 时代**：单连接高并发，废弃了精灵图等旧技巧——但所有 Stream 挤在一条 TCP 里，丢一个包**全部 Stream 连坐阻塞**。弱网高丢包时 HTTP/2 甚至可能比多连接 HTTP/1.1 更慢；
- **HTTP/3 时代**：承认传输层无药可救，换底座。

## 5. QUIC：为什么是借 UDP 的壳，而不是 TCP v2

既然是改进 TCP，为什么不直接改 TCP？三个字：**改不动**。

1. **内核僵化**。TCP 跑在 OS 内核里，改协议要等 Windows/Linux/iOS/Android 全部升级内核，周期 10~15 年；
2. **中间盒毒化**。互联网上的路由器、防火墙、NAT 只认传统 TCP 头，任何新 Option 都可能被当"异类包"丢弃——这就是"协议僵化（ossification）"；
3. **UDP 是天然的用户态通道**。所有系统和防火墙都放行 UDP，QUIC 可以作为普通应用程序库运行，更新一个 App 就能向全球推行新特性。

所以准确的理解是：**QUIC 是穿了 UDP 外套、运行在用户态的重构版 TCP**。UDP 只扮演"能穿越 NAT 的不可靠管道"，可靠性、流控、拥塞控制、加密全部在用户态重新实现——并且顺手修掉了 TCP 四十年的架构欠账：

```
传统栈                          QUIC 栈
┌───────────────┐              ┌───────────────┐
│ HTTP/2        │              │ HTTP/3        │
├───────────────┤              ├───────────────┤
│ TLS 1.3       │ ← 分层解耦   │ QUIC          │ ← Stream+可靠
├───────────────┤              │ (加密+拥塞控制)│    +TLS 合一
│ TCP           │ ← 不知 Stream│ ├───────────────┤
└───────────────┘              │ UDP           │
                               └───────────────┘
```

## 6. QUIC 的四个重构：逐个拆

### 6.1 Stream 隔离——把可靠粒度从"连接"降到"流"

QUIC 在协议头里原生支持 Stream ID，每条流有独立的偏移量、流控窗口和重传。Stream 1（图片）丢包，只有 Stream 1 等重传；Stream 2（文字）、Stream 3（音乐）**已经到达就立即交付**。

但要精确：**QUIC 消除的是跨流阻塞，不是全部阻塞**。同一条流内部丢包照样等重传；连接级拥塞窗口是共享的，丢包会让所有流一起变慢（但这是"变慢"，不是"到了的数据交不上去"）。

### 6.2 Packet Number 单调递增——消灭重传歧义

TCP 重传包复用原序号，收到 ACK 时无法区分回应的是原包（只是迟到）还是重传包，RTT 估算被污染。QUIC 规定**每个包严格单调递增、永不重用**——重传是新包号 + 原 Stream Offset，RTT 计算一清二楚。ACK 还带延迟信息，可扣掉接收端憋 ACK 的时间。序号和帧内容几乎全部加密，中间盒读不懂，也就没法"优化坏"。

### 6.3 握手合并——2 RTT 压到 1 RTT 甚至 0 RTT

传统 HTTPS：TCP 握手 1 RTT + TLS 握手 1 RTT，才能发第一个请求。QUIC 把传输握手和 TLS 1.3 握手强绑定：首次连接 1 RTT；恢复连接用会话票证，**第一个包就带上加密的业务数据（0-RTT）**。注意 0-RTT 有重放风险，只适合幂等请求——GET 可以，扣款 POST 不行。

### 6.4 Connection ID——连接身份与 IP 解耦

TCP 靠四元组（源 IP + 源端口 + 目的 IP + 目的端口）标识连接，手机从 Wi-Fi 切到 5G、IP 一变连接就断，必须重新握手。QUIC 用协商的 Connection ID 标识连接，路径变了服务器照样认出你，走出电梯**用户完全无感**（新路径要过 PATH_CHALLENGE 防伪造源地址）。

### 6.5 代价与未竟之事

QUIC 不是免费的：用户态实现带来 CPU 开销；UDP 可能被运营商 QoS 限速或企业网封锁（浏览器策略是失败即回退 HTTPS/TCP）；QPACK 动态表项依赖仍可能造成应用层等待。

## 7. 弱网场景的组合拳

电梯、地铁等高丢包场景下，QUIC 各机制如何协同（丢包率可达 20%~30%）：

| 场景 | TCP 的表现 | QUIC 的应对 |
|------|-----------|-------------|
| 进出电梯切网 | 四元组变化，连接断开，重握手 100~300ms | Connection ID 迁移，无感续传 |
| 高丢包连坐 | 一个包丢失，已到达的文字/音乐全被扣住 | Stream 隔离，先到的先展示 |
| RTT 估算失真 | 重传歧义导致拥塞控制误判、盲目减速 | 包号单调，毫秒级精确 RTT |
| 等重传卡顿 | 一来一回上百毫秒 | 应用层 FEC：10 个包带 2 个冗余包，丢了直接"算"出来 |
| 重新打开 App | 重新 TCP+TLS 握手 | 0-RTT 秒开 |

这就是抖音、微信、淘宝全面转向 QUIC 的原因。但注意 FEC 抗丢包的边界："60% 丢包还能流畅"意味着音频走了部分不可靠/快进——字可能糊、可能跳，但不断麦。这对通话有意义，对"每个字都要念准"的播报型 TTS 未必是你要的。

## 8. 弱网的第一性原理

把整个弱网问题收束成一句话：**过时数据不要救，有效数据才重传，路堵了就少发。**

- TCP 的风险是"越丢越重传，再加应用层重试"；
- 裸 UDP 的风险是"越丢越不减速，照样狂发"；
- 三种 UDP 用法结果完全相反：裸 UDP 改善的是播放流畅不是拥塞；UDP 上自己做全可靠等于劣质 TCP；只有 **UDP + 部分可靠 + 拥塞控制**（QUIC/WebRTC/RTP+NACK+FEC）才谈得上改善——而且起作用的是策略，不是 UDP 这个名字。

工程上比"选哪个协议"更重要的四条军规：重试必须带抖动、上限、幂等键；合成结果按 task_id 去重；不要在 TCP 还活着时用短超时狂重连；接入层对半开/慢连接做数量和时长限制。

## 9. 演进的元规律：可靠粒度持续细化

现在可以站在高处俯瞰整条演进线了：

```
IP ─ 不可靠数据报（物理事实）
 ├─ TCP ─ 连接级可靠字节流          ← 可靠粒度：整条连接
 │   ├─ TLS + HTTP/2
 │   └─ WebSocket ─ 全双工消息通道
 └─ UDP ─ 裸数据报（逃生通道）
      └─ QUIC ─ 用户态可靠 + 多流    ← 可靠粒度：单条流
           ├─ HTTP/3 ─ 网页、流式下载
           ├─ WebTransport ─ 浏览器里的 WS 继任者
           └─ AOQ / MoQ ─ 音频轨+数据轨 ← 可靠粒度：按轨区分
```

规律一：**可靠粒度从连接 → 流 → 轨，持续细化**。每次细化都对应一类新业务：网页多资源并发催生了流级隔离，实时音视频催生了轨级区分（媒体轨可丢帧保流畅，控制轨独立可靠）。

规律二：**协议栈从内核迁往用户态**。迭代速度从"10~15 年等内核"变成"发一个 App 版本"。

规律三：**会话模型比传输名字重要**。落到机器人语音业务（TTS 选型）：

- 典型 TTS 是**一条有序音频流**，QUIC 的跨流 HOL 优势派不上用场——音频必须按时间轴连续播，这条流丢包照样等重传，和 WebSocket 底下的 TCP 没有本质区别；
- 延迟大头在**合成首帧（100~400ms+）**，不在传输握手（省 1 个 RTT 只有几十毫秒），长连接复用后握手优势进一步摊薄；
- 对话式、LLM token 流入、可打断 → WebSocket 仍是对症的主流选择（讯飞/阿里/火山/Azure/OpenAI Realtime 均如此）；
- QUIC/AOQ 真正赢的场景：移动端实时对话——多轨隔离（丢音频帧 ≠ 冻住打断指令）、连接迁移、SDK 内置 3A 回声消除。注意这是"带媒体栈的私有实时套件 vs 消息通道"的比较，不是"QUIC vs TCP"。

正确姿势：**同一套业务事件，端上走 AOQ，中台走 WS，按端选择传输，而不是按信仰选择传输。**

## 10. 一张判断清单

评估任何传输方案（包括厂商宣传）时，问这六个问题：

1. 可靠粒度是连接、流，还是轨？
2. 控制面和媒体面有没有隔离？
3. 丢包时是卡死、重传，还是允许丢帧保流畅？
4. 换网之后会话还在吗？
5. 这是开放协议，还是必须绑定对方 SDK？
6. 堵了之后是减速让路，还是原速率重传/应用层整段重发？

六个问题问完，TCP/UDP/QUIC/WebSocket/AOQ 就不再是名词，而是同一套权衡在不同层上的实现。
