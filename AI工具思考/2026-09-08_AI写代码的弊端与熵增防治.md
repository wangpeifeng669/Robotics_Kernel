# AI写代码的弊端与熵增防治

**核心摘要**：AI 不必然把代码写坏，它默认沿阻力最小路径交货——没有落点时，这条路径就是"打开已经很大的文件，再塞一个 if"。熵经六条路径进入：往大文件打补丁、复制而非抽变体、同一件事叠三层、死代码误导下一轮、无契约用探测补洞、提示词只当哲学。防治靠落点地图、指定模块、超限先拆、机械门槛、按初级工程师审 diff、对话短停。日历式大重构是补救，不是防治。

## 一、问题不在「会不会写」，而在「往哪写」

AI 优化的是「这次任务能不能过」，不是「三个月后还能改」。每次对话都是局部视野：它看见当前打开的文件、最近的调用栈、你这句话里的现象，看不见系统在半年里是怎么长歪的。

人写代码也会堆补丁，但速度慢，痛感来得早。AI 把同一条路径加速了十倍：功能一周能堆完，结构债也一周能堆完。于是团队的体感变成「AI 把代码写乱了」。更准确的说法是：**没有结构约束时，AI 是高效的熵增引擎；有约束时，它同样能高效降熵。**

一次对照就够说明差异。同一类需求——「三种很像、只有配置不同的实现」——两种做法：

- 把公共运行时抽出来，差异放进 profile / 策略对象，三个入口各几十行。下次改采音、改超时，只改一份。
- 复制三套包，再在最大的那个节点里加分支。下次修 bug 改错一份，三套开始分叉，直到必须整包重构。

边界清楚时，AI 做得很好；只说「把功能加上」时，它几乎总会选第二种。所以问题从来不是「AI 不会写」，而是「没人告诉它该写到哪、什么不能碰」。

## 二、熵从哪些路径进来

### 2.1 往最近的大文件打补丁

典型路径：打开已经 800 行的服务类 → 在现有回调里加分支 → 不问「这职责该不该在这里」→ 文件涨到 1200 行。提示词里写了「单文件不超过 300 行」，但任务若是「把开麦时序修一下」，遵守提示词的成本高于再加一个方法。模型会选能过测试的最短路径。

上帝对象一旦形成，就会成为所有后续对话的默认落点。越胖越容易被打开，越被打开越胖。

### 2.2 复制，而不是抽变体

硬件有三种麦阵、支付有三家渠道、部署有两套环境时，最快的实现是拷贝目录改几行。真实差异往往只有路径、通道数、默认设备、一个策略开关。复制之后，热插拔、超时、日志格式会在副本之间漂移。AI 没有「这三份其实是一个东西」的记忆，下次只会改它搜到的那一份。

正确切口是：**一种职责一份源码，变体用配置或策略对象。** 禁止再复制第四套。

### 2.3 同一件事叠三层

语音链路上很常见：前端引擎有一层 VAD，识别前再做人声门控，云端还有静音超时。Web 上也常见：网关鉴权、服务鉴权、数据库行级权限各写一套，口径还不一致。调「误触发」或「截尾」时，AI 不知道该动哪一层，三层都拧一点，行为更难推理。

叠罗汉的标志是：改一处时序，另外两处 silently 分叉。

### 2.4 死代码和过时文档误导下一轮对话

Agent 没有跨会话记忆。它读到的「现在」就是仓库里还活着的文字：已下线的启动包、过时的话题发布者、根目录孤立脚本、仍把旧模块写成入口的 README。下一轮会按旧地图改错地方，再留下一层新补丁。

删掉死代码、让文档与代码同一次提交更新，不是洁癖，是给后续 Agent 的输入消毒。

### 2.5 没有契约，用探测补洞

`hasattr` 判断客户端有没有某个方法、改 import 切换实现、用类变量在模块间塞全局状态。AI 加一种厂商或一种模式时，不知道该改工厂还是改调用方，两种都会改一点。接口继续以「现在能跑」为定义，而不是以类型和工厂为定义。

契约先行的意思是：先有接口和策略对象，再写实现。不是先堆能跑的分支，再指望以后抽象。

### 2.6 提示词是哲学，不是地图

「函数不超过 40 行、文件不超过 300 行、禁止堆 if」方向正确，但回答不了「改开麦时序该动哪个文件」。全局文风管「怎么写」，管不住「写到哪」。没有仓库级落点时，哲学约束会被「先把功能做上」压过。

## 三、为什么定期重构不够

等乱到必须开一次「重构整个交互」「重构三套算法」，成本和回归风险已经很高：要在行为表面上不变的前提下，把几个月的补丁重新切开。

定期大重构的问题：

- 它承认日常交付没有结构约束，债是故意攒的。
- 两次重构之间，AI 仍按最小阻力生长，重构幅度会被下一批功能抵消。
- 大重构本身也常半途：抽出一层策略，上帝类还在。看起来「重构过了」，下次功能的落点其实没变。

大重构只留给**架构变更**：合并复制包、拆上帝节点、换掉跨模块的全局状态。日常功能用童子军规则——动到的文件带走一点混乱；超限则**先拆再改**，不要「这次先加上，下周再重构」。

## 四、怎么避免加速熵增

杠杆从大到小。前三条比再加长提示词有用。

### 4.1 先有落点地图，再让 AI 动手

给仓库一份短的、Agent 会自动读的说明（例如根目录 `AGENTS.md`）：只写包职责和「改 X 只动 Y」，不写文风。文风放在编辑器的全局规则里。

地图必须可执行。坏例子：「保持整洁、注意复用」。好例子：「开麦 / 关麦 / 播放期间是否采音，只改 `session_policy`；节点只执行策略对象，禁止再堆时序分支。」

结构变了，地图必须同一天改。过时的地图比没有地图更糟，它会把 Agent 精确地推向旧落点。

### 4.2 任务指定模块，而不是指定现象

| 少这么说 | 改成 |
| --- | --- |
| 把开麦时序修一下 | 只改策略模块，节点不准加业务分支 |
| 再加一种类似的后端 | 新增 profile / 策略，禁止拷贝包 |
| 接一个新厂商 | 实现已有接口，只改工厂分支 |
| 检索再调准一点 | 只动检索客户端，不要写进编排节点 |

写清**不准动的文件**，比写「请保持架构清晰」有效。

### 4.3 超限先拆，同一条改动里完成

给体量设死线（例如单函数几十行、单文件三百行、嵌套不超过三层）并不重要，重要的是**超了就先拆**。已经 1000 行的文件，本轮若还要加逻辑，先把那块搬到它该去的目录，再改行为。不要在胖子身上继续贴。

半途重构的标志：新目录有了，旧文件一行没少。那只是多了一个调用转发，落点仍是旧文件。

### 4.4 用机械门槛补提示词

提示词没有牙齿。对仓库最值钱的检查往往很窄：

- 禁止新增拷贝包（目录名模式直接失败）
- 厂商 SDK / 生成代码 / 资源目录只读
- 已点名的上帝文件行数只许下降、不许上升

模型对「会被拒绝」比「请保持优雅」敏感。门槛要少、要硬，不要做成又一份风格指南。

### 4.5 把 AI 当初级工程师来审 diff

每次只问三句：

1. 新逻辑是进了已有大文件，还是进了事先约定的落点？
2. 是复制了一份，还是复用了接口、profile 或策略对象？
3. 新分支能不能收进已有策略，而不是再开一个条件漏斗？

过不了就先拆再改，不要合并。不要用「以后重构」换过审。

### 4.6 对话要短，结构歪了就停

长对话里，早期选错的结构会被后续轮次当成既成事实继续长。功能做完但结构歪了：停掉，新开对话，附上地图和「只准改这些文件」。不要在已经打满补丁的线程里让它「再优化一下」——它会优化补丁，而不是拆掉补丁。

## 五、提示词怎么分工

三层各管一件事，叠在一起才会生效：

| 层 | 放什么 | 不放什么 |
| --- | --- | --- |
| 全局 User Rules | 体量、命名、注释语言、禁止堆补丁 | 某个仓库的目录职责 |
| 仓库 `AGENTS.md` / 项目规则 | 包职责、改 X 只动 Y、只读目录 | 长篇哲学、过时模块名单当百科 |
| 单次任务 | 准改 / 不准改的文件、验收行为 | 「顺便重构一下整个系统」 |

全局规则解决不了落点问题；仓库地图解决不了「这次到底改哪几个文件」；单次任务解决不了下一次对话失忆。少哪一层，熵就从那一层漏进来。

可把下面这段当作新任务的默认开头，再补上本仓库的具体文件名：

```text
先读仓库落点说明。对表改代码：策略进策略模块，节点只做编排。
禁止复制包。已超限的文件先拆再改，不准继续追加。
注释只写为什么。
```

做完用 4.5 的三句话审 diff。过不了就拆，不要靠定期重构救命。

## 六、结论

一句话收束：**结构熵不是 AI 的固有属性，而是「没有落点」的默认行为。** 防治的杠杆全部落在"提前把落点、契约、边界写成可执行的东西"上——落点地图管住"写到哪"，机械门槛管住"什么不许碰"，三句话审 diff 管住"过不过审"。这三样都比再加长提示词、再开一次大重构有用，因为它们在补丁产生之前就把它挡在门外。
