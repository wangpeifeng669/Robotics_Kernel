## 五、节奏规律与使用特征

### 5.1 工作节律

1. **工作日密集，周末明显回落**：5/10（周六）、5/23、5/31（周末）请求量骤降至个位数，休息边界清晰，没有把 AI 用成 7×24 小时焦虑工具
2. **深夜使用极少**：00:00–06:00 近乎空白，主力时段集中在 09:00–18:00，符合正常工作状态
3. **三段式专注节奏**：峰值出现在 10:00（上午专注期）、15:00（下午复工期）、17:00（收尾冲刺期），12:00 明显低谷，午休习惯稳定
4. **高强度攻坚日存在**：5/08 单日 ~70 次请求 / 3,000 万 token，是均值的 2 倍以上，典型的"功能突破日"

### 5.2 使用方式

5. **缓存命中率极高（86%）**：习惯将整个工程目录作为上下文，每次对话都在复用大量已有代码——机器人/AI 工程代码耦合度高、需要全局视野时这是合理选择，但也带来额度消耗较大的副作用
6. **单次上下文体量大**：多条记录单次 Cache Read 超过 100 万 token，对应场景很可能是让 Cursor 跨文件理解 pipeline 架构（ASR→VAD→LLM→TTS）并进行修改
7. **thinking 模型克制使用（3%）**：`claude-4.6-sonnet-medium-thinking` 仅在复杂推理场景启用，没有无脑全开，说明对模型能力边界有清醒认知
8. **三档模型分工初步成型**：auto 处理日常补全，composer-2.5-fast 承担多文件任务，thinking 保留给高难度场景——分工逻辑合理

## 六、使用优化建议

### 6.1 上下文管理——最值得改进的一项

当前 86% 的 token 消耗来自缓存读取，大量上下文对当前任务并不必要。

- **按任务开新对话**：避免一个 Composer 会话无限滚动。当话题从"修 ASR 模块"切换到"调 TTS 参数"时，新开对话，上下文归零
- **子模块独立上下文**：ASR、LLM、TTS 各自维护独立的 Composer 会话，而不是在一个超长会话里反复切换
- **收益**：响应更快、模型注意力更集中、额度消耗降低

### 6.2 模型选择策略——明确三档边界

composer-2-fast（占 11%）和 composer-2.5-fast 之间的切换边界目前不够清晰，建议固化规则：

| 场景 | 推荐模型 |
|------|---------|
| 代码补全、单文件修改、快速问答 | `auto` |
| 多文件 Composer、跨模块重构 | `composer-2.5-fast` |
| 架构设计、复杂 bug 根因分析、算法推导 | `claude-4.6-sonnet-medium-thinking` |

> 避免用 thinking 模型处理"帮我加个注释"这类任务，浪费额度且无收益

### 6.3 攻坚日策略——大任务拆小再执行

峰值日 token 消耗是均值 2–3 倍，往往因为"一次性让 Cursor 解决一个大问题"。

- **攻坚前做任务分解**：把大问题切成 3–5 个独立 Composer 子任务分批执行，避免单次上下文过长导致模型遗忘早期约束
- **留存记录**：攻坚日结束后写一条工作日志，记录解决了什么问题——高强度输出值得留痕，也便于复盘

### 6.4 碎片化请求整合

部分日期存在大量 token 极小（< 10 万）的请求，属于频繁的"小问题小问"模式。

- **攒批处理**：同类型小问题一次性提交，比如"以下三个函数的命名规范有什么问题？"，比三次独立请求效率更高，上下文也更连贯
- **复用 prompt 模板**：对高频任务（如代码 review、接口文档生成）建立固定 prompt 格式，减少每次重新描述的成本

### 6.5 错误率监控

当前错误/中止率约 3.7%，属正常范围。如某类任务错误率偏高，考虑将该任务的 prompt 模板化，减少模型误解。
