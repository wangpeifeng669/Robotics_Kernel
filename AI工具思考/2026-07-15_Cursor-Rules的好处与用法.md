# Cursor Rules 的好处与用法

> **核心摘要**：Cursor Rules 把"编码约定"从每轮对话的口头叮嘱变成持久、可版本化、自动注入的指令。本文讲清四类规则（Always / Auto Attached / Agent Requested / Manual）的适用场景与写法，并附一份可直接落地的全中文编码规范实例。

## 一、为什么要在 Cursor 里写 Rules

不写 Rule 时，Agent 的默认假设是：这是一个通用的、要编译要跑的软件项目。结果就是——你每轮对话都得重复叮嘱：

- "用中文回复，别用英文"
- "变量用全英文，注释用中文"
- "别直接堆 if，先重构"
- "时间默认用东八区"
- "装依赖走国内源"

这些话你今天说、明天说、换个项目还得再说一遍。更糟的是 **约定只存在你脑子里**：换台机器、换个同事、隔两周再打开，约束就丢了，Agent 又按默认习惯乱来。

Cursor Rules 解决的就是这件事：把约定固化进仓库 / 设置，让它 **每次、每个文件、每个会话自动生效**。

| 约束方式 | 持久性 | 是否自动生效 | 适合场景 |
|----------|--------|--------------|----------|
| 聊天里口述 | 否（关掉就没） | 否，需重复 | 一次性临时的小调整 |
| `@引用` 文件 | 否（需手动 @） | 否，需每轮 @ | 点状补充某份文档 |
| Notepads | 否（临时上下文） | 否 | 临时拼装上下文 |
| **Cursor Rules** | **是（进 Git / 设置）** | **是，按类型自动** | **长期、可复用的约定** |

写 Rules 的六个实在好处：

1. **持久化**——一次写，永久生效，不用每轮重复。
2. **版本化**——进 Git，团队和自己都能迭代、回滚、Code Review。
3. **自动注入**——无需每次 @ 或复述，规则在 prompt 开头就就位。
4. **一致性**——命名、架构、注释风格全仓库统一。
5. **防错**——把"禁止做什么"变成硬约束，比对话里骂一句有效。
6. **省心省钱**——一条规则顶几百次重复叮嘱，长期比反复对话便宜。

## 二、Cursor Rules 的两种层级与四种类型

Cursor 的 Rule 分两个层级：

- **User Rules（用户级）**：全局，在 `Settings → General → Rules for AI` 里配置，你的所有项目都生效。适合放个人偏好（语言、提交习惯、通用风格）。
- **Project Rules（项目级）**：放在仓库的 `.cursor/rules/*.mdc`，随仓库版本化，**只对当前项目生效**。适合放"这个仓库是什么 / 怎么写"。

> 此外还有两个补充形态：`.cursorrules` 是旧版单文件规则（**已弃用**，建议改用 Project Rules）；`AGENTS.md` 是纯 Markdown 的轻量替代（不想用 `.mdc` frontmatter 时可考虑）。

项目规则的"何时生效"由 frontmatter 里的三个字段（`alwaysApply` / `globs` / `description`）组合决定，官方归纳为 **四种类型**：

| 类型 | frontmatter 组合 | 生效时机 | 适合放什么 |
|------|------------------|----------|------------|
| **Always** | `alwaysApply: true` | 每次会话都注入 | 仓库性质、不可妥协的硬约束 |
| **Auto Attached** | `globs: 模式`，`alwaysApply: false` | 引用/打开匹配文件时 | 框架或目录专属规范（最可靠，确定性匹配） |
| **Agent Requested** | `description: 写清楚`，无 `globs`，`alwaysApply: false` | 模型判断描述相关时 | "写测试时""做迁移时"这类场景化指引 |
| **Manual** | 三个字段都留空 | 聊天里 `@规则名` 才生效 | 长清单、迁移手册（不想每轮占上下文） |

**选型要点**：

- 全局偏好 → 用 **User Rules**。
- 仓库约定 → 用 **Project Rules**，几乎必配一条 `Always` 声明"本仓库的性质与产出形式"。
- 某类文件专属规范（如 `src/components/**/*.tsx`）→ 用 **Auto Attached**，最稳。
- 场景化指引（"USE WHEN 写测试"）→ 用 **Agent Requested**，描述要带触发短语。
- 沉重的长文档 → 用 **Manual**，需要时才 `@` 调出来。

> **成本提醒**：Always 规则最贵——它的全文会 prepend 到每一次 prompt。社区经验是：所有 `alwaysApply: true` 规则加起来控制在约 **500 行 / 2000 token** 以内。所以"Always"要克制，能 Auto Attached 的就别 Always。

## 三、怎么写一条 Rule（格式与位置）

**文件位置与命名**：放在仓库根目录的 `.cursor/rules/` 下，扩展名必须是 **`.mdc`**（注意不是 `.md`——`.md` 文件会被忽略！）。例如：

```text
.cursor/rules/
├── coding-standards.mdc     # 识别为项目规则
└── api-guidelines.md        # 被忽略（扩展名错误）
```

**文件结构**（MDC 格式 = frontmatter + Markdown 正文）：

```markdown
---
description: 全中文编码规范——命名、注释、体量、时区、国内源
globs:            # 留空则配合 alwaysApply 控制；填了就 Auto Attached
alwaysApply: true
---

# 核心哲学
- 角色：资深架构师。始终对抗代码熵增，坚守代码极简与高可复用原则。
...
```

**三个 frontmatter 字段**：

| 字段 | 作用 |
|------|------|
| `description` | 规则摘要；Agent Requested 模式下模型据此判断是否相关 |
| `globs` | 逗号分隔的文件模式，匹配时自动挂载（Auto Attached） |
| `alwaysApply` | `true` 则每次会话注入（Always） |

**正文写法**：纯 Markdown。可以有表格、✅/❌ 示例、代码片段。规则里还能用 `@文件名` 引用仓库里的真实文件当上下文，避免把示例代码抄进规则、又防止它过时。

**创建方式**（任选其一）：

- 命令面板 `Ctrl/Cmd + Shift + P` → 输入 `New Cursor Rule`，自动在 `.cursor/rules/` 生成带 frontmatter 的空 `.mdc`；
- `Cursor Settings → Rules` 里可视化添加；
- 对话里直接 `/Generate Cursor Rules` 或 `/create-rule`，让 Agent 帮你从本轮决策反推规则。

**嵌套规则**：子目录也能有自己的 `.cursor/rules/`，只对该目录范围生效——Monorepo 里 `backend/`、`frontend/` 各放一份是天然做法。

## 四、让 Rule 真有用的编写原则

1. **一条规则一个关切**——仓库性质（"这是知识库不是代码仓"）和领域规范（"端侧部署必含板卡型号表"）分开写。
2. **短而可执行**——单文件理想 < 50 行，所有规则合计 < 500 行；用表格和 ✅/❌ 示例，少写套话。
3. **给具体例子，别写空话**——"用全英文命名"不如"禁止拼音、拼音缩写、中式英文"来得明确。
4. **可迭代**——踩一次坑就改一次 Rule，然后 commit，全仓库 Agent 行为一起升级。
5. **用对层级**——个人偏好进 User Rules，仓库约定进 Project Rules，别混。

## 五、实战：一份可直接落地的全中文编码规范 Rule

下面这份规则来自真实使用中的 `cursor_rules.txt`，是一份典型的 **编码规范类 Project Rule**——覆盖了体量控制、命名注释、时区、异常、全中文交互、国内源。它把"对抗代码熵增"的硬约束一次性固化，省去每轮叮嘱。

### 5.1 作为 Project Rule 的用法

在仓库建 `.cursor/rules/coding-standards.mdc`，把下面整段（含 frontmatter）粘进去即可。因它要求"全局强制"，用 `alwaysApply: true`；若你希望只对源码文件生效，可把 `globs` 设为 `**/*.{ts,tsx,py,go,java}` 并改 `alwaysApply: false` 变成 Auto Attached。

```markdown
---
description: 全中文编码规范——命名、注释、体量、时区、异常、国内源
alwaysApply: true
---

# 核心哲学
- 角色：资深架构师。始终对抗代码熵增，坚守代码极简与高可复用原则。

# 一、 严格体量与复杂度控制
- **体量死线**：单个函数限制在 40 行以内，单个文件限制在 300 行以内。超限必须主动提出模块化拆分方案。
- **嵌套控制**：代码嵌套深度严格控制在 3 层以内。一律优先使用卫语句提早返回，消除多余的条件分支。
- **拒绝盲目追加**：禁止直接堆砌条件判断打补丁。涉及新逻辑必须重构优先，严防代码臃肿。
- **契约先行**：禁止使用宽泛或未知类型。必须先定义好清晰的接口或数据结构，再编写核心业务实现。

# 二、 注释、时区与异常防线
- **全英文命名**：变量、函数、类及文件名必须使用地道全英文，**绝对禁止拼音、拼音缩写或中式英文**。
- **纯中文业务注释**：所有代码注释和文档字符串必须使用纯正简体中文。**严禁单纯翻译代码，不解释"做了什么"，只解释"为什么这么写"（阐明业务考量、特殊逻辑与潜在陷阱）**。
- **标准时区防线**：所有时间、日期、定时任务处理默认使用中国标准时间（东八区），必须显式指定时区参数，严防时间偏差漏洞。
- **异常捕获**：严禁仅处理正常流程。涉及网络、异步或核心计算必须编写完整的边界防御与错误捕获。

# 三、 交互与全中文输出规范
- **全中文交互**：与用户的所有对话、方案设计、技术解释，**必须百分之百使用专业、通顺的简体中文输出**。
- **精准代码输出**：修改代码时仅输出受影响的代码块或明晰的差异部分，严禁打印未修改的完整大文件。
- **架构自述**：代码进行结构性调整（如解耦、重构）后，必须在代码块下方用一句话纯中文精炼说明架构学理由。

# 四、 国内镜像与下载源（默认强制）
- 安装依赖、拉模型、克隆仓库、下载镜像时，默认使用国内源；仅用户明确要求时才用国外官方源。
- 给出的命令须直接带国内源参数。常用源：
  - npm：`https://registry.npmmirror.com`
  - pip/uv：`https://pypi.tuna.tsinghua.edu.cn/simple`
  - Go：`https://goproxy.cn`
  - Maven：`https://maven.aliyun.com/repository/public`
  - Hugging Face：`https://hf-mirror.com`
  - Docker / GitHub：优先国内镜像或加速地址
```

### 5.2 作为 User Rules 的用法

如果你的所有项目都想套用这套风格，不必每个仓库都建文件——把 `# 核心哲学` 到 `# 四、...` 的**正文部分**直接粘进 `Settings → General → Rules for AI`（User Rules 没有 frontmatter，纯文本即可）。这样无论打开哪个项目，全中文、东八区、国内源都是默认行为。

### 5.3 这份规则的设计意图（逐节解读）

- **核心哲学 / 体量死线 / 嵌套控制**：用"函数 ≤40 行、文件 ≤300 行、嵌套 ≤3 层"把抽象的质量目标变成可检查的硬指标，逼 Agent 主动提拆分而非堆代码。这是对抗 AI 生成"越写越长"最常踩的坑。
- **全英文命名 + 纯中文注释**：分开约束"标识符"和"说明文字"，既保证代码国际化可读，又让业务意图对中文团队零损耗。关键在注释只讲"为什么"，避免翻译式废话。
- **时区防线**：AI 极易在 `datetime.now()` 上漏时区，导致定时任务差 8 小时。强制"显式东八区"是真实踩坑后的硬约束。
- **异常捕获**：禁止只写 happy path，把网络/异步/计算的边界防御变成必选项，提升生成代码的健壮性。
- **全中文交互 / 精准输出 / 架构自述**：约束 Agent 的输出形态——中文回复、只贴差异、重构后一句话交代架构理由。这三条直接决定"AI 写的代码你能不能放心接手"。
- **国内源强制**：把"装依赖走镜像"从每次手敲参数变成默认行为，省时且避免墙内超时。

> 这套规则的精髓不在某一条，而在于 **把"资深工程师的自律"外化成 Agent 的约束**。你不需要每次 review 它有没有用拼音、有没有漏时区——Rule 已经替你盯住了。

## 六、验证：你的 Rule 是否真的生效

改完 Rule 后，用三则探针 prompt 自测（以本文编码规范为例）：

1. 「给这个模块加个新功能」→ 生成代码应全英文命名、中文注释、函数不超 40 行。
2. 「装一下 xxx 依赖」→ 给出的命令应带国内源参数（如 `npm i xxx --registry=https://registry.npmmirror.com`）。
3. 「现在时间是几点」/ 写个定时任务 → 时间处理应显式带东八区，而非裸 `datetime.now()`。

若失败：检查文件是否在 `.cursor/rules/`、扩展名是否为 `.mdc`、`alwaysApply` 是否符合预期；在 Agent 侧边栏能看到当前激活的规则列表。

## 七、小结

| 要点 | 做法 |
|------|------|
| 为什么写 | 把口头约定固化成持久、可版本化、自动注入的指令，省心且防错 |
| 两个层级 | User Rules 管个人偏好；Project Rules（`.cursor/rules/*.mdc`）管仓库约定 |
| 四种类型 | Always / Auto Attached / Agent Requested / Manual，按 frontmatter 组合选择 |
| 关键坑 | 扩展名要 `.mdc` 不是 `.md`；Always 别超 ~500 行，能 Auto Attached 就不 Always |
| 编写原则 | 一条一关切、短而可执行、给具体例子、可迭代 |
| 实战样例 | 见第五节全中文编码规范 Rule，可直接当 Project Rule 或 User Rules 用 |

Rule 不是一次性的提示词，而是你和 AI 之间的"长期契约"。花一小时写清楚，之后每次对话、每个文件、每台机器都自动遵守——这才是让 Cursor 从"会聊天的编辑器"变成"信得过的结对工程师"的关键一步。
