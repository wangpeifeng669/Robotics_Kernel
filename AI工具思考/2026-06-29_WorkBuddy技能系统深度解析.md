# WorkBuddy技能系统深度解析

## 核心摘要

WorkBuddy 技能（Skill）是注入给 AI 的领域专业知识说明书，本质是一个 SKILL.md 文件，不增加新工具但让 AI 在特定领域更专业。技能可以写成固定流程型，但最佳实践是给"约束区间"而非"精确指令"。触发条件由 Skill 开发者写在 description 字段中，匹配判断由小龙虾执行，匹配成功则强制加载，开发者无法绕过此机制。

---

## 一、问题背景

在日常使用 WorkBuddy 的过程中，"技能"（Skills）、"插件"（Plugins）、"自动化"（Automations）三个概念经常被混淆。核心疑问集中在：

1. 技能到底是什么？开发一个技能是否等于写一套固定的 AI 执行流程？
2. 这与开发 Agent 是否类似？
3. 技能能否控制为固定操作流程？
4. 技能的触发是由开发者控制还是小龙虾自主决定？

本文以实际对话探索为主线，系统梳理这四个问题。

---

## 二、技能的本质定义

### 2.1 一句话定义

**技能 = 给 AI 注入领域专业知识的说明书。**

它是一个叫 `SKILL.md` 的文件，不是可执行代码，不是独立程序，更不是一个独立运行的 Agent。文件内容包含：

| 内容类型 | 说明 |
|---------|------|
| 领域背景知识 | 该领域的基本概念、术语、常见场景 |
| 标准操作流程（SOP） | 处理该类任务的推荐步骤和方法 |
| 常见坑和注意事项 | 容易犯错的地方、边界条件 |
| 推荐工具和方法 | 该用什么库、什么 API、什么范式 |

### 2.2 类比理解

| 类比对象 | 对应关系 |
|---------|---------|
| Python `import pandas` | 导入后获得数据处理能力，不增加新程序 |
| 专科医生 vs 全科医生 | 技能让 AI 从"通用"变"专科" |

安装了 PPT 生成技能后，AI 不会多出一个程序，而是多了一脑子"PPT 领域专业知识"——用什么库、图片怎么处理、排版规则是什么。

## 三、技能、插件、自动化的关系

三者的分工可以用一张三层架构来描述：

```
用户请求
    │
    ▼
┌─────────────────────────────────────────────┐
│          AI 助手（小龙虾 / Agent）             │
│                                             │
│  + 技能（Skills）                             │  ← 知识层面：让 AI 更专业
│    = 领域知识 + 操作规范注入                    │
│                                             │
│  + 插件（Plugins / MCP）                      │  ← 能力层面：给 AI 新工具
│    = 调用外部工具 / 执行真实操作                │
│                                             │
└─────────────────────────────────────────────┘
    │
    ▼
自动化（Automations）= 上面这一切的定时触发器
```

**三者分工表：**

| 维度 | 技能（Skills） | 插件（Plugins） | 自动化（Automations） |
|------|--------------|----------------|---------------------|
| 本质 | 领域知识说明书 | 外部能力接口 | 定时调度器 |
| 增强层面 | 知识层面 | 能力层面 | 时间层面 |
| 回答的问题 | "怎么做更专业？" | "能做哪些事？" | "什么时候做？" |
| 类比 | `import pandas` | Arduino 外接模块 | 定时中断 |
| 触发方式 | 自动匹配或手动指定 | 自动调用 | 定时触发 |

**技能不增加新工具，但让 AI 在特定领域更聪明、更专业、更不容易犯错。**
插件让 AI 能访问外部数据、调用外部工具、执行真实操作。

## 四、技能能否做成固定控制流程

### 4.1 直接结论：可以

你可以在 SKILL.md 中写死步骤序列，AI 会按顺序执行。例如：

```markdown
## 执行流程（严格按顺序）

### 步骤1：扫描文件
用 Glob 搜索 `D:/project/*.md`，取最近7天修改的文件列表。

### 步骤2：提取摘要
对每个文件读前50行，提取 frontmatter 的 topic 字段。

### 步骤3：填入模板
将信息填入固定模板，**一个字不能改**。

### 步骤4：保存输出
保存到指定路径。

### 步骤5：自检
逐项确认步骤1-4已完成，缺一步回到那步重做。
```

### 4.2 关键区别：AI 理解后的"固定" vs 硬编码的"固定"

| 实现方式 | 执行机制 | 严格度 | 容错能力 |
|---------|---------|--------|---------|
| Shell 脚本 | 逐行执行，出错就停 | 100% 固定 | 零 |
| Skill 流程 | AI 理解指令后自主执行 | ~90% 固定 | 遇到意外会自己绕 |
| 纯自然语言 | AI 自由规划 | 不可控 | 最高 |

Skill 流程是**经由 AI 理解后的"固定"**——它读懂了流程并尽力照做，但遇到文件不存在或 API 返回格式变化时，会自己想办法绕过去，而不是直接崩溃。**这就是 Skill 流程相比脚本的优势：保持流程一致性的同时能够容错。**

### 4.3 最佳实践：约束区间而非精确指令

**不好的写法（太死）：**
```markdown
步骤2：用 Glob 搜索 *.md，取第3个文件的第17行
```
文件位置一变就全乱，零容错。

**更好的写法（给约束区间，留判断空间）：**
```markdown
步骤2：搜索 docs/ 下所有 .md 文件，按修改时间倒序，
取最近 10 篇。如果不足 10 篇，取全部并告知用户。
```

| 写法 | 核心差异 | 后果 |
|------|---------|------|
| "取第3个文件的第17行" | 精确指令，零灵活度 | 位置变了直接失败 |
| "取最近10篇，不够就全取" | 约束区间，留判断空间 | 环境变化也能产出结果 |

### 4.4 什么时候该用流程型 Skill

**该用的场景：**
- 操作步骤有明确依赖顺序（部署 → 配置 → 验证）
- 输出格式需要严格一致（周报、测试报告）
- 多步骤中容易遗漏关键节点
- 需要多个工具协作但顺序固定的任务

**不该用的场景：**
- 只需一个命令就能完成 → 直接用 Bash
- 对实时性要求苛刻、不能有任何延迟 → 写脚本
- 逻辑分支极多、每步依赖上一步精确返回值 → 写程序

## 五、技能触发机制

### 5.1 触发流程

```
Skill 文件 frontmatter
  description: "当用户提到'部署 ASR'、'ASR 端侧'、'RK3588 语音识别'时触发。"
  ← 开发者写死的触发条件

用户输入："帮我在 RK3588 上跑 Qwen3-ASR"

小龙虾判断：这句话匹配 "ASR 端侧" + "RK3588"
  → 匹配成功 → **必须**加载这个 Skill

关键：小龙虾的"判断"只是模式匹配，没有"可加载可不加载"的自由。
系统规则写死：匹配就必须加载。
```

### 5.2 三方权力边界

| 角色 | 能控制的 | 不能控制的 |
|------|---------|-----------|
| Skill 开发者 | `description` 的触发词、匹配范围 | 不能写"永远加载"、不能控制用户不说的场景 |
| 用户 | 用"用 xxx 技能"强制指定 | 不能阻止系统自动匹配 |
| 小龙虾 | 做匹配判断（是否命中 description） | 命中后不能拒绝加载 |

**核心约束：** 开发者无法写 `description: "不管用户说什么都加载此技能"`。系统只把 description 当关键词池做文本匹配，不是"开发者声明了就执行"。Skill 开发者真正能控制的只有一件事——description 写得够不够精准和全面。

## 六、技能具体实例

### 6.1 已安装的 aihot Skill（知识型）

本地路径：`C:\Users\wangp\.workbuddy\skills\aihot\SKILL.md`

核心内容：
- API 路由规则：默认走精选（`mode=selected`），只有用户明确说"日报"才走 `daily`
- 5 个分类：模型发布、产品发布、行业动态、论文研究、技巧与观点
- 约束条件：`since` 限 7 天、`take` ≤ 100、限流 600 req/min
- 输出格式：按分类分组 + 全局编号，时间转为人话
- 禁止事项：不暴露 raw 参数、不凭训练数据脑补

这是典型的**知识型技能**——注入 API 使用规范，让 AI 查询和输出更专业。

### 6.2 假设的 ASR 部署 Skill（知识+流程混合型）

内容包含设备选型对比表、部署 5 步骤、常见踩坑清单（量化格式不匹配、VAD 参数调优、采样率统一等）。AI 加载后能自动规划部署步骤并避开已知陷阱。

### 6.3 假设的 TTS 压测 Skill（流程型）

内容包含五阶段递进压测方案（1→5→20→50→100 并发）、指标采集规范、输出报表模板。AI 加载后按固定顺序执行，但遇到错误时会暂停分析而非硬冲。

## 七、技能与 Agent 的关系总结

| 概念 | 定位 | 关系 |
|------|------|------|
| Agent（小龙虾） | 完整的执行者：理解意图 → 规划 → 执行 → 交付 | 整体 |
| Skill（技能） | 挂在 Agent 上的专业领域知识包 | Agent 的组成部分 |
| Plugin（插件） | 挂在 Agent 上的外部能力接口 | Agent 的组成部分 |

**开发技能不是开发 Agent**，而是增强 Agent 在特定领域的专业性。一个 Agent 不装任何技能也能干活，但装了 pptx 技能后做 PPT 就从"勉强能看"变成"专业水准"。

---

## 八、核心结论

1. **技能的本质是知识说明书**，不是可执行程序，不是固定脚本，也不是独立 Agent。
2. **技能可以做成固定控制流程**，但最佳实践是给"约束区间"而非"精确指令"，利用 AI 的理解力做容错。
3. **触发条件由开发者写死**（description 字段），小龙虾做模式匹配判断，匹配成功后强制加载，没有自由裁量空间。
4. **技能、插件、自动化**三者分工清晰——知识增强、能力扩展、定时调度——可叠加使用形成完整自动化工作流。
