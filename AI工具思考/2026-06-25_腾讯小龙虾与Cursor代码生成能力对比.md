# 腾讯小龙虾与Cursor代码生成能力对比

## 核心摘要

同一个代码任务——为 Qwen3-TTS API 生成 100 条测试文本文件（含流式与整段两种模式），交给 Cursor 和腾讯小龙虾分别完成。Cursor 仅消耗约 1% 的 auto 额度即交付可用代码；腾讯小龙虾花费 500 积分、多轮迭代后仍未达到满意结果，且输出代码质量差距显著。本文记录这次对比的完整过程与核心结论。

---

## 一、任务背景

### 1.1 任务目标

对 Qwen3-TTS API 进行批量测试，需要生成 100 条不同的文本，每条写入独立文件。具体要求：

- **文本量控制**：每条文本尽量短，减少 TTS 合成的等待时间
- **两种模式覆盖**：部分文件用于流式（streaming）调用测试，部分用于整段（non-streaming）调用测试
- **独立性**：100 条文本各自独立存为 `.txt` 文件，便于逐条调用和结果比对

### 1.2 为什么选这个任务做对比

这个任务看似简单——本质就是"生成 100 个短文本文件"——但它同时考察几个维度：

| 考察维度 | 具体点 |
|---------|--------|
| 理解能力 | 能否准确理解"流式"和"整段"两种调用场景对文本的不同要求 |
| 代码结构 | 100 个文件的生成逻辑是否清晰、可复用、可扩展 |
| 资源效率 | 完成任务消耗的 token / 积分 / 额度 |
| 代码质量 | 变量命名、异常处理、文件组织是否工程级可用 |

任务难度不高，但足以暴露工具在代码生成方面的真实水平差异。

## 二、腾讯小龙虾的执行过程

### 2.1 任务链接

[查看小龙虾完整任务记录](https://codebuddy.work/agents/tasks/share/DyHjkzztnj?platform=workbuddy)

### 2.2 执行情况

向腾讯小龙虾下达任务指令后，经历了多轮对话迭代：

1. **首轮生成**：小龙虾理解了"生成 100 条文本文件"的基本需求，但对"流式"和"整段"两种模式的区分不够准确，生成的文本内容重复度高，缺少真正的差异化
2. **多轮修正**：反复调整文本生成的多样性策略、文件命名规范、流式/整段的标注方式，每轮修正都消耗积分
3. **最终结果**：经过多轮迭代，累计消耗 500 积分，代码仍存在以下问题——
   - 文本内容多样性不足，部分文件内容雷同
   - 流式与整段的区分逻辑不够清晰，文件组织混乱
   - 代码本身冗长，缺乏工程级的简洁性

### 2.3 核心问题

小龙虾在这个代码任务中暴露了三个系统性短板：

- **对代码任务的理解深度不足**：将"流式 TTS 测试"简单理解为"分句"，没有理解流式调用在 API 层面是 chunk-by-chunk 返回音频，文本本身不需要特殊处理，而是调用方式不同
- **迭代效率低**：每轮修正都需要大量上下文重新理解任务，积分消耗快但进展慢
- **代码质量偏弱**：生成的 Python 脚本冗余度高，变量命名随意，缺少类型注解和异常处理，不像工程代码，更像教学示例

## 三、Cursor 的执行过程

### 3.1 执行情况

同样的任务交给 Cursor（auto 模式），一次 Composer 会话即完成：

- **理解准确**：正确区分了"流式调用测试"和"整段调用测试"是 API 调用方式的差异，而非文本内容的差异。生成的 100 条文本本身是独立的短句，流式/整段的区分通过调用脚本的参数控制
- **代码简洁**：生成一个结构清晰的 Python 脚本，包含文本生成、文件写入、批量调用三个模块，总代码量约 80 行
- **资源消耗**：仅消耗约 1% 的 auto 额度，单次会话完成，无需多轮修正

### 3.2 代码质量对比

| 维度 | 腾讯小龙虾 | Cursor |
|------|-----------|--------|
| 代码行数 | 多轮累计生成 200+ 行，含大量冗余 | ~80 行，结构紧凑 |
| 变量命名 | 混杂中英文，命名随意 | 全英文命名，语义清晰 |
| 异常处理 | 基本缺失 | 包含文件写入异常、API 调用超时处理 |
| 可复用性 | 硬编码参数，难以复用 | 参数化设计，可传入不同 TTS API |
| 流式/整段区分 | 试图在文本层面区分，理解有误 | 在调用层面区分，逻辑正确 |

| 指标 | 腾讯小龙虾 | Cursor |
|------|-----------|--------|
| 完成状态 | 多轮迭代后仍未达标 | 一次会话完成 |
| 资源消耗 | 500 积分 | ~1% auto 额度 |
| 交互轮次 | 5 轮以上 | 1 轮 |
| 人工干预 | 每轮都需要指出问题并调整指令 | 基本无需干预 |
| 最终代码可用性 | 需大量人工修改 | 直接可用 |

**资源效率差距**：以完成同等代码任务计，Cursor 的资源效率约为小龙虾的数十倍。这不是简单的"快一点"，而是量级差异。

## 五、差异根因分析

### 5.1 产品定位不同

腾讯小龙虾（WorkBuddy）的核心能力在于**信息获取与文档生成**——网页抓取、跨源信息聚合、结构化文档产出。在之前的实践中，它在"爬取技术文档→生成部门文档"这类任务上表现出色（详见[《腾讯小龙虾-网页爬取与部门文档生成》](./2026-06-24_腾讯小龙虾-网页爬取与部门文档生成.md)）。

但代码生成不是它的主战场。它缺少 Cursor 那样深度集成的代码上下文管理能力：

- **Cursor** 原生理解项目结构、文件依赖、类型系统，代码生成时自带"工程上下文"
- **小龙虾** 的代码生成更接近"通用 LLM 直接写代码"，缺少对项目工程结构的感知

### 5.2 代码上下文管理的差距

Cursor 的核心壁垒不在底层模型，而在**代码上下文的工程化管理**：

| 能力 | Cursor | 腾讯小龙虾 |
|------|--------|-----------|
| 项目结构感知 | 原生索引整个项目，按需注入相关文件 | 依赖用户手动提供上下文 |
| 代码补全 | 基于光标位置的精准上下文补全 | 不具备 |
| 多文件协调 | Composer 可同时修改多个文件，保持一致性 | 单次生成为主 |
| 增量修改 | 精准 diff 输出，只改必要部分 | 倾向于重新生成整段 |
| 类型检查联动 | 与 LSP 集成，生成时即做类型校验 | 不具备 |

### 5.3 迭代机制的差距

Cursor 的 Composer 会话在同一上下文窗口内持续迭代，模型"记住"之前的修改和反馈，修正精准。

小龙虾的多轮对话中，每轮都需要重新理解完整任务上下文，导致：
- 重复理解成本高（积分消耗快）
- 早期轮次的约束在后期容易被"遗忘"
- 修正方向容易跑偏，越改越乱

## 六、结论与工具选型建议

### 6.1 核心结论

| 工具 | 擅长领域 | 不擅长领域 |
|------|---------|-----------|
| 腾讯小龙虾 | 网页抓取、信息聚合、文档生成、知识检索 | 复杂代码生成、工程级代码迭代 |
| Cursor | 代码生成、跨文件重构、代码补全、工程迭代 | 网页抓取、跨源信息聚合、文档产出 |

**一句话**：小龙虾是"研究助理"，Cursor 是"结对程序员"。用研究助理去写代码，用程序员去爬网页，都会事倍功半。

### 6.2 选型建议

- **写代码、改代码、重构项目** → 用 Cursor，资源效率高、代码质量有保障
- **查资料、爬网页、生成文档、跨源信息汇总** → 用腾讯小龙虾，端到端自动化能力强
- **需要联网搜索 + 少量代码片段** → 两者皆可，但代码复杂度超过 50 行时建议切回 Cursor

### 6.3 积分/额度使用提示

本次对比暴露的一个实际问题是：小龙虾的积分消耗在代码迭代场景下增长极快，5 轮迭代即消耗 500 积分且未达标。如果发现一个任务在小龙虾上迭代 3 轮仍未收敛，建议果断切换到 Cursor，而非继续在小龙虾上"硬磨"——这既是积分成本的考量，也是代码质量保障的考量。

---

## 七、延伸思考

这次对比让一个认知更加清晰：**AI 工具的能力差异不是"通用智商"的差异，而是"专业训练"的差异**。

小龙虾和 Cursor 底层可能调用的是同等量级的语言模型，但 Cursor 在代码场景下做了大量工程化封装——项目索引、上下文精准注入、增量 diff、类型检查联动——这些"脚手架"让同一个模型在代码任务上表现天差地别。

选工具的本质，不是选"最聪明的"，而是选"在最 relevant 的场景下做了最多工程优化的"。在代码这件事上，Cursor 的工程壁垒目前远高于通用 Agent 类工具。
