# 知识库项目是否需要开发为Skill的决策分析

## 核心摘要

WorkBuddy Skill 本质是"给 AI 注入领域专业知识的说明书"，通过渐进式加载替代每次手动引用 README。但对于已具备 README 规范 + 工作记忆自动注入的知识库项目，Skill 的核心价值（自动化触发、渐进式上下文、格式校验）大多已被记忆覆盖。结论：规范简单（5-6 条）、个人使用、无跨项目复用需求时，不需要做 Skill；当规范复杂到记忆摘要丢失细节、需确定性校验脚本、或团队多人协作时，才值得投入。

---

## 一、问题背景

Robotics_Kernel 是一个个人技术知识库，根目录 README.md 定义了完整的文章生成规范——文件命名规则、frontmatter 字段、正文结构要求、六条写作原则。日常使用 WorkBuddy 时，工作记忆（`.workbuddy/memory/MEMORY.md`）已将规范要点自动注入每次会话上下文。

核心疑问：既然记忆已经覆盖了规范，是否有必要把这套规范额外封装成 WorkBuddy Skill？

---

## 二、Skill 能做什么

### 2.1 Skill 的本质

Skill 是一个以 `SKILL.md` 为核心的知识包，将领域专业知识注入给 AI。结构如下：

| 组件 | 作用 |
|------|------|
| `SKILL.md` | 核心指令文件，定义触发条件与执行流程 |
| `references/` | 按需加载的参考文档 |
| `scripts/` | 可执行脚本（如格式校验） |
| `assets/` | 输出模板 |

关键设计是**渐进式加载**：Skill 描述（约 100 字）始终在上下文中，匹配触发条件后加载完整规范，具体参考文档按需展开。避免一次性占满上下文窗口。

### 2.2 Skill 与记忆的职能对比

| 维度 | 工作记忆 | Skill |
|------|---------|-------|
| 注入时机 | 每次会话自动注入 | 匹配触发条件后注入 |
| 内容粒度 | 摘要式（要点列表） | 完整流程 + 脚本 + 模板 |
| 可执行性 | 信息性（告诉 AI 规则） | 行动性（包含校验脚本、输出模板） |
| 上下文效率 | 全量注入，占固定 token | 渐进式，按需展开 |
| 跨项目复用 | 仅限当前项目 | User Skill 可跨所有项目 |
| 确定性 | AI 理解后自主执行，可能遗漏 | 流程化指令 + 脚本校验，遗漏率低 |

## 三、三种典型使用场景不受 Skill 限制

有人担心做成 Skill 后会限制灵活性。实际上 Skill 管的是"怎么写"（格式规范、写作流程），不限制"写什么"（内容来源）。

### 场景一：参考已有 MD 文章

```
用户指令："参考 端侧部署/2026-07-04_qwen3-tts-4090独占部署效果验证.md 的风格，写一篇新的"
```

AI 照常用 Read 工具读取指定文件。Skill 只在读完之后接管格式组织——frontmatter 怎么写、摘要怎么放、文件名怎么命名。内容来源完全由用户指令决定。

### 场景二：直接指定领域写文章

```
用户指令："写一篇关于 RK3588 蓝牙音频架构的文章"
```

这是 Skill 的标准触发场景。Skill 被激活后加载写作规范，AI 按规范组织文章。领域内容由用户指令决定，Skill 不限制主题范围。

### 场景三：参考网上 HTTP 链接

```
用户指令："参考这个链接的内容 https://xxx.com/article，整理成知识库文章"
```

AI 照常用 WebFetch 抓取 URL，读完后按 Skill 定义的规范组织输出。Skill 不拦截任何工具调用。

**本质区别**：Skill 是写作规范的自动执行器，不是内容过滤器。它替代的是"请先读取 README，按照规范..."这段重复指令，而非替代每次写作时的具体意图。

## 四、决策分析：这个项目要不要做 Skill

### 4.1 Skill 额外能力对这个项目的实际价值

| Skill 额外能力 | 对本项目的实际价值 | 判断依据 |
|---|---|---|
| 校验脚本（自动检查 frontmatter 格式） | 低 | 规范就 5-6 条，看一眼就能发现格式问题 |
| 渐进式上下文加载 | 低 | 规范不长，记忆注入占不了多少 token |
| 精确执行步骤 | 低 | 记忆里的要点已够 AI 执行 |
| 跨项目复用 | 不需要 | 这是单一项目的规范 |
| 分享给他人 | 不需要 | 个人知识库 |

### 4.2 什么情况下值得做 Skill

以下条件满足**两条以上**时，Skill 的投入产出比才转正：

- 规范复杂到记忆摘要会丢失关键细节（如超过 15 条规则、多层级嵌套约束）
- 需要带脚本做确定性校验（如 frontmatter 字段完整性、摘要字数统计、文件名正则匹配）
- 团队多人共用同一套规范（需要统一入口、版本化管理）
- 工作流程跨多个工具和多步骤（不只是写一个 MD 文件）
- 需要跨项目复用同一套写作规范

本项目当前只满足零条。README 规范 5-6 条核心要点，工作记忆已经完整覆盖，个人使用，单项目，写一个 MD 文件就完事。

### 4.3 结论

**当前阶段不需要做 Skill。** 现有方案——README 定义规范 + 工作记忆自动注入——已是这套场景的最优解。

如果以后知识库规范变复杂（如增加多语言版本、多人协作、自动发布流程），再考虑做也不迟。技术决策的节奏感比工具本身更重要——不过度工程化，不为了"用 Skill"而做 Skill。

## 五、方法论沉淀：如何判断"要不要做 Skill"

这次决策过程可以提炼为一个通用判断框架，适用于任何"已有某种规范注入机制，是否升级为 Skill"的场景：

| 步骤 | 问什么 | 判断标准 |
|------|--------|---------|
| 1 | 现有机制是否已覆盖核心规范？ | 记忆/README 能否让 AI 在 90% 场景下正确执行 |
| 2 | Skill 额外能力是否解决真实痛点？ | 校验脚本、渐进加载等是否有实际用武之地 |
| 3 | 投入产出是否合理？ | 做 Skill 的时间成本 vs 每次省下的重复指令成本 |
| 4 | 未来复杂度趋势如何？ | 规范是否会显著增长、是否有多人/多项目需求 |

核心原则：**Skill 解决的是"重复且复杂"的流程问题，不是"重复但简单"的规范问题。** 后者用记忆就够了。
