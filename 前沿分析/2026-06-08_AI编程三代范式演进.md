AI编程正经历从"工具"到"系统"的范式跃迁。第一代Tab Coding（自动补全）仅解决打字效率，第二代Vibe Coding（对话式）释放了生成力但缺乏工程纪律，第三代Spec Coding（规约驱动）以结构化Spec为中间产物，实现了可复现、可审计、可积累的软件工厂模式。核心洞察：AI产出的质量上限由规约质量决定，约束才是生产力。

## 三代演进全景

### 第一代：Tab Coding — AI当自动补全

2021年6月GitHub Copilot发布，标志着AI编程进入实用阶段。开发者写前半句，AI补后半句，人和AI的关系是"程序员+打字员"。

**技术特征**：信息输入仅限当前文件上下文+光标位置，输出为单行/多行代码补全。代表产品包括GitHub Copilot、Codeium、Tabnine。

**结构性局限**：AI"只见树木，不见森林"——它看不到项目整体架构、设计模式和模块依赖。补全的代码在局部可能正确，但放在全局可能违反既定约定或引入不一致。

**价值定位**：零学习成本，不改变编码习惯，是AI编程的"最低可用形态"。对于重复性模式代码（如CRUD、样板初始化），效率提升显著；但对于需要架构理解的复杂逻辑，帮助有限。

### 第二代：Vibe Coding — AI当结对程序员

2024-2025年间，Cursor Composer、Claude Code Chat、Windsurf等产品出现，Karpathy在2025年初正式提出"Vibe Coding"概念——人提需求，AI编码，人=甲方，AI=乙方。

**技术特征**：信息输入为自然语言对话+上下文文件，输出为完整代码块/文件/项目。AI从"补全者"升级为"执行者"。

**结构性缺陷**：

| 问题 | 表现 |
|------|------|
| 对话失忆 | 第二次修改可能忘记第一次的约定，上下文窗口内信息被覆盖或稀释 |
| 架构腐烂 | 多次即兴修改后，代码风格和架构设计逐渐不一致 |
| 不可复现 | 中间产物是对话记录，换模型/换人无法复现同等质量的输出 |
| 不可审计 | 无法追溯"为什么这样写"的决策依据 |

Karpathy的比喻精准："即兴发挥可以写出精彩的独奏，但写不出交响乐。"Vibe Coding的本质是即兴编程——每次对话都是一次新的即兴演奏，没有乐谱。

### 第三代：Spec Coding — AI当执行团队

2025年末至2026年，Spec Coding范式确立。人写规约（Spec），AI按规约执行，人=架构师，AI=工程团队。

**核心区别**：Vibe Coding的中间产物是自然语言对话（不可复现、不可审计），Spec Coding的中间产物是结构化规格文档（可复现、可审计、可积累）。这一转变使AI编程从"即兴创作"进入"工程化生产"。

**技术特征**：

- **超长上下文与项目级理解**：AI能吞下整个Repository，理解模块间依赖，避免"改了A导致B塌掉"
- **工具调用闭环**：Agent自主运行Terminal命令、查看编译报错、阅读日志、自动反思迭代
- **多Agent异步协同**：同时启动多个Agent分别处理前端UI、后端接口、自动化测试，人类转为"技术主管"角色

**代表实践**：Garry Tan（YC CEO）开源的GStack框架（48小时破万星，两个月9.5万星），Anthropic内部2026年初超过一半的代码生成基于Spec文件。

## 三代范式核心对比

| 维度 | Tab Coding | Vibe Coding | Spec Coding |
|------|-----------|------------|------------|
| 人与AI关系 | 程序员+打字员 | 甲方+乙方 | 架构师+工程团队 |
| 中间产物 | 无 | 对话记录 | 结构化Spec |
| 可复现性 | 高 | 低 | 高 |
| 可审计性 | 低 | 低 | 高 |
| 规模上限 | 单文件/函数 | 中小项目 | 大型项目 |
| 学习成本 | 零 | 低 | 中 |
| 对开发者要求 | 编码能力 | 提问能力 | 架构与规约能力 |

## 行业验证：数据说话

这些不是概念推演，而是已被验证的事实：

| 主体 | 实验/实践 | 结果 |
|------|----------|------|
| Garry Tan（YC CEO） | 全职运营YC同时用Spec驱动开发 | 3个生产级服务、40+功能，代码产出速度是2013年手写时代的810倍 |
| Vercel | 删掉AI Agent 80%的可用工具 | 响应更快、token消耗更少、成功率更高——约束才是生产力 |
| LangChain | 不换模型，只改Harness设计 | Terminal Bench 2.0从52.8%→66.5%（第30名→前5） |
| Cursor（Anysphere） | 团队内部Spec-driven开发 | Bug率降低约60% |
| YC近两期孵化公司 | MVP开发方式 | 超过40%的团队先写Spec再让AI生成主要代码 |

**关键发现**：Vercel和LangChain的实验证明，提升AI编程效果的最大杠杆不是换更强的模型，而是优化约束设计。这与传统软件工程中"需求质量决定软件质量"的经验完全一致。

## Spec的核心结构

一份有效的Spec包含三个层次：

1. **功能清单**（What）——做什么？明确功能边界和优先级
2. **技术方向与约束**（How）——怎么做？指定框架、规范、禁忌
3. **验收标准**（Done）——怎么算做完？定义可量化的完成条件

GStack的ETHOS.md进一步定义了三条原则：

- **角色即约束**：每个Spec对应一个明确的Agent角色和职责边界，AI不是越自由越强大
- **把湖烧开**：既然AI做完整方案的成本几乎为零，就没有理由交半成品
- **造之前先搜**：写Spec前先让AI搜索现有方案，避免重复造轮子

## 延伸思考

### 1. Spec Coding是对软件工程常识的回归

Spec Coding的核心理念——"先定义清楚要什么，再动手做"——并不是新发明。传统软件工程中，需求工程（Requirements Engineering）一直被认为是最关键也最困难的环节，需求缺陷是软件项目失败的首要原因。AI编程让这个老问题以新的形式重新浮现：当编码成本趋近于零时，定义"做什么"的能力就成了唯一的稀缺资源。

这与Fred Brooks在《没有银弹》中的论断形成有趣的呼应：软件的本质复杂性（Essential Complexity）在于概念结构的规约，而非性能上的偶然复杂性（Accidental Complexity）。AI编程消除了大量偶然复杂性（手写代码、调试语法），但本质复杂性——理解业务、定义架构、做出权衡——仍然是人类不可推卸的责任。

### 2. "AI屎山"风险：规约质量决定代码质量

第三代AI编程的最大隐患不是"AI不够聪明"，而是"规约不够严谨"。当Agent在错误的架构方向上长时间独立编码，会以极高的效率堆砌出更难维护的代码。Vibe Coding下，这个问题被自然限制在对话窗口的范围内；Spec Coding下，一个有缺陷的Spec可能触发Agent生成一整个方向的错误代码。

这意味着：第三代编程对开发者的架构能力和Code Review能力要求不是降低了，而是升高了。你从"写代码的人"变成了"审代码的人"，审查的量更大、速度更快，且必须有能力在架构层面发现系统性偏差。

### 3. 工程直觉的代际断层

如果新一代开发者从一开始就完全依赖Spec→AI→验收的工作流，可能缺乏底层Debug、内存管理、性能优化的直觉。这种直觉不是知识，而是通过大量编码实践内化的判断力。

但这个问题并非无解。类比计算器没有消灭数学直觉——反而让数学家从繁琐计算中解放，专注于证明和建模。关键在于：开发者是否主动用省下来的时间去深入理解系统原理，而非仅仅追求更快地产出功能。

### 4. 对端侧部署场景的特殊意义

在机器人端侧部署场景下，Spec Coding的价值尤为突出。硬件约束（内存、算力、功耗）是不可协商的边界条件，Spec必须精确描述这些约束——"模型内存占用不超过7GB""推理延迟TTFT不超过600ms""NPU利用率不低于80%"。这类量化约束恰好是Spec最擅长表达的，而Vibe Coding的模糊对话很容易在约束边界上失控。

实际上，我在使用Cursor进行端侧部署开发时，已经不自觉地走向了Spec Coding：先整理需求和环境约束到文件中，再让AI按约束生成代码，而非在对话中即兴修改。只是当时没有用"Spec Coding"这个框架来命名这种工作方式。

## 判断信号：你是否该转向Spec Coding

三个自检问题：

1. Vibe Coding项目是否超过3个文件就开始失控？
2. 是否经常对AI重复说同一件事——因为它在对话中"失忆"？
3. 是否希望AI编程工作流可复现——同一需求换模型也能产出同等质量的代码？

任何一条回答"是"，就值得尝试Spec Coding。
