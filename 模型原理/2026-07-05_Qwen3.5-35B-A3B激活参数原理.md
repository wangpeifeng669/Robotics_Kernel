# Qwen3.5-35B-A3B激活参数原理

## 核心摘要

Qwen3.5-35B-A3B 采用 MoE（混合专家）架构：总参数量 35B 指模型全部专家参数之和，需完整载入显存；激活参数量 A3B（3B）指每个 Token 推理时实际参与计算的参数量，仅为总量的约 1/12。MoE 的稀疏激活发生在每一层内部的 FFN 专家横向筛选，而非跨层的纵向跳过——注意力机制仍是全量计算。工程上体现为：用 3B 级别的算力成本获得接近 35B 级别模型的能力，适合低延迟端侧交互场景。

---

## 一、问题背景

在端侧部署 Qwen 系列模型时，常看到类似 `Qwen3.5-35B-A3B`、`Qwen3-30B-A3B` 这样的命名。其中的 `A3B`（Activation 3B）令人困惑：

- 35B 参数需要载入显存，那 3B 是什么意思？
- 是不是推理时只跑其中一部分层，其他层"跳过"？
- 激活参数少，是否意味着能力也打折扣？

要回答这些问题，需要理解 MoE 架构与 Dense 模型的本质区别，以及 Transformer 层内到底哪部分被稀疏化、哪部分仍全量计算。

---

## 二、命名拆解：35B-A3B 到底是什么意思

### 2.1 三段式命名规则

| 字段 | 含义 | 示例值 |
|------|------|--------|
| 系列版本 | 模型家族与迭代版本 | `Qwen3.5` |
| 总参数量 | 硬盘/显存占用的全部参数 | `35B`（约 350 亿） |
| 激活参数量 | 每个 Token 推理时实际参与计算的参数 | `A3B`（约 30 亿） |

**总参数量（Total Parameters）**：模型的"静态容量"，包含所有专家网络参数的总和。35B 参数若以 BF16 精度存储，占用约 70GB 显存。

**激活参数量（Active Parameters）**：推理时真正"转动"的参数。处理每个 Token 时，只有约 3B 参数参与矩阵运算，其余参数处于"静止"状态。

### 2.2 Dense vs MoE 的本质差异

| 维度 | Dense 模型（如 Llama3-8B） | MoE 模型（如 Qwen3.5-35B-A3B） |
|------|--------------------------|-------------------------------|
| 总参数 = 激活参数 | 是，每次全部计算 | 否，激活量远小于总量 |
| 算力成本 | 与总参数成正比 | 与激活参数成正比 |
| 能力上限 | 受总参数约束 | 接近总参数对应的 Dense 模型 |
| 推理速度 | 慢（参数量即计算量） | 快（只算激活部分） |

> **一句话总结**：MoE 用"大容量知识库 + 小算力激活"的错位设计，实现用 3B 级别的推理成本，获得接近 35B 级别模型的能力。

## 三、MoE 架构底层：激活参数如何在层内实现

### 3.1 关键纠正：筛选发生在"层内横向"，而非"跨层纵向"

一个常见误解是：激活参数少，是不是推理时跳过某些层？

**答案是否定的。** Transformer 的层与层之间是强耦合的：

- 第 N 层的输入必须是第 N-1 层的输出
- 跳过任意层会导致特征空间"断层"，输出无意义

MoE 的稀疏激活发生在**每一层内部**，具体地说，是每一层中的 **FFN（前馈网络）被替换为多个并行专家**，由路由算法横向筛选。

### 3.2 单层内部结构对比

**Dense 模型单层流程：**

```
输入 → LayerNorm → Self-Attention（全量） → 残差连接 → LayerNorm → FFN（全量） → 残差连接 → 输出
```

**MoE 模型单层流程：**

```
输入 → LayerNorm → Self-Attention（全量） → 残差连接 → LayerNorm
                                                 ↓
                                         Router（路由网络）
                                                 ↓
                              选出 Top-K 个专家（如 2/16 个）
                                                 ↓
                              被选中专家的 FFN 计算结果加权求和
                                                 ↓
                                      残差连接 → 输出
```

关键观察：

1. **Self-Attention 仍是 Dense 的**：每一层的注意力机制对所有 Token 全量计算，参数不参与稀疏激活。
2. **只有 FFN 被 MoE 化**：原先的一个大 FFN 被拆成 N 个"专家 FFN"，每次只激活其中 K 个（通常 K=2）。
3. **每一层独立路由**：每层有自己的 Router，根据当前 Token 的语义决定激活哪些专家。

### 3.3 Router 路由机制

Router 是一个轻量的线性分类器，工作流程：

1. 接收当前 Token 在该层的隐藏状态向量 `h`（维度如 4096）
2. 通过线性投影得到每个专家的"匹配得分"
3. 取 Top-K 得分最高的专家（如 Top-2）
4. 以 Softmax 归一化后的得分为权重，对选中专家的输出加权求和

```
Router(h) = Softmax(W_routing × h)   # W_routing 形状：[num_experts, hidden_dim]
选中专家 = TopK(Router(h))
输出 = Σ (权重_i × Expert_i(h))        # 仅对选中的 K 个专家计算
```

## 四、数学账本：35B 和 A3B 是怎么算出来的

以 Qwen3.5-35B-A3B 的典型配置为例，做一个粗略的参数核算。

### 4.1 参数分布

| 组件 | 是否稀疏 | 参数量估算 | 说明 |
|------|---------|-----------|------|
| Embedding 层 | 全量 | ~1B | 词表映射，始终参与 |
| 每层 Self-Attention | 全量 | ~0.5B/层 | Q/K/V/O 四个矩阵 |
| 每层 MoE-FFN（专家总容量） | 稀疏 | ~1B/层（每专家）/ 16专家 | 每层的专家总参数量 |
| LM Head（输出层） | 全量 | ~1B | 投影到词表 |
| **合计（总参数）** | — | **~35B** | 所有专家参数累加 |

### 4.2 激活参数核算

假设模型共 32 层，每层有 16 个专家，路由 Top-2 激活：

- **固定全量参数**（Embedding + Attention + LM Head）：约 **1.5B**，每层必算
- **激活的专家参数**：每层 16 个专家中只算 2 个，激活比例为 2/16 = 1/8；32 层专家总容量约 32B，激活部分约 **4B**

精细调优后（专家共享、参数复用等工程手段），实际激活量被压缩到约 **3B**，即 `A3B`。

```
激活参数量 = 固定全量参数 + 专家总容量 × (K / N_experts)
          ≈ 1.5B + 32B × (2/16)
          ≈ 1.5B + 4B
          ≈ 5.5B  （理论值，工程优化后压至 ~3B）
```

> **注意**：不同厂商对"激活参数"的统计口径略有差异（是否含 Attention、是否含 Embedding），A3B 是官方给出的推理时实际 FLOPs 对应的参数量级。

## 五、工程视角：部署时的显存与算力测算

### 5.1 显存占用——看总参数 35B

模型必须完整载入显存（除非做 Expert Offloading，但会严重拖慢推理速度）。

| 精度 | 显存占用估算 | 推荐显卡 |
|------|------------|---------|
| BF16/FP16 | 35B × 2Byte ≈ **70GB** | A100/H800 80GB |
| INT8 | 35B × 1Byte ≈ **35GB** | A100 40GB（临界） |
| INT4 | 35B × 0.5Byte ≈ **17.5GB** | RTX 4090 24GB ✅ |

**KV Cache 额外开销**：推理时还需为上下文 Token 存储 K/V 张量，长上下文场景下可能再占 10~30GB，需纳入预算。

### 5.2 计算吞吐——看激活参数 3B

一旦模型载入显存，推理的计算量由激活参数量决定：

- **Prefill 阶段**（处理输入提示）：并行计算，激活参数 3B 意味着每 Token 的计算量相当于一个 3B Dense 模型，Batch 较大时吞吐量优势明显
- **Decode 阶段**（逐 Token 生成）：逐 Token 计算，每次只激活 ~3B 参数，延迟极低

与真正的 35B Dense 模型对比：

| 指标 | 35B Dense | 35B-A3B MoE |
|------|-----------|-------------|
| TTFT（首 Token 延迟） | 高（全量计算） | 低（仅激活 3B） |
| 吞吐量（Token/s） | 低 | 高（约 3~5×） |
| 端侧实时交互适用性 | 差 | **好** |

### 5.3 端侧部署建议

对于 RK3588、PC 端侧等场景：

1. **优先 INT4 量化**：17.5GB 显存需求可压缩至消费级显卡可承受范围
2. **TTS+LLM 分卡隔离**：避免 LLM 推理与 TTS 推理竞争 GPU，确保 TTFT < 100ms
3. **Batch Size 控制**：MoE 模型在大 Batch 下路由冲突加剧，小 Batch（1~4）时延迟最优

## 六、局限性：MoE 不是免费午餐

1. **显存无法节省**：总参数 35B 仍需完整载入，显存需求与同量级 Dense 模型相当
2. **路由不均（Load Balancing）**：训练时部分专家可能被频繁选中，其他专家训练不足，推理时导致算力浪费
3. **端到端延迟不一定线性下降**：路由计算、专家间通信（多卡场景）引入额外开销，实际加速比低于理论值（3B/35B ≈ 1/12）
4. **知识冗余风险**：专家之间的功能可能重叠，35B 总参数中实际有效知识可能低于同量级 Dense 模型

## 七、总结

| 问题 | 答案 |
|------|------|
| 35B-A3B 的 A3B 是什么意思？ | 每个 Token 推理时实际参与计算的参数量约 30 亿 |
| 是不是跳过某些层来减少计算？ | 否，每一层都完整经过，稀疏激活发生在层内的 FFN 专家横向筛选 |
| Attention 机制参与稀疏激活吗？ | 不参与，Self-Attention 仍是全量 Dense 计算 |
| 部署时看哪个参数算显存？ | 看总参数 35B，需完整载入显存 |
| 部署时看哪个参数算算力？ | 看激活参数 A3B，决定推理延迟与吞吐 |
| 适合什么场景？ | 低延迟要求的实时语音/机器人交互，对显存有预算但对延迟敏感的场景 |

**核心结论**：MoE 的本质是"用显存换算力"——付出完整载入 35B 参数的显存成本，换取仅 3B 激活量的低延迟推理。是否选用，取决于显存预算与延迟要求的权衡。
