# Qwen3.8-27B-FP8 首帧实测：为什么 64 个 token 就上一个台阶

**核心摘要**：本文实测 Qwen3.8-27B-FP8 在 4090 上的首帧时间：1~64 token 约 40ms 平坦，第 65 个起每跨 64 抬约 24ms，512 后 0.40ms/token 线性，8191 为 3.30 秒。根因是 48 层为线性注意力，FLA 按 64 分块：块内 padding 同价、块间状态串行，每开一块重跑一遍。

---

## 一、实测背景与口径

**模型**：`Qwen3.8-27B-FP8`（64 层，48 层线性注意力 + 16 层全注意力的混合架构）。

**服务**：本机 vLLM，`http://127.0.0.1:8000/v1`，参数：

| 参数 | 值 | 说明 |
|---|---|---|
| `max_model_len` | 8192 | 上下文总长度 |
| `gpu_memory_utilization` | 0.90 | 显存占用上限 |
| `max_num_seqs` | 192 | 最大并发序列数 |
| 思考模式 | 关闭 | 不产生思考 token |
| 前缀缓存 | 关闭 | 防止短前缀把长请求算短 |

**测量口径**：

- 走 `/v1/completions`，请求体直接传 token id，没有对话模板，`prompt_tokens` 即表中长度；
- `max_tokens = 1`，`temperature = 0`，只看首帧，不统计后续吐字；
- 每档先打 1 次预热、再记 5 次（193 之后记 3 次），预热不进表；
- 边界点（65、129，以及 193 后每隔 64）单独复测，即"64k+1"的位置；
- 测量时间 2026-10-18 21:35–21:39（东八区）。显存 42901–43616 MiB / 49140 MiB，无 OOM。

## 三、首帧时间（TTFT）由什么组成

TTFT（Time To First Token）从请求发出计到第一个文字出现，由五段组成：

```text
① 网络与框架入队   HTTP 解析、请求进 waiting/running 队列（本机回环，很小）
② 输入处理         tokenize（本次直接传 id，跳过）；embedding 查表
③ Prefill 前向     64 层逐层计算（见下），是 TTFT 的主体
④ 出 logits        最后一层 RMSNorm + lm_head
⑤ 采样与回传       temperature=0 时为 argmax；首 token 回传
```

**Prefill 前向的每一层内部**：RMSNorm → 注意力/QKV 投影（FLA 层为线性注意力，16 层为全注意力）→ 输出投影 → 残差 → RMSNorm → FFN 的 gate/up/down 三个投影 → 残差。每层在 GPU 上发射几十个 kernel，所有 kernel 跑完即该层完成。

从成本形态看，TTFT 可以写成三段之和：

```text
TTFT(T) ≈ 固定基线（约 20ms）          ← ①②④⑤＋首块的非 FLA 成本
        ＋ 块数 × 每块成本（约 24ms），块数 = ⌈T/64⌉  ← 48 层线性注意力的分块成本（小 T 主导）
        ＋ 随 T 平滑增长的部分（约 0.40ms/token） ← 全注意力 16 层与 FFN（大 T 主导）
```

注意模型权重在服务启动时就已加载到显存，**首帧不再走 PCIe 搬运权重**；固定基线里也没有"搬运权重"这一项。下面解释每一段为什么是这个数。

---

## 四、框架怎么算：每一层内部按 64 分块

先分清两个嵌套的方向：

- **层**（64 层，纵向堆叠）：第 2 层的输入是第 1 层的输出，**必须第 1 层全部 token 算完，第 2 层才能开始**，层与层严格串行；
- **块**（64 token 一块，序列方向）：分块发生在**每一层内部**——这一层对所有 token 的计算，是一块一块完成的。

执行顺序（先层、后块，以 3 个块为例）：

```text
             块1(1~64)    块2(65~128)   块3(129~192)
第 1 层  →   [算块1] ──→  [算块2] ──→  [算块3]      每块 128 个 SM 同时算，约 0.4ms
               ↓ 等第 1 层全部 token 算完
第 2 层  →   [算块1] ──→  [算块2] ──→  [算块3]
               ↓ 等第 2 层全部算完
   ……
第 64 层 →   [算块1] ──→  [算块2] ──→  [算块3]
```

块一在某一层算完，产出两样东西：

1. **64 个 token 在这一层的输出向量**（每个 token 一个），送进下一层；
2. **一个注意力状态**（前面 token 的信息摘要），交给同层的块二。

随后同层算块二：块二在本层的输入 + 块一的状态 → 块二的输出向量和新状态。一层所有块算完，才轮到下一层。KQV 只是层内的中间值，算完注意力即丢弃，不是"块的结果"。

为什么同层内不能所有块一起算：48 层线性注意力里，后面块的计算依赖前面块的状态（块1→块2→块3）；16 层全注意力更直接——每个 token 要看到全部 token，必须等所有块到达这一层再一起做（相当于屏障）。

最后一块不足 64 也补齐到 64 来算（padding，补空位、不参与结果）。

128 个 SM 的角色：每算一块（约 0.4ms），64 个 token 的计算切成几十个 tile，铺给 128 个 SM 同时完成；块间排队，层间也排队。

注意区分两个数字：**64 是框架的"每块多少 token"（软件分块，换模型可以变）；128 是显卡的"有多少个 SM 车间"（硬件，4090 固定）**。

## 五、台阶的两个规律

### 5.1 规律一：1~64 个 token 同价

因为不足 64 也按 64 补齐，输入 1 个 token 和输入 64 个 token 都是**一块的工作量**，128 个 SM 都要为这 64 个位置跑一遍，所以首帧都是 38~46ms，不随 token 数变化。可以理解为"打一辆车，一个人坐和坐满，车价一样"。

### 5.2 规律二：每多一块，就多约 24ms

每多一块，它在**每一层都要被算一遍**（单层单块约 0.4ms × 64 层），这是一笔固定开销，实测约 **24ms/块**。由于同层内块与块之间要排队、层与层之间也要排队，这笔时间不能被并行掉，台阶高度也就恒定不变。

### 5.3 台阶逐档实测

| 跨过 | 块内末尾 | 下一块第一个 | 抬升 |

| 64 | 0.046 秒 | 0.067 秒 | +21 毫秒 |
| 128 | 0.064 秒 | 0.089 秒 | +25 毫秒 |
| 192 | 0.091 秒 | 0.115 秒 | +24 毫秒 |
| 256 | 0.111 秒 | 0.139 秒 | +27 毫秒 |
| 320 | 0.147 秒 | 0.173 秒 | +26 毫秒 |
| 384 | 0.165 秒 | 0.190 秒 | +26 毫秒 |
| 448 | 0.192 秒 | 0.216 秒 | +24 毫秒 |
| 512 | 0.211 秒 | 0.238 秒 | +27 毫秒 |

### 5.4 公式逐档验证

把"固定基线 20ms ＋ 块数 × 24ms"代入，块数 = ⌈T/64⌉：

| 区间（块数） | 公式预测 | 实测 |
| --- | --- | --- |

## 六、512 之后台阶去哪了：台阶就是那条直线

关键换算：**0.40ms/token × 64 = 25.6ms/块 ≈ 台阶高度 24ms**。台阶没有消失，只是换成了"每 token 多少毫秒"的形式：

- 512→1024：0.37ms/token；1024→2048：0.39；2048→4096：0.40；4096→8191：0.41；
- 512→768：+106ms ÷ 4 块 ≈ 26.5ms/块——每块还是 24ms 左右；
- 只是 512 之后的采样点全部落在 64 的整数倍（768、1024…8191），即永远落在"块内末尾"，没有再测 +1 边界，阶梯在图上就变成了直线。

### 6.1 这块 24ms 里，GPU 用了多少力气

一块 64 个 token 约 3.46×10¹² 次浮点运算，除以 24ms ≈ 144 TFLOPS，只占 4090 稠密 INT8 峰值（660T）的约 **22%**。原因是每块只有 64 个 token，对 128 个 SM 来说是"小活"，车间没铺满；而且块与块之间排队，GPU 有力也不能提前使。这是短 prompt 下的正常利用率，不代表卡有问题。

## 七、几个补充现象

### 7.1 块内并非完全平坦：96 比 128 还慢

96 token 为 0.072 秒，128 token 反而回到 0.063 秒。原因是 96 的第二块只填了 32（padding 一半），kernel 形状不规整；128 正好两块对齐，核更顺。不改变"跨过 64 就抬一档"的规律。

### 7.2 预热与稳态

1 个 token 的首次预热是 0.080 秒，后面五次回到 0.041 秒。其余档位预热与稳态同量级，没有出现首次加载 kernel 的几秒延迟。

### 7.3 全注意力 16 层没有拉成平方增长

全注意力只占 64 层中 16 层（1/4），到 8191 仍没有明显平方拐点。8191 按线性预测 3.28 秒、实测 3.30 秒，差值仅 20ms。

## 八、工程启示

1. **小 T 台阶是软件块长导致的，不是硬件慢**：首帧第一次增加发生在第 65 个 token，本质是"为 1 个 token 付了 64 个 token 的钱"；
2. **压低首帧的方向**：缩短 chunk（减小 padding 浪费，但会增加串行步数）、前缀缓存（公共前缀免重复 prefill）、合并请求减少状态递推次数；
3. **长 prompt 的首帧看 0.40ms/token 这条线**：8191 约 3.3 秒，交互设计上应做流式提示，不能让用户干等；
4. **选卡仍看三件套**：算力（prefill 斜率）、带宽（固定地板）、显存（KV cache 容量，本次显存 43.6GB 未触顶）。

性能核查清单：

- [ ] 是否在 64k+1 边界复测过，确认台阶来自 chunk 数而非网络抖动？
- [ ] 前缀缓存是否关闭/开启，结论口径是否一致？
- [ ] 实测斜率（0.40ms/token）反推的有效算力是否与 MFU 经验区间吻合？
- [ ] 长 prompt 的 chunked prefill 是否会阻塞其他用户的首帧？
- [ ] 全注意力层占比多少，在目标长度内会不会出现平方拐点？
