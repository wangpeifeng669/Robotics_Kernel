# Qwen3-30B-A3B-MoE架构与INT8推理原理

Qwen3-30B-A3B 的本质是一份「显存按 30B 备货、算力按 3B 消耗」的合同：128 个专家全部常驻显存，每个 token 只激活 8 个。单卡 4090 48G 跑不动 BF16 本体（约 61 GB），INT8 权重量化（W8A16）把它压到约 32 GB 才成立。本文拆解 MoE 路由、GQA 注意力、KV Cache 显存公式与 Prefill/Decode 两阶段的硬件行为，并给出 48G 显存的上下文容量账本。

---

## 1. 为什么这个模型值得单独拆一遍

Qwen3-30B-A3B-Instruct-2507 是典型的 MoE（Mixture of Experts）模型，总参数 30.5B，每 token 激活仅约 3.3B。这个「仓库 30B、上岗 3B」的结构决定了它的所有部署特性：

| 项 | 值 | 对推理的含义 |
|---|---|---|
| 总参数 | 30.5B | 显存按这个备货 |
| 每 token 激活 | 约 3.3B | 每个字的算量按这个估 |
| 层数 | 48 | 每个 token 串行过 48 次 |
| 隐层 | 2048 | 残差流的宽度 |
| 注意力 | 32 Q 头 / 4 KV 头，头维 128 | GQA，KV Cache 只有完整 MHA 的 1/8 |
| 专家 | 128 选 8，中间维 768 | 显存全备，计算只派 8 个 |
| 词表 | 151936 | 输出头要打这么多 logits |
| 原生上下文 | 262144 | 能力上限；单卡 48G 用不满 |

一句话总结：**显存看总参数，算力看激活参数**。这是 MoE 与稠密模型在部署决策上的根本分叉——稠密 30B 每个字要把近 30B 权重扫一遍，MoE 每个字只动约 3.3B。

注意官方 ModelScope 仓库本体是 BF16（约 61 GB），INT8 是 GPTQ / AWQ / GGUF Q8 等量化副本，与官方另发的 FP8 版本也不是同一套格式。本文按最常见的「权重量化、计算半精度」（W8A16）路径展开。

## 2. 名词先行：容易混在一起的六样东西

| 说法 | 它实际是什么 | 它不是什么 |
|---|---|---|
| 权重 | 训练好的固定参数，启动后不变 | 用户这句话的内容 |
| 激活 | 当前层算出的中间向量，算完可扔 | 模型「记忆」 |
| KV Cache | 历史 token 的 Key/Value，供后续注意力复用 | 把整段原文再跑一遍 |
| INT8 | 权重 1 字节存，推理时乘 scale 还原 | 参数量变一半 |
| MoE | 128 个专家都在显存，每 token 只算 8 个 | 只用 8 个专家的小模型 |
| Prefill / Decode | 提示词并行算完写 KV / 每次只进 1 个新 token | 两个阶段走同一条硬件路径 |

推理成立，显存里必须同时站住三样东西：

```
常驻：INT8 权重（约 32 GB，128 个专家全在）
增长：KV Cache（对话越长越大）
临时：当前层的激活工作区（算完可覆盖）
```

显存账不是「模型文件多大」，而是这三笔之和。漏算任何一笔，就会出现「明明算过显存够却 OOM」的经典误判。

## 3. MoE：128 个专家都在，只叫醒 8 个

### 3.1 路由机制

每层有一个很小的路由器：`2048 → 128` 打分，取 Top-8，权重归一化（`norm_topk_prob=true`）。每个专家是一个小 SwiGLU（中间维 768）：

```
专家输出 = (silu(xW_gate) ⊙ xW_up) W_down
层输出   = Σ  gate_i × 专家_i(x)
```

硬件分工必须分开看：

- **存储**：128 份专家权重都在 GDDR6X
- **计算**：只把当前向量乘到被选中的 8 份上
- **其余 120 个专家**：躺在显存里，不参与乘加

### 3.2 MoE 的硬约束：专家不能按需从硬盘抽

路由事先不知道每个 token 会选中哪 8 个专家，且每个 token 都可能换专家。如果按需从硬盘加载，生成速度会从几十 token/s 掉成不可用。所以 **128 个专家必须全部常驻显存**——MoE 省的是算力和带宽搬运量，不省显存。

### 3.3 MoE 在 Decode 阶段更划算

Decode 是显存带宽瓶颈（每个字都要把相关权重从 GDDR6X 抽到 SM），MoE 每个新字只搬运约 3.3B 参数对应的权重，INT8 又把每次搬运的字节减半，两个效应叠加，生成速度往往接近翻倍——这才是单卡 INT8 的主收益，而不是「算力变成 INT8 加法」。

## 4. GQA：32 个问题共用 4 把钥匙

Qwen3-30B-A3B 的注意力是 GQA（Grouped Query Attention）：

```
Q: [序列长, 32, 128]     每个 token 提 32 个问题
K: [序列长,  4, 128]     只有 4 份钥匙，8 个 Q 头共用一把
V: [序列长,  4, 128]
```

隐层 2048，Q 被投到 32 × 128 = 4096 维，比残差流更宽；K/V 只有 4 个头。这使 KV Cache 体积变成完整 MHA 的 **1/8**——这是 48G 上还能开较长上下文的关键，不是 INT8 单独省出来的。

位置信息用 RoPE 旋进 Q/K，不另加绝对位置向量。FlashAttention 类内核不会把「序列长 × 序列长」的分值矩阵整张物化，而是分块在片上算完就扔，否则 8K 上下文一张分值图就能打爆工作区。

## 5. INT8 的正确姿势：常驻量化、片上反量化

INT8 W8A16 的核心约定：**显存里保持 INT8（约 32 GB），计算时在片上乘 scale 还原成 FP16/BF16**。

两个关键推论：

1. 若引擎加载后把 INT8 展开成 BF16 常驻，体积回到约 61 GB，48G 立刻 OOM。启动就 OOM 时先查这一点，而不是换模型。
2. 反量化发生在 Tensor Core 侧（读出权重 → × scale → 还原），不是每步都在 CPU 上做。若发现每步 CPU 反量化，速度会显著低于预期。

Decode 阶段 batch=1 时「算得少、搬得多」，INT8 让每次权重搬运字节减半，直接提升生成速度。

## 6. KV Cache 显存公式与 48G 容量账本

### 6.1 公式

按半精度（FP16/BF16，每元素 2 字节）估算：

```
每 token 字节 = 2（K和V） × 层数 × KV头数 × 头维 × 2（半精度）
             = 2 × 48 × 4 × 128 × 2
             = 98304 ≈ 96 KB
```

### 6.2 容量表（INT8 权重约 32G 之后）

| 上下文 | KV Cache | 结论 |
|---|---|---|
| 8K | 0.75 GB | 宽裕，可多并发 |
| 32K | 3.0 GB | 日常对话舒适区 |
| 64K | 6.0 GB | 单路长文通常没问题 |
| 128K | 12 GB | 贴着天花板，并发基本无望 |
| 256K | 24 GB | 权重 32G + KV 24G，会爆 |

结论：**48G + INT8 能稳跑数万到十万级 token，跑不满官方 256K**。官方 256K / 1M 是按多卡或更大显存设计的，单卡把最大长度收到 32K～64K 更稳。

并发是另一笔账：两条对话就是两份 KV。**权重共享，Cache 不共享**——单卡想「又长又多」，会先撞 KV，不是先撞权重。

## 7. Prefill 与 Decode：两段不同的硬件行为

### 7.1 Prefill：算力密集

第一次前向把整段提示词的 N 个 token 并行处理，Tensor Core 利用率高，首字延迟主要看提示词长度。交付两样东西：

1. 整段历史的 KV Cache，供 Decode 复用
2. **最后一个位置**的 logits——中间位置的 logits 对生成无用，可不保留

用户等待的「第一个字之前的空白」几乎都花在这一段。

### 7.2 Decode：带宽瓶颈

之后每个新 token 单独走一遍全网络：只算新 token 的 Q/K/V，新 Q 与 KV Cache 里所有历史 K 做点积，新 K/V 追加进 Cache，MoE 为这个 token 再选 8 个专家，输出头再出 151936 维 logits，采样下一个字，循环直到结束符。

采样常用组合：Temperature=0.7，TopP=0.8，TopK=20。这是 logits 上的 CPU/小核操作，相对 48 层矩阵乘可以忽略。

## 8. 一个 token 在一层里的微循环（Decode、batch=1）

```
显存 GDDR6X                         4090 SM / Tensor Core
───────────                         ────────────────────
INT8 的 W_q, W_k, W_v  ──读出──►   × scale，还原成 FP16
当前 hidden [1,2048]   ──读出──►   GEMM → Q/K/V
历史 KV Cache          ──读出──►   Q·K^T → softmax → ×V
W_o                    ──读出──►   投影回 2048，写回激活

路由器 W_gate          ──读出──►   算出 top-8 专家编号
8 份专家 INT8 权重     ──读出──►   反量化 + 3 个小 GEMM
其余 120 个专家        躺着不动
```

整体数据流一条主线：

```
NVMe 上的 INT8 safetensors
        │  OS 读盘（5～15 秒）
        ▼
   主机 DDR（中转，加载后可释放）
        │  PCIe 4.0 x16 DMA（实际 20～25 GB/s，纯拷贝约 1.5 秒）
        ▼
   4090 48G 显存
   ├─ 31～33G 权重常驻（128 专家全在）
   ├─ KV Cache 按对话增长
   └─ 一层一份激活工作区（1～3 GB）
        │
        ├─ Prefill：N token 并行，Tensor Core 打满，写出整段 KV
        └─ Decode：每次 1 token，带宽瓶颈，复用 KV，MoE 只算 8/128
        ▼
   logits → 采样 → 新 token → 再进模型 → 分词器还原成汉字
```

加载相关的两个坑：系统内存建议 ≥ 64 GB（笨路径 CPU 持有完整张量再拷贝，峰值内存约 2 倍模型体积）；分片读、立刻拷、立刻释放才能压住峰值。盘速只影响启动，不影响每个字的速度。

## 9. 常见误区速查

| 错觉 | 实际 |
|---|---|
| INT8 模型变笨一半 | W8A16 下质量通常接近原版 |
| MoE 很省显存 | 省的是算力，128 专家必须全在 |
| 加载慢就是推理慢 | 加载走硬盘/PCIe 只付一次；推理走显存带宽 |
| 48G 够用就可开满 256K | 权重 32G 后 KV 涨到 24G 会顶满 |
| 引擎会按需从硬盘抽专家 | 每个 token 都可能换专家，按需读盘不可用 |

故障定位：

| 现象 | 先查 | 不要先做 |
|---|---|---|
| 启动直接 OOM | INT8 是否被展开成 BF16 常驻；max 长度是否开到 256K | 换更大模型 |
| 加载时整机卡死 | 系统内存是否 < 64G；是否双份占用 | 怪 GPU |
| 首字慢、之后正常 | Prefill 提示词是否过长 | 降量化位数 |
| 越聊越慢或中途 OOM | KV Cache 是否涨满 | 重装驱动 |
| 速度明显低于预期 | 是否真在 GPU 上跑；是否每步 CPU 反量化 | 先改提示词 |

## 10. 收束

**INT8 把 30B 的仓库塞进 48G；MoE 让每个字只算约 3B；Prefill 一次写出 KV，Decode 每次只追加一个 token。**

权重从硬盘经内存、PCIe 搬进显存后不再回头；每个 token 查表变 2048 维向量，过 48 层「GQA 注意力 + 128 选 8 专家」；48G 的余量要留给 KV，不要留给「把 INT8 再展开成 BF16」。对端侧部署的启示：MoE 模型换算到小显存设备时，「专家全常驻」这条硬约束同样成立，RK3588 这类 8～16G 内存的平台跑 MoE 需要更激进的量化（INT4）加更小的专家规模，架构红利才能兑现。
