# 4090 GPU 硬件架构通俗讲解：128 个 SM 车间如何跑出 1321 TOPS

**核心摘要**：4090 的 1321 TOPS 不是巨型引擎，而是 128 个 SM 车间、每车间 128 个 CUDA Core 与 4 个 Tensor Core 叠成。用工厂类比讲透 GPU 层级、线程 / Warp/Block 映射、GEMM tile 波次与显存接力，解释标称算力为何只跑出几分之一（MFU），并把硬件与 Prefill/Decode 对应。



***

## 一、先立直觉：GPU 为什么需要一万多个核心

深度学习算到最底层，99% 的运算量是矩阵乘法。一个 4096×4096 的矩阵乘法包含约 1.7 亿次乘加，这些运算之间**几乎没有依赖、不需要分支判断、不需要复杂流程控制**—— 谁先算谁后算无所谓，只要最后结果对。

CPU 和 GPU 对这种工作负载给出了两种截然相反的设计：



| 设计取向 | CPU                   | GPU（4090）                             |
| ---- | --------------------- | ------------------------------------- |
| 核心数量 | 十几个复杂大核               | 16384 个 CUDA Core + 512 个 Tensor Core |
| 优化目标 | 单线程延迟（分支预测、乱序执行、多级缓存） | 整体吞吐（海量简单计算并行铺满）                      |
| 类比   | 几十个教授，什么难题都能解         | 一万多个经过分工训练的小学生，同时做口算                  |
| 擅长   | 复杂逻辑、串行依赖、操作系统        | 矩阵乘法、卷积、海量元素并行计算                      |

让一百个教授解同一道 1 亿次的重复乘法题，他们要排队一道一道做；让一万个小学生每人分一万道，眨眼就做完了。GPU 的全部架构设计，都围绕一件事：**如何把海量重复计算切成尽可能小的块，均匀铺给尽可能多的计算单元，并且让它们别饿着（等数据）**。



***

## 二、硬件层级：芯片 → GPC → TPC → SM

4090 用的是 Ada Lovelace 架构的 AD102 芯片。芯片内部不是一万多个核心平铺，而是三级组织：



```
GPU（AD102 芯片，整卡 450W）
└── GPC ×12（Graphics Processing Cluster，图形处理簇）
    └── TPC ×6（Texture Processing Cluster，纹理处理簇）
        └── SM ×2（Streaming Multiprocessor，流式多处理器）
```

满规格 AD102 是 12×6×2 = **144 个 SM**，RTX 4090 产品中启用了 **128 个 SM**（其余 16 个因良率 / 功耗定位被屏蔽）。

**SM 是 GPU 真正的 "计算车间"，是理解一切调度问题的基本单位**：kernel 以 SM 为单位分配、片上存储以 SM 为单位私有、波次以 SM 数量为一波容量。先记住 128 这个数，后面所有调度计算都围绕它。

4090 的关键规格总表：



| 部件          | 规格                  | 说明           |
| ----------- | ------------------- | ------------ |
| SM          | 128 个               | 计算车间总数       |
| CUDA Core   | 16384 个（每 SM 128）   | 通用标量计算       |
| Tensor Core | 512 个（每 SM 4，第四代）   | 矩阵乘专用        |
| Warp 调度器    | 每 SM 4 个            | 以 32 线程为单位派活 |
| L2 缓存       | 72 MB               | 全片共享         |
| 显存          | 24GB GDDR6X，384-bit | 1008 GB/s    |
| 整卡功耗        | 450W                | —            |

## 三、SM 内部解剖：一个计算车间里有什么

把一个 SM 放大，里面有六类部件，各有明确的工厂角色：



```
一个 SM（车间）
├── Warp 调度器 ×4      工头：每周期从就绪班组里挑一个派活
├── Tensor Core ×4      矩阵冲压机：一条指令直接输出一个小矩阵块
├── CUDA Core ×128      通用工人：一人一条标量指令（加减乘除、函数）
├── 寄存器堆 256 KB      工人手边的零件盒：速度最快、容量最小
├── L1 / Shared Memory  车间料架：128KB 片上 SRAM，同车间工人共享
└── Load/Store 单元     搬运工：负责从显存/L2 把数据领进来
```

### 3.1 CUDA Core：通用工人

每个 CUDA Core 一个周期完成一次标量浮点或整数运算（FFMA 等）。128 个工人 / SM × 128 个 SM = 16384 个，它们保证 "任何算子都能算"——Sigmoid、Softmax、LayerNorm 这类没有专用电路的算子，就由它们一条条指令软解。

### 3.2 Tensor Core：矩阵冲压机

Tensor Core 不做标量，它只认一种活：**矩阵乘累加（MMA，Matrix Multiply-Accumulate）**。一条 MMA 指令喂进去的不是两个数，而是一个 16×16 量级的小矩阵块（FP16 为 16×8×16，INT8 为 16×8×32 等规格），直接输出 `D = A×B + C`。

类比：CUDA Core 是工人拿着笔一个个算乘法，Tensor Core 是焊死的冲压模具，压一下就是一整块矩阵的结果。AI 推理 90% 以上的时间花在矩阵乘法上，所以 1321 TOPS 的标称值全部来自这 512 个冲压机；而 CUDA Core 的 FP32 标称算力只有 82.6 TFLOPS，两者差近 16 倍。

这也构成了 4090 的 "双梯队" 结构：矩阵类算子进 Tensor Core 冲极速，其余算子 CUDA Core 兜底，详见 [4090 与 RK3588 硬件设计差异与原理](2026-08-03_4090与RK3588硬件设计差异与原理.md)。

### 3.3 Warp 调度器：用切换掩盖等待

每个 SM 有 4 个调度器，最小调度单位是 **Warp（线程束）= 32 个线程**，这 32 个线程锁步执行同一条指令（SIMT，单指令多线程），只是各自处理不同数据。

数据从显存搬进来需要几百个周期，工人如果干等就会停工。调度器的做法是在一个 SM 上同时驻留几十个 Warp（可达 64 个）：这个班组在等数据，立刻切换到另一个已经就绪的班组，**用高频切换把等待时间藏起来**。驻留的 Warp 越多，可掩盖的延迟越大，这就是常说的 Occupancy（占用率）。

## 四、软件怎么映射到硬件：线程、Warp、Block、Grid

程序员写的 CUDA kernel 是一套层级化的线程组织，它和硬件一一对应：



```
Grid（一个 kernel 的全部线程）
└── Block（线程块，CTA）     →  驻留在一个 SM 上，共享该 SM 的料架
    └── Warp（32 个线程）    →  调度器的最小派活单位
        └── Thread（线程）   →  一个 CUDA Core 上的一个工人
```



| 软件概念   | 规模                  | 硬件落点                         |
| ------ | ------------------- | ---------------------------- |
| Thread | 1 个                 | 处理 1 个数据元素                   |
| Warp   | 32 个 Thread         | 一次锁步调度，32 人同做一条指令            |
| Block  | 若干 Warp（最多 1024 线程） | 固定驻留在一个 SM，可共享 Shared Memory |
| Grid   | 若干 Block            | 铺满全部 128 个 SM，分波次执行          |

以前文的 Sigmoid 为例：4096×4096 特征图有 1677 万个数据点，启动 1677 万个线程，每个线程只算一个数。硬件收到这个 Grid 后，把 Block 一个个分派给 128 个 SM，每个 SM 内部再按 32 人一组交给调度器，CUDA Core 并行算完。

这里有个关键的 "绑定" 关系：**Block 一旦分配给某个 SM，就固定在这个 SM 上直到结束**（但可以轮换），因为 Block 内共享的 Shared Memory 是该 SM 的私有 SRAM。这也是为什么一个 Block 天然对应 "一块能在片上 SRAM 里反复使用的数据"—— 下一节的 tile 正是利用了这一点。



***

## 五、矩阵乘法怎么跑：tile 切块与波次调度

### 5.1 为什么必须切块

矩阵乘法的计数公式是 `FLOPs = 2×M×N×K`（每个输出元素做 K 次乘法 + K 次加法）。但 Tensor Core 一次只吃 16×16 量级的小块，而一个真实的权重矩阵是 4096×11008，不可能一次冲压完。于是库（cuBLAS/CUTLASS）把矩阵乘法切成一张**瓦片（tile）网格**：



* 每个输出 tile 取 128×128 个元素；

* **一个 thread block 负责计算一个 tile**；

* 一个 tile 内部再由若干 Warp 调 MMA 指令完成。

### 5.2 一个 block 内部：搬一条、算一条、复用一条

计算 128×128 的输出 tile，需要沿 K 维（4096）扫一遍。block 不是把 4096 全量数据搬进片上，而是分条带循环：



```
// 一个 thread block 负责输出矩阵的一块 128×128 tile
for (int k = 0; k < K; k += STEP) {
    // 1. 全 block 协作：把权重/激活的一个条带搬进 Shared Memory（车间料架）
    load_to_smem(A_tile, B_tile);
    __syncthreads();
    // 2. 各 Warp 从料架取数，喂 Tensor Core 做 MMA，累加到寄存器
    mma(acc, A_tile, B_tile, acc);
    __syncthreads();
}
// 3. 全部条带累加完，结果写回显存
```

**精髓在 "复用"**：权重条带搬进片上 SRAM 后，被同一 block 内所有 MMA 反复读取；而当 batch 里有多个 token（M 维度变大）时，同一份权重被更多输出行复用。数据搬一次，算很多次，这就是矩阵乘法能跑出高吞吐的根本机制。

### 5.3 波次调度：128 个 SM 一波

一个 kernel 启动后，Grid 里可能有几百上千个 block，而 SM 只有 128 个：



* 第一波（wave）：前 128 个 block 铺到 128 个 SM 上**同时**执行；

* 第一波跑完释放 SM，第二波 128 个 block 再上，以此类推；

* 波次 ≈ ⌈block 总数 ÷ 128⌉。

以 7B 模型的一个 FFN 投影（权重 4096×11008，tile 128×128）为例：



| batch 内 token 数 T | M 方向 tile 数  | N 方向 tile 数     | block 总数 | 波次  |
| ----------------- | ------------ | --------------- | -------- | --- |
| 100               | 1（⌈100/128⌉） | 86（⌈11008/128⌉） | 86       | 1 波 |
| 300               | 3            | 86              | 258      | 3 波 |
| 1000              | 8            | 86              | 688      | 6 波 |

每波的理论耗时可以直接算：一个 tile 的运算量是 `2×128×128×4096 ≈ 1.34×10⁸ FLOPs`，单 SM 的 INT8 峰值是 `660×10¹² ÷ 128 ≈ 5.16 TFLOPS`，单波约 **26 μs**。

注意 T=100 时只有 86 个 block、128 个 SM 中有 42 个完全没分到活 ——**这就是短输入喂不饱 GPU 的硬件级原因**，下一节展开。

## 六、存储接力：数据从大仓库到冲压机的四级通路

Tensor Core 算得再快，数据不到也是空转。4090 的存储是一个典型的 "容量递减、带宽递增、延迟递减" 金字塔：



```
GDDR6X 显存   24 GB   | 1008 GB/s  | 延迟数百周期      ← 工厂大仓库
   ↓
L2 缓存       72 MB   | 数 TB/s    | 全片共享          ← 厂区中转仓
   ↓
L1/Shared     128 KB  | 十几 TB/s | 每个 SM 私有      ← 车间料架
   ↓
寄存器堆       256 KB  | 最高，零级延迟 | 工人手边       ← 工人手边的零件盒
   ↓
Tensor Core（冲压机）
```

为什么不把存储全做成 SRAM？因为成本、面积、功耗：SRAM 每比特占用的晶体管面积是 DRAM 的几十倍，24GB 全用片上 SRAM 芯片会做到脸盆大。所以真实架构是 "**小容量快存储 + 大容量慢存储 + 精心组织的搬运复用**"。

复用的账可以量化。还是单个 FFN 投影：



* 权重 45MB（4500 万个 INT8 参数），从 GDDR6X 读一遍约 `45MB ÷ 1008GB/s ≈ 45 μs`，**与 T 无关**；

* 纯计算耗时 `9.0×10⁷ × T ÷ 660×10¹²`：T=1 时仅 0.14μs，T=100 时 13.7μs，T=1000 时 137μs。



| T    | 计算耗时    | 读权重耗时 | 实际耗时取 max      |
| ---- | ------- | ----- | -------------- |
| 100  | 13.7 μs | 45 μs | ≈ 45 μs（搬运主导）  |
| 300  | 41 μs   | 45 μs | ≈ 45 μs（交叉点）   |
| 1000 | 137 μs  | 45 μs | ≈ 137 μs（计算主导） |

交叉点约在 T=300：数据搬进来的速度刚好够 Tensor Core 吃不饱也不闲着。这就是 Roofline 模型 ——**计算与搬运是流水线并行的，总时间由两者中较长的一条决定**。更系统的带宽论证见 [内存带宽为何决定解码速度](2026-09-27_内存带宽为何决定解码速度-算术强度与带宽三因子.md)。

## 七、标称算力的口径：1321 TOPS 是怎么来的

看 4090 规格书会看到一串差异巨大的数字，它们的区别是 "谁在算、算什么精度"：



| 精度        | 稠密峰值        | 2:4 稀疏峰值   | 由谁执行        |
| --------- | ----------- | ---------- | ----------- |
| FP32      | 82.6 TFLOPS | —          | CUDA Core   |
| FP16/BF16 | 330 TFLOPS  | 660 TFLOPS | Tensor Core |
| INT8      | 661 TOPS    | 1321 TOPS  | Tensor Core |
| INT4      | 1321 TOPS   | 2642 TOPS  | Tensor Core |

三个口径要点：



1. **精度越低，单周期塞进 Tensor Core 的数越多**，INT8 吞吐量是 FP16 的 2 倍、FP32 的 16 倍，这就是量化加速的来源；

2. **1321 是 2:4 结构化稀疏口径**：要求权重矩阵每 4 个数里至少 2 个是 0，硬件直接跳过。真实模型很难满足这个模式，工程估算一般按**稠密 661 TOPS** 计算；

3. INT8 是整数运算，严格单位是 **TOPS**（Operations Per Second），口语才叫 TFLOPS；无论 TOPS 还是 TFLOPS，都是**每秒速率**，不是 "一次能装多少"。



***

## 八、MFU：标称算力为什么实际只跑出几分之一

**MFU（Model FLOPs Utilization，模型算力利用率）**：



```
MFU = 理论必需的运算量（如 2 × 参数量 × token 数）
       ÷（峰值 FLOPS × 实际墙钟时间）
```

即标称峰值里有多少真正转化成了有效矩阵计算。典型数量级：



| 场景              | MFU 数量级  |
| --------------- | -------- |
| 大集群训练           | 40%\~55% |
| 大 batch Prefill | 30%\~60% |
| 单个短 prompt      | 10%\~20% |
| 单并发 Decode      | 通常不到 5%  |

标称算力浪费在三个地方，都能在前面的硬件结构里找到对应：



1. **tile 铺不满 SM**：T=100 只有 86 个 block，42 个 SM 当场闲置；decode 时 M=1，GEMM 退化成 GEMV，Tensor Core 连一个 tile 的宽度都填不满。

2. **数据供不上**：T<300 时计算被 45μs 搬运地板淹没，Tensor Core 后半段空转等数据（算术强度约 2T FLOPs/byte，而 4090 的 Roofline 拐点约为 `660×10¹² ÷ 1008×10⁹ ≈ 655 FLOPs/byte`）。

3. **非矩阵开销**：每层几十个 kernel 的启动开销（数 μs / 次），以及 Softmax、RoPE、LayerNorm、采样、KV cache 读写等不跑 Tensor Core 的算子。矩阵越小，这些固定开销占比越大。

## 九、用硬件结构解释四个推理现象

把前面的机制串起来，推理引擎的常见现象都有了物理解释：



| 现象                             | 硬件根因                                                 |
| ------------------------------ | ---------------------------------------------------- |
| Prefill 要长 prompt / 大 batch 才快 | M 维度大才能切出足够 tile 铺满 128 个 SM，且权重复用次数越过 Roofline 拐点   |
| Decode 单并发只有几十～上百 token/s      | M=1 的 GEMV，每步读 7GB 权重只需 7ms 但计算只占 0.1%，纯带宽受限         |
| Continuous batching 能大幅提吞吐     | 把多用户的单 token 拼成大 tile，让同一份权重搬运被几十个 token 摊薄          |
| CUDA Graph 能降延迟                | 一次性录制每层几十个 kernel 的启动序列，消除反复 launch 的数 μs 开销         |
| 长上下文真正的硬上限是显存                  | 不是算力装不下，而是 KV cache 占显存：7B 模型 FP16 约 1MB/token，写满才排队 |

用 7B 模型（约 6.7B 参数，每 token 前向运算量 `2P ≈ 1.4×10¹⁰ FLOPs`）在 4090 上做两个闭环估算：



```
Prefill 理论天花板：660×10¹² ÷ 1.4×10¹⁰ ≈ 4.7 万 token/s（×MFU 30%~60% 后为 1.5~2.8 万）
Decode 带宽天花板：  7GB 权重 ÷ 1008 GB/s ≈ 7 ms/token（约 144 token/s，实际 10~20ms）
```

同一个 7B 模型，Prefill 单价是微秒级、Decode 单价是毫秒级，相差约百倍 —— 这不是软件优化差异，而是 "一批 token 并行冲压" 与 "一次只算一个 token 却要搬全部权重" 的结构差异。

## 十、工程启示与性能核查清单



1. **判断瓶颈先看算术强度**：`每字节复用次数 = 2 × batch总token数`，低于约 300 就是带宽受限，加 TOPS 无效，要加 batch、减权重（量化）或争带宽。

2. **短 prompt 的 MFU 低是物理必然**，不是引擎没调好；提升单请求短 prompt 性能的正确手段是拼批（continuous batching /chunked prefill），不是换更快的卡。

3. **选卡看三件套，不要只盯 TOPS**：算力（Prefill 上限）、显存带宽（Decode 上限）、显存容量（KV cache 决定并发与上下文上限）。

4. **警惕宣传口径**：稀疏 TOPS 直接砍半估算，INT8 与 FP32 标称值不可混用，实测以 MFU 折算后的有效算力为准。

性能核查清单：



* [ ] 当前任务是 GEMM 还是 GEMV？batch 总 token 数能否越过 Roofline 拐点？

* [ ] nvidia-smi 之外是否用 profiler（Nsight/nvitop）看过 SM Active 与 Tensor Core 利用率？

* [ ] kernel launch 开销是否已用 CUDA Graph 消除？

* [ ] KV cache 显存占用是否已估算（FP16 约 1MB/token/7B）？并发上限是多少？

* [ ] 带宽是否被同卡其他服务（ASR/TTS/ 渲染）竞争？
