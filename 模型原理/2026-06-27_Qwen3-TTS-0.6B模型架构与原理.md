## 核心摘要

Qwen3-TTS-0.6B 采用 Talker → Code2Wav 两阶段架构：Talker 以 28 层 Transformer 将文本编码为 12 Hz 的 16 路多码本语音 token，Code2Wav 以因果卷积声码器增量解码为 PCM 波形，两阶段经 SharedMemory 异步流水线实现帧级流式输出。该设计将语义编码与波形合成解耦，0.6B 即可实现低延迟流式 TTS，但 Code2Wav 单槽设计在高并发时成为瓶颈。

---

## 一、设计动机：为什么不用端到端

传统 TTS 方案（Tacotron、VITS 等）尝试用单一网络完成「文本 → 波形」，面临两个工程难题：

1. **波形分辨率太高**：24 kHz 音频每秒 24000 个采样点，自回归逐点生成极其缓慢；
2. **语义与声学耦合**：文本理解（语义）和波形细节（声学）混在一个网络里，难以分别优化、难以流式。

Qwen3-TTS 的解法是**分层抽象**——引入一个中间表示「语音 codec token」：

```text
文本 ──Talker──→ 语音 codec token（12 Hz, 16 码本）──Code2Wav──→ PCM 波形（24 kHz）
```

- 语音 token 的帧率仅 **12 Hz**（每秒约 12 帧），比原始波形的 24000 Hz 压缩了 **2000 倍**，自回归生成代价可控；
- 每个 token 帧携带 **16 路码本**（multi-codebook），同时编码语义和残差声学信息，信息密度高；
- Code2Wav 作为独立声码器，可以用非自回归的因果卷积快速解码，天然支持流式。

这种「自回归 token + 非自回归声码器」的分工，是近年来语音生成领域的主流范式（VALL-E、CosyVoice 等均采用类似思路），Qwen3-TTS 将其与 Qwen3-Omni 全模态体系中的 Talker–Code2Wav 框架对齐。

## 二、模型概览

| 项目 | 说明 |
|------|------|
| 全称 | Qwen3-TTS-12Hz-0.6B-CustomVoice |
| 参数量级 | Talker 约 **0.6B**；整体权重磁盘约 **2.4 GB** |
| 任务类型 | **CustomVoice** — 预设音色合成，支持 `speaker` + `language` |
| 音频编码率 | **12 Hz**（`tokenizer_type: qwen3_tts_tokenizer_12hz`，帧率约 12.5 Hz） |
| 输出音频 | PCM **24 kHz**、16-bit、单声道 |
| 支持语言 | 中、英、德、意、葡、西、日、韩、法、俄，及北京话、四川话方言 |

**命名解读：**

- **12Hz**：语音离散表示的时间分辨率约为每秒 12 帧 codec token，比传统 25 Hz/50 Hz 更低，有利于流式与并发。
- **0.6B**：指 Talker 自回归主干规模；Code2Wav 声码器参数量很小。
- **CustomVoice**：内置 9 种预设说话人（如 `vivian`、`ryan`），通过 `spk_id` 嵌入音色。0.6B-CustomVoice **不支持 `instructions` 参数**（与 1.7B 变体不同，无法通过指令控制情感语调）。

## 三、整体架构：两阶段流水线

```text
输入：文本 + 音色(speaker) + 语言(language)
                    ↓
┌──────────────────────────────────────────────────┐
│  Talker（Stage 0）                                │
│  自回归 Transformer，生成 multi-codebook 语音 token │
└──────────────────────────────────────────────────┘
                    ↓  speech tokens（异步 chunk）
┌──────────────────────────────────────────────────┐
│  Code2Wav（Stage 1）                              │
│  轻量因果 ConvNet 声码器，token → PCM 波形         │
└──────────────────────────────────────────────────┘
                    ↓
输出：可流式播放的 PCM 音频
```

两个阶段在 **vLLM-Omni** 中被拆成**两个独立的 Stage 引擎进程**（`VLLM::StageEngineCoreProc`），通过 SharedMemory 传递中间 chunk。Talker 边生成 token，Code2Wav 边解码波形，无需等整句 token 全部完成——这就是帧级流式输出的实现基础。

## 四、Talker：自回归语音 token 生成（Stage 0）

### 4.1 职责

Talker 是模型的**核心自回归（AR）组件**。它不直接输出音频采样点，而是将文本条件「翻译」成一串高压缩率的**多码本语音编码**。可以理解为：在内部把「要说的话」编成一串离散的语音 token 序列。

### 4.2 结构配置

| 配置项 | 值 | 含义 |
|--------|-----|------|
| `model_type` | `qwen3_tts_talker` | Talker 主干 |
| `num_hidden_layers` | **28** | Transformer 层数 |
| `hidden_size` | 1024 | 隐藏维度 |
| `num_attention_heads` | 16 | 注意力头数 |
| `num_key_value_heads` | 8 | GQA 分组 |
| `max_position_embeddings` | 32768 | 最大上下文长度 |
| `num_code_groups` | **16** | 每帧 **16 路码本**（multi-codebook） |
| `position_id_per_seconds` | 13 | 与时间位置编码相关 |

Talker 内嵌 **code_predictor**（`qwen3_tts_talker_code_predictor`，5 层），用于**多 token 预测（MTP）**：先预测语义码本，再预测各残差声学码本。这与 Qwen3-Omni 技术报告中的 multi-track codec 建模一致——16 路码本并非一次性预测，而是按「语义 → 残差声学」的层次逐步展开。

### 4.3 多码本机制：为什么是 16 路

单一码本无法同时表达语音的语义（说了什么）和声学细节（怎么说的）。Qwen3-TTS 采用 **16 路残差量化码本**：

- **前几路码本**编码语义信息（类似文本的音素级表示）；
- **后几路码本**编码残差声学细节（音色、韵律、环境噪声等）；
- 16 路叠加后，一帧 token（12 Hz）携带的信息足以重建 24 kHz 波形中约 1920 个采样点。

这种分层量化借鉴了 EnCodec / SoundStream 的残差向量量化（RVQ）思想：每路码本修正前一路的量化误差，逐级逼近原始波形。

### 4.4 音色与语言注入

音色和语言信息通过 codec 侧的 ID 直接注入模型：

| 条件 | 示例映射 |
|------|----------|
| `spk_id` | `vivian` → 3065，`ryan` → 3061 |
| `codec_language_id` | `chinese` → 2055，`english` → 2050 |

这些 ID 作为特殊 token 拼接在输入序列中，Talker 在自回归生成时即可条件化到指定音色和语言，无需额外的适配器网络。

### 4.5 输出形态

每解码步产出**一帧** multi-codebook tokens（16 个量化器层级），帧率约 **12 Hz**。这些 token 经 SharedMemory 送给 Stage 1，支持 `async_chunk: true` 流水线。

### 4.6 运行特征

| 项目 | 典型值 |
|------|--------|
| GPU 权重显存 | 约 **1.74 GiB**（固定下限） |
| 可调运行时 | **KV cache**（由 `gpu-memory-utilization` 主导）、`torch.compile`、CUDA Graph |
| `max_num_seqs` | **10**（最多约 10 路序列并行） |
| `max_num_batched_tokens` | **512** |

Talker 是唯一需要大规模 KV cache 的阶段。`gpu-memory-utilization` 主要压缩这一块：4090 独占时默认约 12.26 GiB KV cache（理论约 28× 4096-token 并发），设为 0.10 时约 2.8 GiB（约 6.4×）。

## 五、Code2Wav：增量声码器（Stage 1）

### 5.1 职责

Code2Wav 是**声码器（vocoder）**：将 Talker 输出的离散 codec tokens **增量解码**为连续 PCM 波形。对应 `speech_tokenizer` 的 decoder 路径（`Qwen3TTSTokenizerV2Model` 的 decoder），采用轻量**因果卷积网络（causal ConvNet）**，替代早期 DiT 类块级合成器。

### 5.2 为什么用因果卷积而非自回归

声码器的目标是「token 序列 → 波形序列」，这是一个**确定性的映射**（给定 token，波形基本确定），不需要像文本生成那样做概率采样。因果卷积网络的优势在于：

- **非自回归**：一次前向即可输出整段波形，不需要逐采样点循环；
- **因果性**：只依赖历史 token，天然支持流式（来一批 token 解码一批波形）；
- **轻量**：8 层卷积远比 Transformer 参数少，解码速度快。

### 5.3 结构配置

| 配置项 | 值 | 含义 |
|--------|-----|------|
| `model_type` | `qwen3_tts_tokenizer_12hz` | 12 Hz 编解码器族 |
| `input_sample_rate` / `output_sample_rate` | 24000 | 24 kHz |
| `encoder_valid_num_quantizers` | 16 | 与 Talker 16 码本对齐 |
| `decode_upsample_rate` | 1920 | 单帧 token → 采样点倍数（12 Hz × 1920 ≈ 24 kHz） |
| `decoder_config.sliding_window` | **72** | 解码滑动窗口帧数 |
| `decoder_config.num_hidden_layers` | 8 | 解码器深度 |
| `encoder_config._frame_rate` | 12.5 | 编码帧率 |

**关键数值关系**：12 Hz 帧率 × 1920 倍上采样 ≈ 23040 ≈ 24 kHz 采样率。这意味着每一帧 codec token 对应约 1920 个音频采样点（约 80 ms 音频）。

### 5.4 流式分块解码

Code2Wav 按 `codec_chunk_frames` 窗口接收 token，配合 `codec_left_context_frames` 保持说话人连续性与 chunk 边界质量。核心约束是：

> `codec_left_context_frames` 必须 ≥ decoder 的 `sliding_window`（72 帧）

这保证了卷积的感受野覆盖 chunk 边界，避免拼接处出现爆音或音色跳变。vLLM-Omni 默认 `initial_codec_chunk_frames: 1`，首包只解码最小 chunk 以降低首帧延迟（TTFA），后续恢复正常窗口。

### 5.5 运行特征

| 项目 | 典型值 |
|------|--------|
| GPU 权重显存 | 约 **0.45 GiB**（固定下限） |
| 运行时占用 | 编译缓存 + CUDA Graph，总占用常达 **3–4 GiB+** |
| `max_num_seqs` | **1**（同一时刻只 vocode **一路**） |
| `max_num_batched_tokens` | 65536 |

Code2Wav 参数量很小，但 `torch.compile` 缓存和 CUDA Graph 的编译产物会占用数倍于权重的显存——这是「轻量模型 ≠ 低显存」的典型案例。

## 六、流式输出与首包延迟（TTFA）

### 6.1 流式管道的协作

帧级流式的实现依赖两阶段的异步协作：

```text
Talker:  [prefill] → [token₁] → [token₂] → [token₃] → ...
                           ↓          ↓          ↓
Code2Wav:              [vocode₁] → [vocode₂] → [vocode₃] → ...
                           ↓          ↓          ↓
输出:                 [PCM₁]     [PCM₂]     [PCM₃]  (可播放)
```

Talker 生成第一批 token 后，Code2Wav 立即开始解码，二者形成流水线。用户在 Talker 还在生成后续 token 时，就已经能听到前半句的语音。

### 6.2 首包延迟的构成

首帧可播放 PCM 需要**两个阶段都完成各自的第一步**：

1. **Talker**：至少完成一轮 prefill + 产出首批 codec tokens；
2. **Code2Wav**：对首批 tokens 完成首次 vocode。

### 6.3 并发瓶颈分析

Code2Wav 的 `max_num_seqs = 1` 意味着**同一时刻只解码一路音频**。多路并发时，各路的 vocode 请求会排队：

| 并发路数 | 瓶颈位置 | 典型 TTFA |
|----------|----------|-----------|
| 1–2 路 | 无明显瓶颈 | warm 后 HTTP ~68 ms，WS 首帧 PCM ~46 ms |
| 8 路 | **Code2Wav 单路排队** + Talker prefill batch 限制 | 约 **955 ms** |

8 路短句压测中 TTFA 飙升的主因是 Code2Wav 单路串行解码，而非 0.6B Talker 算力不足。这意味着提高并发不能靠继续降 `gpu-memory-utilization`，而需要 Code2Wav 多实例或调整 batch 参数。

## 七、显存：为何不是「0.6B × 2 bytes」

直觉上 0.6B 参数 × 2 bytes（FP16）≈ 1.2 GiB，但实测远不止于此。

### 7.1 显存构成拆解

| 组件 | 权重（固定） | 运行时（可调） |
|------|--------------|----------------|
| Stage 0 Talker | **1.74 GiB** | KV cache + `torch.compile` + CUDA Graph |
| Stage 1 Code2Wav | **0.45 GiB** | 编译缓存、解码 Graph（通常 **3–4 GiB**） |

### 7.2 为什么权重就超了

- 0.6B 指的是 Talker 的**主干参数**，不含 code_predictor（5 层）、embedding 表等附加结构；
- Code2Wav 虽然推理时只用 decoder，但 encoder 权重也可能被加载（磁盘体积约 651 MB）；
- FP16 下 0.6B 参数 ≈ 1.2 GiB，加上附加结构后 Talker 实际约 1.74 GiB。

### 7.3 运行时的隐性开销

- **KV cache**：Talker 是唯一需要大规模 KV cache 的阶段，这是 `gpu-memory-utilization` 能调控的主要部分；
- **CUDA Graph / torch.compile 缓存**：尤其 Code2Wav 的解码路径，Graph 缓存可达 3–4 GiB，与 0.45 GiB 的参数量完全不成比例；
- **双进程开销**：vLLM-Omni 将 Talker 和 Code2Wav 拆成两个独立进程，各有自己的框架开销。

### 7.4 实测数据

| 配置 | 4090 空闲显存 |
|------|---------------|
| 默认（独占 TTS） | 约 **20 GB** |
| `gpu-memory-utilization=0.10` | 约 **10 GB** |

权重下限约 **2.2 GiB**，无法通过推理参数再压低。能调的主要是 Talker KV cache 及两侧编译/Graph 行为。

## 八、与 Qwen3-Omni 全模态的关系

Qwen3-TTS 0.6B 可视为 Qwen3-Omni 全模态体系中 TTS 子集的独立部署版本：

| 概念 | Qwen3-Omni（全模态对话） | Qwen3-TTS 0.6B（本模型） |
|------|--------------------------|---------------------------|
| Thinker | 理解多模态输入、生成文本 | **无**（纯 TTS，文本由外部提供） |
| Talker | 从 Thinker 隐状态生成语音 token | **有**，直接从文本条件生成 token |
| Code2Wav | token → 波形 | **有**，结构类似，独立 Stage 1 |

Qwen3-Omni 的完整链路是「多模态输入 → Thinker 理解 → Talker 生成语音 token → Code2Wav 合成波形」。Qwen3-TTS 0.6B 砍掉了 Thinker，直接从外部文本输入起步，保留了 Talker → Code2Wav 两阶段，便于流式与 vLLM-Omni 流水线优化。

## 九、知识点速查表

| 概念 | 所在阶段 | 作用 |
|------|----------|------|
| Talker | Stage 0 | 自回归 Transformer，文本 → 16 路多码本语音 token |
| Multi-codebook (16 路) | Talker 输出 | 残差量化，分层编码语义 + 声学细节 |
| code_predictor (MTP) | Talker 内部 | 多 token 预测，先语义后残差声学 |
| Code2Wav | Stage 1 | 因果卷积声码器，token → PCM 波形 |
| 12 Hz 帧率 | 编解码器 | 时间分辨率，比波形压缩 2000 倍 |
| decode_upsample_rate (1920×) | Code2Wav | 单帧 token → 1920 采样点（≈80 ms 音频） |
| sliding_window (72 帧) | Code2Wav | 解码感受野，保证 chunk 边界质量 |
| SharedMemory 异步管道 | Stage 0→1 | 帧级流式，Talker 边生成 Code2Wav 边解码 |
| KV cache | Talker | 自回归加速，显存可调主项 |
| CUDA Graph 缓存 | 两阶段 | 编译产物，Code2Wav 侧可达 3–4 GiB |

## 十、延伸思考

- **解耦的代价**：两阶段架构换来流式能力，但 Code2Wav 单槽设计成为高并发瓶颈。未来方向可能是 Code2Wav 多实例部署或更高效的并行声码器。
- **0.6B vs 1.7B 的取舍**：0.6B-CustomVoice 不支持 `instructions` 参数（无法指令控制情感），1.7B 变体支持。在需要情感控制的场景下，0.6B 的轻量优势可能不成立。
- **端侧部署启示**：Talker 的 KV cache 是显存大头，在显存受限设备上需权衡并发数与序列长度；Code2Wav 虽然参数小但 Graph 缓存大，端侧可能需要关闭 `torch.compile` 换取显存。
- **与端到端模型的对比**：VITS 等端到端模型在单句合成时延迟可能更低（无阶段间通信），但流式能力和可控性不如两阶段方案。选型需根据「是否需要流式」「并发规模」「音色可控性」综合判断。
