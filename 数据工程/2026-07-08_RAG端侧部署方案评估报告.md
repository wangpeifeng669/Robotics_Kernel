# RAG 语料库检索服务端侧部署方案评估报告

> 评估对象：`rag_doc/` 目录下 11 份技术文档，覆盖总体方案、三阶段技术规格、调用协议、部署指南、语料处理流程、领域词表说明等。  
> 评估时间：2026-07-08  
> 评估结论：**综合评分 8.9/10 — 工程成熟度高，端侧部署方案尤其扎实，属于可落地的生产级方案。**

---

## 一、总体定位判断

这套方案**不是通用大模型 RAG**，而是一个面向 RK3588 端侧的**轻量级垂直领域 QA 检索引擎**。核心判断是正确的：

- **数据规模小**（≤1000 条 QA），全量内存化，无需 Milvus/Faiss/ES 等重型组件
- **算力受限**（RK3588 ARM64），不适合重型生成链路，高置信直接返回答案
- **垂直领域**，专业词精确性要求高，单一向量检索不够
- **语音交互场景**，ASR 错字、谐音字是主要痛点

方案明确提出了「不做系统内可计算推理」的能力边界——答案只来自语料原文，推理型问题降级为候选+证据交外部大模型。这个边界划得非常清楚，避免了端侧设备上跑不动的东西被塞进来。

## 二、逐维度评估

### 2.1 架构设计 — 9.0/10

**亮点：**

1. **四层分离清晰**：调用层（TCP/UDS）→ 服务层（API）→ 检索推理层（Hybrid Retrieval）→ 数据层（内存索引），职责边界明确
2. **双通道接入**：TCP 供局域网设备、UDS 供板内低延迟调用，非常贴合端侧多模块协作场景
3. **三档置信决策**（direct/candidates/miss）是整个系统的核心设计，直接定义了「什么时候敢答、什么时候给候选、什么时候拒答」
4. **Direct Guard 机制**：不只是看分数阈值，还要求分差 margin + 向量分 + 槽位不冲突，防止 BM25 单路高分导致误答
5. **能力边界明确**：每个阶段都列出了「不实现什么」，避免了功能蔓延

**可改进：**

- 调用层缺少鉴权机制。TCP 监听 `0.0.0.0` 意味着局域网任意设备可调用，生产环境应考虑 token 或 IP 白名单
- 进程内缺少优雅退出机制（SIGTERM 处理），systemd 重启时可能丢失正在处理的请求

### 2.2 检索策略 — 8.5/10

**亮点：**

1. **六路混合召回**（Exact/BM25/Vector/Alias/Pinyin/Slot）覆盖了端侧语音场景的主要痛点：精确匹配兜底、关键词召回专业词、向量召回语义、别名/拼音纠错 ASR、槽位消歧时间地点
2. **融合打分公式**有明确的权重分配和归一化逻辑，权重可通过配置调优
3. **多 Query 扩展**策略设计合理：原始 query 始终保留，高置信纠错生成修正 query，低置信纠错只追加不覆盖
4. **Reranker 可选化**：trigger_mode 支持 `always`/`medium_only`/`disabled`，medium_only 模式下高置信命中跳过 Reranker 节省延迟
5. **意图分类影响权重**：temporal_query 提升槽位权重、operational_query 提升 BM25 权重，comparison_query 强制走 candidates

**可改进：**

1. **BM25 归一化方式有隐患**：使用 `raw_score / max_raw_score` 做 per-query 归一化，导致负例 query 内部 BM25 分也常接近 1.0，是 false_direct 的主要根因。改进策略文档已识别此问题，但未给出根本解决方案。建议引入 **全局 BM25 统计基线**或 **IDF 加权的绝对分数**，而非仅 per-query 相对归一化
2. **拼音纠错的计算复杂度**未充分讨论。文档提到「不对每次 query 全量暴力扫描」，但具体预构建策略不够明确。在领域词 200 条以内时问题不大，但如果词表增长需要关注
3. **中置信阈值过窄**：第二阶段配置 `high=0.90, medium=0.88`，只有 0.02 的 candidates 窗口，可能导致大量问题在 direct 和 miss 之间两极分化，candidates 模式几乎不触发
4. **缺少 Query 理解的反馈机制**：系统有 trace 和日志，但没有基于线上错样的自动调参闭环（需要人工跑 tune_thresholds.py）

### 2.3 端侧适配 — 9.5/10

**亮点：**

1. **CPU 基线先行**：第一阶段明确要求先跑通 CPU 版 bge-small-zh-v1.5，再切 NPU，避免「无法判断问题来自模型、量化、推理后端还是检索逻辑」
2. **ONNX 精简部署**：母盘制作走 `setup_runtime_board.sh`，venv ~200MB 无 PyTorch，模型只保留 `model.onnx` + tokenizer 文件，非常精简
3. **母盘镜像 + deb 增量更新**：量产板刷镜像零安装，小版本迭代走 `dpkg -i` 只更源码，部署策略成熟
4. **模型选择合理**：bge-small-zh-v1.5 作为主模型（体积小、延迟低），bge-base-zh-v1.5 作为备用（效果更好但需实测），bge-reranker-base 作为可选精排
5. **性能目标分阶段设定**：从 P1 的 100ms 到 P3 含 Reranker 的 250ms，逐步加码，每阶段有明确验收指标
6. **热更新机制**：`reload_corpus` 支持 URL 下载 Excel → 原子替换 → 重建索引，期间 query 返回 `corpus_downloading/loading`，设计周到

**可改进：**

- **NPU 适配路径缺失**：文档反复提到「后续切 NPU」，但没有 NPU 适配的技术方案（RKNN 模型转换、量化校准、推理后端选型）。考虑到 RK3588 有 6TOPS NPU 算力，这部分应该是端侧部署的关键竞争力
- **内存预算偏紧**：RK3588 推荐 ≥4GB 内存，但 bge-small + Reranker + 索引 + Python 运行时可能接近 2.2GB。如果板上还跑 ASR/LLM/TTS 模块，内存可能不足

### 2.4 工程化 — 10.0/10

**这是整套方案最突出的部分。**

**亮点：**

1. **文档可直接生成代码**：每阶段文档末尾都有「AI 代码生成指令」，明确生成顺序和约束，可以用 AI 工具直接产出可运行代码
2. **验收标准明确**：每阶段 15-16 条验收标准，从功能可用到单元测试覆盖到性能指标，逐条可验证
3. **单元测试全覆盖**：loader/normalizer/retrieval/decision/protocol 每个模块都有明确测试要求，Embedding 支持 fake 模式用于无模型测试
4. **评测体系完整**：从测试集构建（8 类样本）到核心指标（Top1/Top3/false_direct/miss_rate/P95）到阈值调参工具，形成闭环
5. **配置即文档**：YAML 配置文件结构清晰，每个字段有注释和约束条件
6. **协议兼容性**：version 字段、向后兼容（不传 version 按 1.0 处理）、稳定字段列表，协议演进路径清晰
7. **日志设计**：结构化 JSON 日志，包含 request_id/query/score/status/latency/score_profile，可回放评测
8. **systemd 集成**：service 文件、自启、journalctl 日志查看，标准 Linux 服务管理

### 2.5 可观测性 — 8.0/10

**亮点：**

1. **结构化查询日志**：每次 query 记录完整链路信息（归一化后 query、扩展 query 列表、各路分数、最终决策、延迟）
2. **Stats 接口**：运行期统计包括 query/hit/miss 计数、纠错触发次数、Reranker 触发/超时次数、意图分布
3. **Trace 模式**：`need_trace=true` 返回扩展 query、各路分数 profile、Reranker 前后对比，便于调试
4. **Health 接口**：语料版本、QA 数量、索引条数、词典加载状态、Reranker 状态

**可改进：**

1. **缺少 Prometheus/metrics 导出**：当前只有 stats 接口拉取，没有 push 到监控系统的机制。生产环境建议加 Prometheus exporter
2. **缺少延迟分位数实时监控**：stats 只返回 avg_latency，P95/P99 需要日志回放才能获得
3. **缺少告警机制**：Reranker 超时、语料加载失败、内存超限等异常没有主动告警

### 2.6 可扩展性 — 8.5/10

**亮点：**

1. **阶段间解耦**：每阶段只增量添加模块，不重建工程，不删除前序模块
2. **接口预留**：AsrCorrector/ContextResolver/PinyinRetriever/Reranker/CorpusReloader 都有预留接口，且保持无副作用
3. **Embedding 后端可切换**：cpu/npu/fake 三种后端，配置切换
4. **协议可演进**：JSON → MessagePack/protobuf 的评估和切换路径已规划

**可改进：**

1. **单进程架构的并发瓶颈**：asyncio 单线程模型，多 query 扩展会放大计算量。如果并发查询增加，可能需要 Worker 池或多进程
2. **语料规模上限未测试**：文档基于 1000 条 QA 设计，如果语料增长到 5000-10000 条，BM25 和向量矩阵的内存/延迟变化未讨论
3. **多语料库支持**：当前只支持单份 Excel，如果需要按场景分库检索（如不同业务领域），架构需要扩展

### 2.7 文档质量 — 9.0/10

**亮点：**

1. **分层清晰**：总体方案 → 三阶段技术规格 → 调用协议 → 部署指南 → 操作手册 → 入门解读，面向不同读者
2. **可复现**：每个技术选型都有理由说明，每个配置项都有约束条件，部署步骤可直接照做
3. **面向不同读者**：操作指南面向业务/运维，技术方案面向开发，混合检索流程说明面向初学者
4. **交叉引用完整**：文档间互相引用，形成知识网络

**可改进：**

- 缺少一份全局的 **架构决策记录（ADR）**，解释为什么选 bge-small 而非其他模型、为什么选 JSON Line 而非 gRPC、为什么不做系统内推理等

## 三、关键风险识别

| 风险等级 | 风险描述 | 当前应对 | 建议 |
|---------|---------|---------|------|
| **高** | BM25 per-query 归一化导致负例高分 | Direct Guard（margin + vector + slot） | 引入全局 BM25 基线或负例训练样本 |
| **高** | 中置信窗口过窄（0.88-0.90） | 阈值可通过 tune_thresholds.py 调 | 实测后根据分布重新设定，建议 medium 降到 0.75-0.82 |
| **中** | Reranker 在 RK3588 上延迟可能 >200ms | 超时保护 + trigger_mode | 优先验证 ONNX 路径，必要时关闭 Reranker |
| **中** | NPU 适配方案缺失 | CPU 基线先行 | 尽快补充 RKNN 转换和量化方案 |
| **中** | 内存预算偏紧（≤4GB 板上多模型共存） | 内存目标 <1.5GB/2.2GB | 实测 ASR+LLM+TTS+RAG 共存时的内存峰值 |
| **低** | TCP 无鉴权 | 无 | 生产环境加 token 或改 UDS only |
| **低** | 语料规模扩展性未验证 | 当前 ≤1000 条 | 压测 5000 条 QA 的延迟和内存 |

## 四、与同类方案对比

| 维度 | 本方案 | 通用 RAG (LangChain+向量库) | LLM 端侧直接生成 |
|------|-------|---------------------------|----------------|
| 端侧适配 | 极强（RK3588 专用优化） | 弱（依赖云服务或大算力） | 弱（端侧 LLM 效果差） |
| 延迟 | 5-250ms（按阶段和配置） | 200ms-2s（依赖网络） | 500ms-5s |
| 准确率 | 可控（三档置信 + 评测闭环） | 不可控（幻觉风险） | 不可控（幻觉风险） |
| 答案可信度 | 高（只返回语料原文） | 中（可能编造） | 低（端侧模型能力有限） |
| 部署复杂度 | 中（母盘+deb） | 高（多个组件） | 中（模型量化） |
| 可维护性 | 高（配置驱动 + 评测闭环） | 中（调试链路长） | 低（黑盒） |

本方案在端侧垂直领域 QA 场景下**显著优于**通用 RAG 和端侧 LLM 直接生成。

## 五、改进建议优先级

### P0（上线前必须解决）

1. **TCP 鉴权**：至少加一个简单 token 校验，防止局域网误调用
2. **中置信阈值实测调优**：当前 0.88-0.90 的窗口太窄，需要用真实评测集重新标定
3. **内存峰值压测**：在 RK3588 上实测 RAG + ASR + TTS 共存时的内存占用

### P1（第一轮迭代）

4. **NPU 适配方案**：补充 RKNN 模型转换、量化校准的技术文档
5. **BM25 归一化改进**：引入全局统计基线，解决负例高分问题
6. **Prometheus metrics 导出**：支持延迟分位数、命中率、纠错触发等指标的实时监控

### P2（后续演进）

7. **多语料库支持**：按场景分库检索
8. **语料规模扩展验证**：压测 5000+ 条 QA 的性能表现
9. **自动调参闭环**：基于线上错样自动推荐阈值调整

## 六、结论

这套 RAG 端侧部署方案是一份**工程成熟度很高的设计**，核心优势在于：

1. **定位精准**：不贪大求全，明确做轻量级垂直 QA 检索，不做系统内推理
2. **端侧深度适配**：从模型选型到部署策略到母盘制作，每个环节都针对 RK3588 做了优化
3. **工程闭环完整**：从 Excel 导入到评测调参到热更新，覆盖了全生命周期
4. **可控性强**：三档置信决策 + Direct Guard + 评测体系，保证「不瞎答」

主要短板在于 BM25 归一化的 false_direct 风险、NPU 适配方案缺失、以及可观测性需要加强。但这些都是**可迭代改进的工程问题**，不影响整体架构的合理性。

**一句话总结：这套方案在端侧垂直 QA 检索场景下是合理且可落地的，工程化程度甚至超过很多商业产品，建议在解决 P0 风险后推进上线。**
