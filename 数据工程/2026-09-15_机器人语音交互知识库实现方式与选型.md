# 机器人语音交互知识库实现方式与选型

> **解决的问题**：机器人语音交互里的知识库，到底有哪些实现方式（FAQ、Wiki、RAG、知识图谱、微调等），按什么条件选、怎么叠，而不是默认上向量 RAG。

语音交互的知识库不是一种技术，而是「用户说完后，系统从哪取事实、敢不敢答、多久开口」。选型由四件事决定：**知识规模与结构、事实刚性、延迟预算、谁来维护**。小而结构化用 Wiki；固定问答用 FAQ 检索；海量非结构化才上混合 RAG；实时数据走 API，不要进知识库。仓库里已有两套验证过的落地：门店导购走两级 Markdown Wiki，垂直 QA 走端侧混合检索。

---

## 一、知识库在语音链路里干什么

级联语音交互的主干是：

```
采音 → ASR → 文本归一化 / ASR 纠错 → 意图分流 → 取知识 → 生成或原文返回 → TTS 约束 → 播报
```

知识库只负责中间的「取知识」。它不替代 ASR，也不替代 TTS。常见翻车是把「大模型会说话」当成「大模型知道事实」——价格、型号、库存、法规一旦编错，比答慢更伤品牌。

语音场景比文本客服多四条硬约束，会直接改写技术选型：

| 约束 | 量化参考 | 对知识库的要求 |
|------|----------|----------------|
| 端到端开口延迟 | 说完到开口目标 &lt;1s（体验锚点见《半身带屏幕仿人机器人语音交互设计方案》） | 高置信命中应跳过 LLM，原文送 TTS |
| ASR 入口脏 | 专业词谐音、口语、相对时间（「这里」「去年」） | 词典纠错、拼音/别名召回必须进检索，不能只靠向量 |
| 事实刚性 | 价格/库存/规格不可幻觉 | 检索不到就拒答或澄清，禁止「编一个差不多的」 |
| 听得下 | TTS 不宜读 Markdown；单轮建议 ≤200 字 | 知识返回要带「口播短答 + 屏幕卡片字段」 |

屏幕在场时，知识库还应同时吐结构化字段（型号、价格、卖点），口播短、屏上细。这不是锦上添花，是嘈杂展厅里「数字听不清」的补救。

## 二、实现方式：按「知识怎么被取出来」分类

名字会过时，机制不会。下面七类按取出方式分，而不是按产品名分。

### 2.1 写进 Prompt 或写进权重：CAG / 微调

**CAG（Cache-Augmented Generation）**：知识量能塞进上下文时，直接把手册或 Wiki 索引放进系统提示，不再检索。

**微调 / LoRA**：把事实写进模型权重。

| | CAG | 微调把知识写进权重 |
|--|-----|-------------------|
| 适合 | 几十页以内、更新不勤的说明书 / 人设 / 话术策略 | 说话风格、领域术语、固定流程，而不是会变的事实 |
| 不适合 | 成百上千文档；频繁改价改规格 | 价格、库存、活动规则 |
| 延迟 | 无检索，但 Prefill 随上下文变长 | 推理本身不变，更新要重训 |
| 语音坑 | 上下文一长，首字延迟立刻破预算 | 改一条事实就要发模型，端侧更难热更新 |

结论：**人设和话术可以进 Prompt；事实不要进权重。** 知识更新走文件或语料包，不走训练。

### 2.2 精确匹配：FAQ / QA 对检索

把「标准问题 + 相似问法 + 标准答案」做成语料。查询归一化后走精确匹配 / BM25 / 轻量向量，**高置信直接返回原文**，不经过生成。

这是展厅、园区、垂直指标问答的主力。仓库对应实现见《端侧RAG语料库检索技术方案》：六路混合召回 + 三档置信（direct / candidates / miss），RK3588 上 UDS 查询可到 5–30ms。

适合：问法可枚举、答案必须原句、规模大约千条以内。  
不适合：开放文档阅读、跨文档综合、「根据这三份材料帮我比较」。

语音增益最大的点是：**命中后零生成**。省掉一轮 LLM，往往就是亚秒开口和破秒的差别。

### 2.3 结构化检索：Markdown Wiki / 表 + 规则

知识本身带属性（价格、人群、场景、标签），用文件或表表达，用规则 / 元数据打分取出，而不是「语义像不像」。

仓库对应实现见《两级Markdown Wiki轻量级知识检索架构》：`index.md` 粗筛 → 单品页按需加载，Frontmatter 打分，介绍 / 推荐两套 Prompt。罗莱门店 21 件产品已上线，明确用来替代向量 RAG。

适合：实体百件级、属性清晰、业务人员要自己改 Markdown、端侧不想挂向量库。  
不适合：千级以上非结构化文档；词表覆盖不到的口语长尾（需轻量语义兜底）。

Wiki 和 FAQ 经常一起用：Wiki 管「这件东西是什么、怎么推」，FAQ 管「营业时间 / 怎么退货」这类固定句。

### 2.4 语义检索：向量 RAG 与混合 RAG

标准流程：文档切块 → Embedding → 向量库召回 →（可选）Rerank → 拼进 Prompt 让 LLM 生成。

纯向量在语音里不够用。专业词、型号、ASR 错字会让「语义像」不等于「事实对」。生产基线是 **BM25（字面）+ 向量（语义）+ Rerank（精排）**。端侧 Embedding 用 bge-small-zh-v1.5 一类小模型时，更要靠混合检索和 Rerank 补短板，原理见同目录 bge 两篇。

| 变体 | 做什么 | 语音上能不能用 |
|------|--------|----------------|
| Pipeline RAG（一次检索 + 生成） | FAQ、手册、政策的单跳问答 | 能，作为长尾层；P95 要把检索+生成一起算进 1s 预算 |
| Agentic RAG（模型多轮决定检索） | 跨文档推理、复杂分析 | 平均 3–8s 量级，不适合作为开口主路径 |
| GraphRAG / KG-RAG | 实体关系、多跳、合规溯源 | 建设成本高；只在关系查询成为主诉求时上 |

适合：文档量大、问法开放、无法为每个问题写 QA 对。  
不适合：小目录导购、必须原文的指标问答、实时库存。

### 2.5 关系检索：知识图谱

把实体和边（产品–配件–故障码–处理步骤）存成图，查询是「沿关系走」，不是「找相似文本」。

适合：运维手册里的多跳（「这个报错换哪个件、有没有替代料」）、合规引用链。  
不适合：通用闲聊、门店导购、百件产品百科——建设周期以月计，维护成本会拖死小团队。

工程原则：**先被向量检索的失败模式证明「问题是关系不是相似」，再建模图。** 不要作为第一版架构。

### 2.6 传统 NLU：意图分类 + 槽位 + 模板

「问天气 / 开灯 / 查库存」这类闭环技能，用规则或小分类模型出意图，槽位填完调 API，模板或 LLM 填话术。

这不是文档知识库，但语音机器人里它往往比 RAG 更先上场：命令、设备控制、业务查询，走技能路由比走检索更稳、更快。意图分类在端侧用 BERT 小模型可到 5–20ms，不必每次调大模型。

### 2.7 外部系统：Tool / API（不要当成知识库）

库存、订单、设备状态、当天活动价，是**状态**不是**知识**。写进向量库当天就会过期。正确做法：意图命中后调业务 API，知识库只放说明书、话术、政策。

## 三、选型决策：四个问题，而不是一张「哪个最好」表

按顺序问，多数项目第一轮就能收窄到一种主路径。

```
① 这是实时状态吗？（库存/订单/开关）
      是 → Tool / API，不要进知识库
      否 ↓
② 实体少、属性清楚、业务要自己改文案？（大约百件内产品/套餐）
      是 → 两级 Wiki + 规则检索
      否 ↓
③ 问法可枚举、答案必须原句？（指标、制度、标准 QA）
      是 → FAQ / QA 检索，高置信原文返回
      否 ↓
④ 文档量大、问法开放、允许「根据资料组织语言」？
      是 → 混合 RAG（BM25 + 向量 + Rerank）
      否 → 先澄清需求；不要上图谱或 Agentic 当默认
```

四个约束把「看起来都能做」的方案拆开：

| 决策维度 | 偏向轻方案（FAQ / Wiki / 规则） | 偏向重方案（混合 RAG / 图谱） |
|----------|-------------------------------|------------------------------|
| 规模 | 百件实体 / 千条 QA | 千份以上非结构化文档 |
| 结构 | 字段、标签、价格、人群 | 长文、混排、扫描件 |
| 事实刚性 | 错一个数字就事故 | 允许综述，但要能引用 |
| 延迟 | 必须亚秒开口 | 可接受「我看看」+ 1–2s |
| 维护者 | 运营改 Markdown / Excel | 需要入库流水线 |
| 算力 | 端侧 RK3588 常驻 | 云端或独立检索服务 |
| 查询形态 | 单跳「这是什么 / 推荐哪个」 | 多跳「A 和 B 什么关系」 |

对照表（语音机器人常用项）：

| 方式 | 延迟量级 | 事实可控 | 维护成本 | 语音主路径 |
|------|----------|----------|----------|------------|
| 命令 / 意图 + API | 毫秒～百毫秒 | 高（以系统为准） | 中（对接业务） | 控制与查询技能 |
| FAQ 原文返回 | 5–50ms（端侧内存索引） | 最高 | 低（Excel / 表） | 高频标准问 |
| Markdown Wiki | 毫秒级 IO + 短生成 | 高 | 低（Git + 文件） | 小目录导购 |
| CAG / 塞上下文 | 取决于上下文长度 | 中 | 低 | 仅极小知识 |
| 混合 RAG | 检索 50–250ms + LLM 生成 | 中（靠引用与拒答） | 中高 | 长尾文档 |
| Agentic RAG | 数秒 | 中高 | 高 | 不要做开口主路径 |
| 知识图谱 | 数百毫秒～数秒 | 高（边可审计） | 很高 | 关系密集型垂直域 |
| 微调灌事实 | 无检索 | 差（难改、易过时） | 极高 | 不建议 |

「RAG」这个词在工程里至少要拆成三种：QA 检索（可不生成）、文档 RAG（检索 + 生成）、Agentic RAG（多步）。口头说「我们上 RAG」而不声明哪一种，后面延迟和幻觉指标会对不上。

## 四、生产形态：分层叠路，而不是赌一种技术

门店、展厅、园区机器人几乎从不会只有一种问法。稳定做法是**快轨保体验、精轨保覆盖**：

```
用户话术（ASR 后）
    │
    ├─ 技能 / API          开灯、查库存、查订单
    ├─ FAQ 精确命中        营业时间、怎么退货、固定指标
    ├─ Wiki 属性匹配       推荐哪款、这款什么材质
    ├─ 混合 RAG            手册、政策、长尾说明
    └─ 闲聊 / 拒答         没有知识就短拒答，不编
```

分流尽量用规则或小模型，不要每轮先调一次大模型做路由——那会把知识库的延迟预算吃掉。Wiki 文里「介绍 / 推荐 / 闲聊」三路规则分流，和 FAQ 方案里的规则意图，是同一原则。

置信策略建议统一成三档，和端侧 RAG 方案对齐：

| 档 | 行为 | 语音表现 |
|----|------|----------|
| 高置信 | 原文或锁定实体后短生成 | 直接开口，可跳过 LLM |
| 中置信 | 返回候选或追问 | 「您是问 A 还是 B？」；屏上出选项 |
| 低置信 | miss | 短拒答 + 引导换问法，禁止自由发挥 |

中置信窗口不要设得过窄（例如 0.88–0.90）。窗口太窄会在「瞎答」和「什么都不答」两极跳，语音上比文本客服更难受。

### 按场景的推荐组合

| 场景 | 主路径 | 辅路径 | 不要先做 |
|------|--------|--------|----------|
| 门店导购（SKU 少、属性清） | 两级 Wiki + 意图分流 | 高频 FAQ；规则未命中再轻量向量 | 一上来 Milvus + 切块 RAG |
| 展厅 / 园区指标问答 | FAQ 混合检索，原文返回 | 未命中交云端 LLM + 拒答 | 端侧大模型现场编数字 |
| 产品手册 / 政策长尾 | 混合 RAG | 高频问沉淀成 FAQ | Agentic 当默认 |
| 设备运维多跳 | 先 FAQ + 手册 RAG | 失败模式稳定后再上图谱 | 第一期就建全量本体 |
| 带屏幕的半身机器人 | 任何一层都返回「口播短文本 + 卡片字段」 | 数字、价格走屏幕 | 只优化长口播 |

端云分工可以很简单：端侧放 FAQ / Wiki / 小 Embedding（离线、亚秒）；云端放长尾 RAG 和 LLM。离线包热更新、命中声明回流，见《RAG数据飞轮-从实验品到技术壁垒》。

## 五、语音链路里必须和知识库一起设计的配套

知识库单独做对，接上麦克风仍会「听不懂 / 答得慢 / 读出星号」。下面几件要同期设计。

**1. 领域词典是知识库的入口，不是 ASR 的私货。**  
产品名、地名、故障码要同时出现在：ASR 热词、检索别名表、Wiki 标签 / FAQ 标准问。只改一处，另外两处会系统性漏召回。《端侧RAG语料库检索技术方案》里的 `domain_lexicon.yaml`（canonical / aliases / asr_errors / pinyin）应视为知识资产。

**2. 流式 ASR 可以预热检索，但不能预热作答。**  
partial 文本可提前召回候选，final 文本再决策。中间误识别直接播出去，比慢半拍更糟。

**3. 生成必须服从 TTS。**  
禁止 Markdown、禁止「根据资料显示」、推荐 1–2 款而不是报菜单。有屏幕就把规格放到卡片上，口播只留结论和一句卖点。

**4. 多轮要有会话状态。**  
「刚才那个太贵了」依赖 `last_recommended_products`，纯检索做不到。Wiki 的已知局限正在这里，要用 Session，而不是再切一层向量。

**5. 评测集要按「语音问法」建，不要只按标准书面问。**  
至少覆盖：标准问、口语、ASR 错字、相对时间地点、无关负例。指标优先级建议：`false_direct = 0`（高置信绝不答错）> Top3 不回退 > Top1 提升 > 负例拒识。

## 六、常见翻车

1. **百件产品上向量 RAG。** 语义相似 ≠ 属性匹配，「颈椎不好」可能召到普通护颈枕而不是牵引枕。小目录用 Wiki。
2. **把库存、当日价写入向量库。** 状态走 API；知识库只放说明书。
3. **用微调当知识更新通道。** 改价要发模型，端侧无法热更新。
4. **Agentic RAG 当语音主路径。** 多轮检索的准确率更高，但秒级延迟会把「亚秒开口」打穿；需要时放在用户已等待、或屏幕已进入「我查一下」之后。
5. **只检索不拒答。** 语音幻觉比文字更难撤回。三档置信和 Direct Guard（分差、槽位冲突、对比问强制候选）是底线。
6. **忽略 ASR 错字，只调 Embedding。** 谐音问题用词典和拼音通道，比换更大的向量模型有效。
7. **一层知识通吃闲聊、导购、控制。** 闲聊走人设 Prompt，控制走技能，导购走 Wiki/FAQ，混在一个 Prompt 里会又慢又油。

## 七、落地顺序（避免一次性上全套）

| 阶段 | 做什么 | 验收 |
|------|--------|------|
| 第一期 | 意图分流 + FAQ 或 Wiki（按上面决策树二选一）+ 拒答话术 + TTS 长度约束 | 高频 20 问口播正确；错答率为 0 |
| 第二期 | 领域词典接入 ASR；混合检索补长尾；屏上卡片字段 | ASR 错字问法 Top3 可接受；P95 开口仍在预算内 |
| 第三期 | 未命中聚类回流、语料热更新（数据飞轮） | 周维度补齐高频 miss，不再纯靠改代码提点 |
| 按需 | 图谱 / Agentic / 领域 Embedding 微调 | 有稳定失败模式再加，不当默认架构 |

第一期刻意不做向量库，不是保守，是先把「敢答 / 拒答 / 开口时间」三条体验锚点钉死。向量层是覆盖率工具，不是正确性工具。
