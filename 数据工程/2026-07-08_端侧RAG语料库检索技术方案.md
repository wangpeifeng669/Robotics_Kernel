# 端侧RAG语料库检索技术方案

> 面向 RK3588 边缘设备的轻量级垂直领域 QA 检索引擎，采用混合检索 + 三档置信决策 + 流式 ASR 预热架构，不引入大模型推理，以低延迟、高可控为核心工程目标。

## 一、背景与定位

本方案面向鲁班猫 RK3588（ARM64 / Ubuntu 22.04 / ≥4GB 内存）上的垂直领域本地问答检索场景，为板内模块和局域网其他设备提供低延迟、高命中率的 QA 检索服务。

### 1.1 核心约束

| 约束项 | 详情 |
|--------|------|
| 硬件 | RK3588，ARM64，建议 ≥4GB 内存 |
| 语料 | Excel 格式问答对（标准问题 / 相似问题 / 答案），单份 ≤1000 条 |
| 通信 | TCP 供局域网调用 + UDS 供板内模块低延迟调用 |
| 能力边界 | 语义对齐与检索增强，不做系统内推导/计算，答案只来自语料原文 |

### 1.2 为什么不做重型 RAG

```
RK3588 算力有限 → 不适合重型生成链路
数据规模 ≤1000 条 → 索引可全量内存化，无需 Elasticsearch/Redis/Milvus
垂直领域特征 → 专业词、实体、上下文准确性比语义泛化更重要
答案可靠性 → 语料原文返回优于大模型自由生成
```

## 二、总体架构

系统分为调用层、服务层、检索推理层、数据层四层，单进程运行。

```
调用层         TCP Server (0.0.0.0:18080)  │  UDS Server (/tmp/qa_rag.sock)
─────────────────────────────────────────────
服务层         Query API │ ASR Preheat API │ ASR Final API │ Reload API │ Health API
─────────────────────────────────────────────
检索推理层     Normalizer → ASR Corrector → Context Resolver
               → Hybrid Retriever (6路召回) → Reranker → Decision Engine → Answer Composer
─────────────────────────────────────────────
数据层         QA Metadata │ BM25 Index │ Vector Index │ Domain Lexicon │ Runtime Cache
```

推荐进程形态为单进程 + 协程 + 检索 Worker 池 + 异步日志。

## 三、数据模型

### 3.1 Excel 到内部结构

语料 Excel 三列：`标准问题` / `相似问题` / `答案`。导入后转换为内部结构：

```json
{
  "question_id": "q_000001",
  "standard_question": "北部湾2025年的销量是多少",
  "similar_questions": ["北部湾去年卖了多少", "这里2025年的销量是多少"],
  "answer": "北部湾2025年的销量为1200台。",
  "location": "北部湾",
  "year": 2025,
  "tags": ["销量"],
  "domain_terms": ["北部湾", "销量"],
  "structured_answer": { "sales_volume": 1200, "unit": "台" },
  "enabled": true,
  "corpus_version": "2026-04-26-001"
}
```

每个标准问题和相似问题都作为独立索引文本，最终以 `question_id` 聚合同一 QA 的多个命中。

### 3.2 索引体系

启动时全量加载到内存，不依赖外部数据库。

```
IndexedText (标准问题) → question_id
IndexedText (相似问题) → question_id
答案摘要（可选） → question_id
专业词扩展文本 → question_id
```

## 四、查询处理流水线

完整查询链路：

```
输入 query
  → 文本归一化（全角转半角、中数转阿数、口语规范化）
  → ASR 专业词纠错（别名替换、拼音匹配、缩写扩展）
  → 时间地点上下文补全（"这里"→"北部湾"，"去年"→"2025年"）
  → 生成多个检索 query（原始 + 纠错 + 补全，去重）
  → Exact / Alias / BM25 / Vector / Pinyin / Slot 六路并行召回
  → 候选融合去重（以 question_id 为聚合键）
  → Reranker 重排（仅对 Top10，可选）
  → 融合打分
  → 置信度决策
  → 返回 direct / candidates / miss
```

### 4.1 文本归一化

轻量规则归一化，不依赖 NER 模型：

- 全角→半角、英文→小写
- 中文数字→阿拉伯数字（二零二五→2025）
- 年份格式统一、标点和空格清洗
- 英文缩写规范化
- 常见口语规范化（卖了多少→销量是多少）

### 4.2 ASR 专业词纠错

依赖独立领域词典文件 `domain_lexicon.yaml`，结构：

```yaml
terms:
  - canonical: "北部湾"
    aliases: ["北部弯", "北部完"]
    asr_errors: ["背部湾", "北部玩"]
    pinyin: "bei bu wan"
    term_type: "location"
    weight: 1.0
  - canonical: "自动化岸桥"
    aliases: ["自动岸桥"]
    asr_errors: ["自动化按桥"]
    abbrs: ["ASC"]
    pinyin: "zi dong hua an qiao"
    term_type: "product"
    weight: 1.0
```

关键纠错策略：高置信纠错可替换原 query；不确定纠错不覆盖原 query，而是生成候选 query 并行检索，原始 query 始终保留。

### 4.3 时间与地点上下文解析

请求方传入 `context`：

```json
{
  "context": {
    "location": "北部湾",
    "current_date": "2026-05-04"
  }
}
```

支持相对表达解析：

| 输入 | 解析结果 |
|------|---------|
| 这里 | → 北部湾（来自 context.location） |
| 去年 | → 2025年（基于 current_date） |
| 上个月 | → 2026年4月 |
| 去年同期 | → 2025年同期 |

时间和地点解析优先使用规则和词典实现，不依赖大模型。

## 五、混合检索设计

### 5.1 为什么不用纯向量检索

- 专业词和实体精确性要求高，向量语义容易漂移
- ASR 错字、谐音字会影响向量语义质量
- 时间、地点、指标类问题需要严格槽位匹配
- 千级 QA 数据中关键词匹配价值极高

因此采用六路混合召回，多路信号叠加，谁该信多一点由配置权重和决策阈值调节。

### 5.2 六路召回通道

| 通道 | 说明 | 权重 |
|------|------|------|
| Exact Match | 归一化后全文精确匹配 | Boost 0.15 |
| Alias Match | 别名、专业词替换命中 | 0.08 |
| BM25 | jieba 分词后关键词召回 | 0.35 |
| Vector Search | bge-small-zh-v1.5 语义向量召回 | 0.45 |
| Pinyin Match | 拼音相似度匹配（仅领域词表） | 0.06 |
| Slot Match | 时间、地点、指标槽位一致性 | 0.06 |

融合公式：

```
base_score = Σ(normalized_weight_i × score_i)
final_score = min(1.0, base_score + exact_match_boost × exact_score + context_boost × context_score)
```

### 5.3 候选融合规则

以 `question_id` 为聚合键，各路分数取该路最大值；最终保留 `final_score` 贡献最大的 matched_text。同一 QA 的多条相似问题间去重。

## 六、置信度决策策略

系统根据 `final_score` 三类返回，并设有 Direct Guard 保护：

### 6.1 三档决策

```
高置信 (final_score ≥ 0.90) → mode = "direct" → 直接返回答案
中置信 (0.88 ≤ final_score < 0.90) → mode = "candidates" → 返回 Top3 候选
低置信 (final_score < 0.88) → mode = "miss" → 返回失败原因
```

### 6.2 Direct Guard

即使 `final_score ≥ 0.90`，也必须同时满足以下条件才能 `direct`：

```
top1_vector_score ≥ 0.90         (语义分足够高)
top1_score - top2_score ≥ 0.03   (与第二名拉开差距)
不存在槽位冲突                     (地点/年份不矛盾)
非 comparison_query 意图           (对比类问题强制 candidates)
```

初期建议阈值设置保守，宁可多返回 Top3，也要降低高置信误命中的概率。

## 七、流式 ASR 预热设计

### 7.1 核心思路

在 ASR 识别的过程中，利用未完成的 partial text 提前召回可能答案，用 `request_id` 关联预热缓存与最终查询，降低最终响应延迟。

### 7.2 预热策略

| 条件 | 行为 |
|------|------|
| partial_query < 4 个中文字符 | 不触发预热 |
| 相邻 partial 间隔 < 100ms | 不重复预热 |
| 文本变化 < 2 个字符 | 复用上次候选 |
| 缓存 TTL | 5-10 秒 |

预热结果只作为加速依据，不能直接作为最终答案返回。

### 7.3 最终 ASR 查询

最终 ASR 输出后调用 `ASR Final API`：

```
final_asr_query
  → 读取同一 request_id 预热候选
  → 最终文本归一化、纠错、上下文补全
  → 优先在预热候选中 rerank
  → 预热不足时补充完整检索
  → 重新置信度决策
  → 返回结果（带 source 字段：preheat_rerank / full_retrieval / no_preheat）
```

这样设计确保中间 ASR 误识别不会最终污染答案。

## 八、接口协议

### 8.1 协议约定

TCP 和 UDS 使用同一套 JSON Line 协议：每个请求/响应一行 JSON，以 `\n` 结尾，UTF-8 编码，单请求最大 64KB。

支持五类请求类型：

| type | 说明 |
|------|------|
| query | 普通查询 |
| health | 健康检查 |
| stats | 运行统计 |
| reload_corpus | 远程下载并热替换语料 |
| (预留) asr_preheat / asr_final | 流式 ASR |

### 8.2 Query 请求示例

```json
{
  "version": "1.0",
  "request_id": "req_001",
  "type": "query",
  "query": "这里去年的销量是多少",
  "context": { "location": "北部湾", "current_date": "2026-05-04" },
  "options": { "top_k": 3, "need_trace": false }
}
```

### 8.3 三类响应

**direct（高置信直接返回）：**
```json
{
  "status": "hit", "mode": "direct",
  "score": 0.93, "question_id": "q_000001",
  "standard_question": "北部湾2025年的销量是多少",
  "answer": "北部湾2025年的销量为1200台。"
}
```

**candidates（中置信返回候选）：**
```json
{
  "status": "hit", "mode": "candidates",
  "candidates": [{
    "question_id": "q_000001", "score": 0.89,
    "standard_question": "北部湾2025年的销量是多少",
    "answer": "北部湾2025年的销量为1200台。",
    "matched_text": "北部湾2025销量多少",
    "matched_type": "similar_question"
  }]
}
```

**miss（低置信失败）：**
```json
{
  "status": "miss", "score": 0.41,
  "reason": "low_confidence"
}
```

### 8.4 协议演进策略

```
第一阶段：JSON（快速联调）
第二阶段：JSON + version 字段固化协议
第三阶段：根据性能数据评估 MessagePack / protobuf 切换
```

调用方应忽略不认识的新增字段，保证向后兼容。

## 九、技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 开发语言 | Python 3.12+ | 千级 QA 可全量内存化，性能满足 |
| 通信协议 | JSON Line | 可读性强，便于联调；后续可换 MessagePack |
| 关键词召回 | BM25 + jieba | 对专业词和实体精确召回 |
| Embedding 主模型 | bge-small-zh-v1.5 | 体积小，适合 RK3588 部署 |
| Embedding 备用 | bge-base-zh-v1.5 | 语义表达更强，需实测后决定 |
| Reranker | bge-reranker-base (ONNX 可选) | 仅对 Top10 重排，支持超时保护 |
| 意图分类 | 规则匹配 | 不调用大模型，延迟 < 1ms |
| 数据存储 | 内存 + SQLite + 本地索引文件 | 不引入重型组件 |
| 服务管理 | systemd | 标准化运维 |

## 十、部署方案

### 10.1 文件布局

```
/opt/qa-rag/
  ├── bin/
  ├── config/
  ├── data/
  │   ├── corpus.xlsx          # 语料 Excel
  │   ├── qa.db                # 元数据
  │   ├── bm25.index           # BM25 索引
  │   ├── vector.index         # 向量索引
  │   └── lexicon.json         # 领域词典
  ├── models/
  │   ├── bge-small-zh-v1.5/
  │   └── bge-base-zh-v1.5/
  ├── logs/
  └── run/
      └── qa_rag.sock
```

### 10.2 启动流程

```
加载配置 → 加载领域词典 → 加载 QA 元数据 → 校验语料
→ 构建 BM25 索引 → 加载 Embedding 模型 → 构建向量索引
→ 初始化 Reranker / IntentClassifier
→ 启动 TCP Server → 启动 UDS Server → 启动健康检查
```

### 10.3 部署策略

- CPU 基线先行：先用 CPU 版本跑通功能验证和效果评测
- ONNX 精简部署：模型 ONNX 化后降低推理延迟和内存占用
- 母盘镜像：制作系统母盘，预装全部依赖和模型
- deb 增量更新：后续通过 deb 包增量更新服务二进制和配置

后续 NPU 版本上线前，必须使用同一份语料、评测集和阈值配置进行 A/B 对比，确认效果不回退。

## 十一、分阶段实施计划

| 阶段 | 目标 | 核心交付 |
|------|------|---------|
| **第一阶段** 基础闭环 | 可用、可测试、可部署的基础检索服务 | Excel 导入 + BM25 + 向量召回 + TCP/UDS + 三档决策 + 评测脚本 |
| **第二阶段** 命中率增强 | 提升垂直领域和 ASR 场景命中率 | 领域词典 + 别名/拼音纠错 + 上下文补全 + 多 query 扩展 + 阈值调参 |
| **第三阶段** 语义增强 | 提升语义等价问法覆盖率，不引入推理计算 | 意图分类 + Reranker + Answer Composer + 结构化证据输出 + bge-base 对比评测 |
| **第四阶段** 工程化 | 适配真实设备链路 | ASR 预热/最终 API + request_id 候选缓存 + 语料热更新 + systemd + 性能压测 |

阶段之间解耦设计：每阶段独立验收，后一阶段代码不破坏前一阶段基线。

## 十二、性能目标

在 1000 条 QA、约 3000 条索引文本的规模下：

| 指标 | 目标值 |
|------|--------|
| UDS 查询延迟 | 5ms ~ 30ms |
| TCP 查询延迟 | 10ms ~ 50ms |
| 带 Reranker 延迟 | 30ms ~ 150ms |
| ASR 预热后最终响应 | 10ms ~ 50ms |
| 服务启动时间 | < 25s（不含首次模型下载） |
| 内存占用 | 500MB ~ 2.2GB（取决于 Reranker 是否启用） |

优化措施：启动全量加载索引到内存、QA embedding 离线预计算、query embedding 模型常驻内存、Reranker 只对 Top10 执行、预热候选缓存按 request_id 管理、日志异步写入、长连接复用。

## 十三、评测体系

### 13.1 测试集构建

每条标准问题至少构建以下维度的测试样本：

| 维度 | 示例 |
|------|------|
| 标准问法 | 北部湾2025年的销量是多少 |
| 相似问法 | 北部湾2025销量多少 |
| ASR 错字 | 北部弯二零二五年卖了多少 |
| 时间替换 | 这里去年的销量是多少（需上下文） |
| 地点上下文 | 这里2025年的销量是多少（需补全"北部湾"） |
| 语义等价 | 北部湾2025年的销售量是多少 |
| 无关问题（负例） | 北京2025年的销量是多少 |

### 13.2 核心指标

```
Top1 命中率 / Top3 命中率
误命中率 (false_direct_count)
漏命中率
高置信准确率 / 中置信可用率 / 低置信拒识准确率
P95 / P99 延迟
内存占用 / CPU 占用
分组指标（alias / asr_error / pinyin / time_context / location_context）
阈值敏感性分析
```

调参目标优先级：`false_direct_count = 0 > 正例 Top3 不回退 > 正例 Top1 尽量提升 > 负例 miss 尽量提升`。

每次查询记录结构化日志，字段覆盖：

```json
{
  "request_id": "req_001",
  "query": "这里去年的销量是多少",
  "normalized_query": "北部湾2025年的销量是多少",
  "expanded_query_count": 3,
  "expanded_sources": ["original", "time_resolved", "context_resolved"],
  "context": { "location": "北部湾", "current_date": "2026-05-04" },
  "intent": "spatial_query",
  "reranked": true,
  "status": "hit", "mode": "direct",
  "top_score": 0.93, "question_id": "q_000001",
  "latency_ms": 38.7, "candidate_count": 5,
  "score_profile": {
    "top_final": [0.93, 0.81, 0.77],
    "top_bm25": [1.0, 0.72, 0.66],
    "top_vector": [0.91, 0.82, 0.80],
    "top_reranker": [0.93, 0.70, 0.72]

```

日志用途：分析 ASR 错误类型、优化领域词典、调整阈值、定位误命中、回放评测、统计高频问题、评估预热命中率。

## 十五、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| ASR 专业词误识别 | 漏召回 | 建设领域词典 + 别名表 + 拼音匹配 + 日志回放机制 |
| 实体错误导致误命中 | 返回错误答案 | 时间/地点/指标槽位参与打分，关键槽位不一致强制降权 |
| 纠错误替换 | false_direct | 原始 query 始终保留，Direct Guard 检查 vector_score + margin + 槽位冲突 |
| 上下文缺失导致臆造补全 | 返回错误上下文 | 无上下文不补全，返回 miss/candidates，日志记录 context_missing_count |
| Reranker 延迟过高 | P95 超标 | trigger_mode=medium_only，减少触发频率；ONNX + 量化降低延迟 |
| bge-base + Reranker 同时加载 OOM | 服务不可用 | 逐次评测，按需加载；ONNX 量化版本降低内存 |

## 十六、设计原则总结

> **不做系统内推理，答案只来自语料原文。** 高置信直接返回，中置信交外部大模型处理，低置信诚实 miss。这是端侧约束下的理性取舍 —— 以低延迟、高可控、可调参、可回放、易集成为核心工程目标，而非追求大而全的语义理解。
