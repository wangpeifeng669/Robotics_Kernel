# 两级Markdown Wiki轻量级知识检索架构

**核心摘要**：针对小规模产品知识库（百件以内）的推荐与问答场景，提出一套以"两级 Markdown Wiki + 规则检索 + 意图分流"为核心的轻量级知识架构，彻底替代向量化 RAG。通过 index 层粗筛 + 单品页按需加载、Frontmatter 元数据打分、Prompt 级话术策略分离等手段，实现完全可追溯、零外部依赖、LLM 原生友好的确定性检索。该模式与 OpenClaw/WorkBuddy 的文件系统驱动 Agent 架构同源，本质是"渐进式上下文加载"思想在领域知识检索中的工程落地。

---

## 一、问题背景：为什么小型知识库不适用传统 RAG

传统 RAG（检索增强生成）的标准范式是：文档 → Embedding 向量化 → 向量数据库 → 语义检索 Top-K → 拼接 LLM Prompt。这套流程在**海量非结构化文档**场景下价值巨大，但在以下场景却显得臃肿且不可靠：

| 场景特征 | RAG 的痛点 |
|----------|-----------|
| 产品实体量小（21 件） | 向量检索精度过剩，但语义相似 ≠ 属性匹配（如"颈椎不好"可能召回到普通护颈枕而非专门的牵引枕） |
| 推荐逻辑依赖结构化属性（价格 / 人群 / 场景） | 向量检索无法表达"价格 < 500 且 适合男士"这类结构化约束 |
| 语音交互终端（机器人） | 需要极低延迟、且回复必须锚定事实（价格/型号不可编造） |
| 导购需要营销话术与客观介绍两套话术 | 单一 RAG 的"检索 → 生成"流水线无法按意图切换生成策略 |
| 业务人员需要维护产品信息 | 向量数据库不可直接读改，而 Markdown 文件谁都能编辑 |

**核心矛盾**：RAG 用"语义模糊匹配"去解决一个本质上是"结构化属性匹配 + 策略化话术生成"的问题，用错了工具。

---

## 二、架构总览

新架构的核心思路是：**把知识库本身变成检索索引**，用文件系统代替数据库，用 Frontmatter 元数据代替向量。

```
顾客提问
    │
    ▼
┌──────────────────────┐
│ 意图分流（规则匹配）   │  ← 纯规则，不调 LLM
│ 闲聊 / 介绍 / 推荐   │
└──────┬───────────────┘
       │
       ├── 闲聊 ──→ 闲聊人设 Prompt
       │
       ├── 介绍 ──→ 产品名精准匹配 ──→ 加载单品页 ──→ 客观介绍 Prompt
       │
       └── 推荐 ──→ 规则多策略打分 ──→ 锁定 1~2 款 ──→ 加载单品页 ──→ 导购推荐 Prompt
                           │
                           ▼
              ┌─────────────────────┐
              │  Wiki 知识库（本地文件） │
              │  index.md（总览索引）   │
              │  products/*.md（单品页）│
              │  concepts/*.md（概念页）│
              └─────────────────────┘
```

**两级加载机制**：

- **第一级 — index.md（主索引/快照）**：包含全部产品的型号、价格、痛点标签、营销卖点。意图识别和初次匹配时只加载这一层，体积小，Token 消耗极低。
- **第二级 — products/*.md（单品详情）**：带完整参数、材质、规格、图片链接。只有锁定了具体产品后才按需加载，实现 Lazy Loading。

这与数据库中的**二级索引**（索引页 → 数据页）和推荐系统中的**召回 → 精排**思想一脉相承，只不过载体从数据库变成了 Markdown 文件。

## 三、核心设计决策

### 3.1 去向量化：规则检索替代语义检索

检索评分策略（按权重叠加，各策略命中原因完全可追溯）：

| 策略 | 权重 | 说明 |
|------|------|------|
| 产品名精准匹配 | +100 | 长名优先，如"棉花糖高低枕 Pro"优先于"棉花糖高低枕" |
| 分类词命中 | +20 | 枕头/床垫/坐垫等类别词 |
| 标签命中 | +10 | 需求词 → 标签映射，如"颈椎"→"护颈"、"租房"→"卷装便携" |
| 正文关键词命中 | +5 | 需求词出现在产品正文中 |
| 正文原词命中 | +8 | 用户原句直接出现在正文中 |

排序规则：得分降序 → 主推款优先 → 价格升序，截取 Top-K（默认 6）供 LLM 上下文。

需求词映射表负责将用户口语映射到产品标签，覆盖六大维度：

| 维度 | 用户口语示例 | 映射标签 |
|------|-------------|----------|
| 身体部位 | 颈椎/脖子/落枕/低头/伏案 | 护颈、颈椎牵引 |
| 体感 | 凉/热/夏天/清爽 | 凉感透气、凝胶 |
| 功能 | 抗菌/螨/过敏/水洗/拆洗 | 抗菌防螨、可水洗 |
| 人群 | 送/礼物/长辈/男士/女士/小孩 | 送礼、男士、女士、青少年 |
| 场景 | 租房/搬家/宿舍/临时 | 卷装便携 |
| 预算 | 性价比/便宜 | 性价比 |

**关键优势**：规则检索的命中原因对调试完全透明（"为什么推荐 A 而不是 B"可以精确到哪个词命中了哪个标签），而向量检索是黑盒。

### 3.2 意图分流：纯规则分类，不调 LLM

意图分类采用规则匹配而非 LLM 调用，理由很直接——这个场景的分类边界足够清晰：

| 输入特征 | 判定意图 | 示例 |
|----------|---------|------|
| 含产品名 | 产品介绍 | "云朵护颈枕怎么样" |
| 命中推荐/购买/需求/人群/场景词 | 产品推荐 | "我颈椎不好，推荐个枕头" |
| 纯礼貌短句（≤12 字且无产品词） | 闲聊 | "谢谢"、"好的" |
| 其余 | 闲聊 | "今天天气不错" |

**工程收益**：每次对话节省一次 LLM 调用，延迟和成本趋近于零。代价是词表需要维护——但相比 LLM 意图分类的幻觉风险，这个代价可接受。

### 3.3 话术策略分离：介绍 vs 推荐两套 Prompt

这是该架构中一个容易被忽视但体验影响巨大的设计：

- **介绍模式 Prompt**："你是专业产品百科，用客观简洁的语言回答功能、尺寸、价格，不夸大推销。"
- **推荐模式 Prompt**："你是资深导购，结合顾客痛点从推荐列表中选 1~2 款，强调产品如何解决其痛点，语气亲和有感染力。"

避免了传统 RAG 中"一个 Prompt 既要讲事实又要做推销"导致的逻辑混淆和话术生硬。

### 3.4 单源真理：build.py 自动编译，消除数据冗余

产品信息分散在总览文件和单品文件中，若人工维护两份数据，价格变更时必然出现不一致。

解决方案：**总览文件绝不人工维护**。产品手册是唯一数据源，`build.py` 脚本负责：
1. 解析产品手册（按标题层级切分章节与产品实体）
2. 逐行提取字段（型号/材质/卖点/规格/价格）
3. 从卖点文本中**规则匹配自动提取标签**
4. 生成单品页（Frontmatter + 正文 + 关联产品 wikilinks）和 index.md

```
产品手册.md（唯一数据源）
       │
       ▼
   build.py（解析 + 提取 + 标签生成）
       │
       ├──→ index.md（总览索引，自动生成）
       └──→ products/*.md（21 个单品页，自动生成）
```

### 3.5 TTS 适配：为语音交互终端定制的生成约束

这是门店机器人场景特有的需求，但设计思想具有通用性——**生成格式必须适配输出介质**：

| 约束 | 理由 |
|------|------|
| 禁止 Markdown 标记（`**`、`#`、数字列表） | 语音合成器会读出星号和井号 |
| 禁止括号旁白（"根据资料……""检索到……"） | 语音播报中元描述语破坏对话自然感 |
| 限制回复 ≤ 200 字 | 语音信息密度有限，用户"听"记不住长文本 |
| 推荐 1~2 款而非 3 款 | 避免价格/型号连续播报造成的听觉疲劳 |

## 四、与向量化 RAG 的系统对比

| 维度 | 传统向量化 RAG | 两级 Markdown Wiki 架构 |
|------|---------------|------------------------|
| 检索方式 | 语义向量相似度 | 规则 + 关键词 + Frontmatter 打分 |
| 外部依赖 | Embedding 模型 + 向量数据库 | 零外部依赖，文件系统即数据库 |
| 命中可解释性 | 黑盒（"语义相似"） | 白盒（可精确追溯命中词/标签） |
| 结构化约束 | 不支持（无法过滤价格/人群） | 原生支持（Frontmatter 元数据字段匹配） |
| 数据维护 | 需专业工具 | Markdown 文件，业务人员可直接编辑 |
| 版本控制 | 需单独方案 | 原生 Git 版本控制 |
| Token 效率 | 一次加载全部检索结果 | 两级按需加载，仅加载相关页面 |
| 延迟 | Embedding 推理 + 向量检索 | 本地文件 IO，毫秒级 |
| 适用规模 | 千级以上的非结构化文档 | 百件以内、结构化属性丰富的场景 |
| 话术策略 | 单一 Prompt 覆盖所有场景 | 介绍 / 推荐两套 Prompt，按意图切换 |

## 五、与 OpenClaw/WorkBuddy 文件系统架构的同源性

Gemini 在评测中明确指出，该架构与 OpenClaw（小龙虾）的 Skill/Wiki 管理模式**原理完全同源**，都遵循"基于文件系统的轻量级渐进式上下文加载（Progressive Context Disclosure）"思想。

两者的共性：

| 设计元素 | 罗莱 Wiki 架构 | OpenClaw / WorkBuddy |
|----------|---------------|---------------------|
| 总览层 | index.md（产品名+标签+价格索引） | SKILL.md 的 description/tags + INDEX.md |
| 详情层 | products/*.md（按需加载单品详情） | SKILL.md 正文 + references/ 目录 |
| 元数据驱动 | YAML Frontmatter（分类/价格/标签/材料） | YAML Frontmatter（name/version/permissions/tags） |
| 触发条件 | 规则词表匹配（命中产品名/需求词） | 意图匹配（命中 description/tags 中的场景描述） |
| 加载策略 | 先匹配 index → 再加载单品页 | 先匹配 Skill Directory → 再加载 SKILL.md |

**共同的工程哲学**：
1. **文件即数据库**：告别向量数据库和专用存储，Markdown + YAML 是人、LLM、Git 三者都能直接操作的通用载体。
2. **LLM-Native**：大模型对 Markdown 语法（标题 `#`、列表 `-`、Frontmatter `---`）有天然的理解和解析能力，无需额外的序列化/反序列化。
3. **透明可控**：知识和规则以纯文本呈现，可读、可测、可审计、可版本对比。
4. **按需加载**：不一次性塞入全部上下文，而是渐进式地加载必要信息，最大化 Token 利用效率。

## 六、适用边界与局限性

### 适用场景

- 产品/实体数量在百件以内
- 实体属性结构化程度高（有明确的分类、价格、适用人群、功能标签）
- 需要多策略话术（介绍 vs 推荐 vs 对比）
- 运行在端侧/离线环境，无法部署外部数据库
- 业务人员需要直接参与知识维护

### 不适用场景

- 海量非结构化文档（千级以上），标签体系无法覆盖 → 此时向量化 RAG 仍是首选
- 需要跨文档的深度语义推理（如"哪些产品符合某种潜在趋势"）
- 用户输入高度口语化、错别字频发、且无法建立完备的词表映射 → 需要轻量语义模型兜底

### 已知局限性

1. **语义空白**：如"睡眠浅"这类非直接需求词，若未编入词表则无法命中——需持续扩展映射表，或在规则未命中后引入轻量 Embedding 模型作为二级召回。
2. **词表维护成本**：新增产品若引入新标签（如"电动"），需在 build.py 的标签规则和词表映射中同时登记。
3. **单轮推荐**：目前缺少多轮推荐状态跟踪（如"刚才那个太贵了，有没有便宜的"），需在 Session State 中维护 `last_recommended_products` 上下文。

## 七、总结

这套"两级 Markdown Wiki + 意图分流 + 规则检索"架构，本质上是对"小数据场景下过度工程化"的一次纠偏。它用三个简单的工程决策——**去向量化**（规则替代语义检索）、**两级加载**（索引页→详情页 Lazy Loading）、**策略分离**（介绍/推荐两套 Prompt）——换来了可解释性、零外部依赖、低延迟和业务可维护性。

更深一层看，这套架构与 OpenClaw/WorkBuddy 的 Skill 系统共享同一个核心思想：**把知识结构化地写进文件系统，让文件既服务于人类阅读，也服务于 LLM 的渐进式上下文加载**。在这个范式下，RAG 不再是唯一答案——很多时候，一个精心设计的 Markdown 目录树比一个向量数据库更实用。
