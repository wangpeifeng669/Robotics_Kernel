# RK3588 大小核与 CPU 绑定：为什么不绑核会抖动

**核心摘要**：RK3588 一共 8 个 CPU 核，分两类：4 个 Cortex-A76 大核（板子锁 2.352 GHz）+ 4 个 Cortex-A55 小核（锁 1.8 GHz），大核单核性能约为小核的 1.5～2 倍。不做绑核时，Linux 调度器会让同一个线程在大小核之间来回迁移：算力跳变、缓存跨簇失效、目标核排队，三样叠加使同样的任务一帧快一帧慢，这就是抖动。对实时语音链路，抖动会击穿 32 ms 音频帧预算（爆音断流）、让 VAD 判停时刻前后飘、让识别和吐字出现长尾延迟。

> **环境与口径**
> 板子：Embedfire LubanCat（RK3588，4×A76 + 4×A55，RKNPU v2，内存约 7.7 GiB）
> 实测频率：A76 2.352 GHz、A55 1.8 GHz（全程定频）
> 日期：2026-10-09
> 引用的语音链路数据来自《端侧半双工语音链路选型与实麦闭环》；缓存与 DDR 交接细节见《RK3588 推理数据流：CPU 缓存与 NPU 的 DDR 交接》
> 下文 “一帧 2ms 变 4ms” 之类的数字是机制示意，真实数值以板子埋点为准

## 一、八个核：四个 “壮汉” 和四个 “轻便骑手”

RK3588 是 8 核 64 位 CPU，但 8 个核不是同一种，而是 ARM 的 big.LITTLE（大小核）搭配：



| 类别      | 数量 | 核型号        | 板子上频率     | 常见编号   |
| ------- | -- | ---------- | --------- | ------ |
| 大核（性能核） | 4  | Cortex-A76 | 2.352 GHz | cpu4–7 |
| 小核（能效核） | 4  | Cortex-A55 | 1.8 GHz   | cpu0–3 |

打个比方：



* A76 大核像四个壮汉，力气大、干活快，但吃得多（功耗高、发热大）；

* A55 小核像四个轻便骑手，力气小，但省电解热，适合长时间干轻活。

系统的分工思路是：重活（模型推理、压缩解压、突发计算）交给壮汉，轻活（后台守护、I/O 等待、界面常驻）交给骑手。这样平时省电，需要时又有力气。

在板子上确认自己的核编号和拓扑：



```
lscpu -e
# 或
cat /proc/cpuinfo | grep -E "processor|CPU part"
```

RK3588 上通常是 cpu0–3 为 A55、cpu4–7 为 A76，但以 `lscpu` 实际输出为准。

## 二、两种核差在哪



| 对比项  | A76 大核                                   | A55 小核         |
| ---- | ---------------------------------------- | -------------- |
| 定位   | 性能核                                      | 能效核            |
| 主频   | 2.352 GHz（官方标称最高 2.4 GHz）                | 1.8 GHz        |
| 微架构  | 乱序执行宽度大、流水线深，能同时铺开多条指令                   | 窄发射、结构简单，按顺序推进 |
| 缓存   | 每核 64 KB L1 指令 + 64 KB L1 数据 + 512 KB L2 | L1 同档，L2 更小    |
| 单核性能 | 约为 A55 的 1.5～2 倍（量级估算）                   | 基准 1           |
| 功耗   | 高                                        | 低              |
| 适合的活 | 模型前向、突发计算、对延迟敏感的任务                       | 常驻轻载、系统后台、I/O  |

有两个自然的追问：



1. **既然大核快，为什么不把 8 个都做成大核？** 因为功耗和发热。大核满载时耗电是小核的数倍，8 个大核同时跑，板子的供电和散热压不住，频率反而会被热保护压下来。大小核搭配是在 “一块芯片的功耗预算” 内做的折中。

2. **小核是不是 “废物核”？** 不是。对 I/O 等待多的活（等声卡、等网络、等磁盘），核大部分时间在睡觉，用大核跑纯属浪费。小核干这种活，性价比最高。

## 三、不绑定为什么会抖动

### 调度器默认会 “搬家”

在 Linux 眼里，8 个核都是可以干活的资源。调度器的职责是把所有线程尽量均匀地铺到核上，它会根据每个核的实时负载决定线程在哪跑 —— 这意味着同一个线程，上一帧在 A76 上跑，下一帧可能被挪到 A55 上跑。

**绑定（affinity）** 就是告诉调度器：“这个线程只准在这几个核上跑，别给它搬家。” 不做绑定，抖动就来自三个地方：

### 抖动来源一：算力跳变

同样一帧 512 点的音频处理，在 A76 上假设 2 ms，被挪到 A55 上可能要 3～4 ms。干的活一模一样，耗时却凭空多出一截，而且你无法预测下一帧会在哪种核上 —— 耗时就开始忽长忽短。

### 抖动来源二：迁移瞬间缓存全冷

A76 四个核组成一个簇，A55 四个核组成另一个簇，**两个簇的缓存不共享**。线程搬家时，原来核缓存里的音频数据、模型权重，新核一个都看不见，只能重新从内存搬一遍。这一帧会额外慢一次，叫 “冷启动” 尖峰。

打个比方：你在自己工位上干活，文件都摊在桌上，伸手就拿；突然被要求换到另一个楼层的工位，桌上的文件全得重新搬 —— 路上的时间就是缓存冷启动。

### 抖动来源三：排队等待

搬家时如果目标核正好在忙别的线程，线程还得排队等。这个等待时间没有确定上限，取决于当时系统有多忙。

三样叠加，结果就是：**任务本身的计算量没变，但完成时间一帧快、一帧慢**，这就是 “抖动”。

## 四、抖动会导致什么

### 1. 实时音频：爆音、断流、丢帧

音频是以固定速率流动的：16 kHz 采样，一帧 512 点，每隔 32 ms 就必须交出一帧。这 32 ms 是硬预算 —— 某一帧恰好撞上 “迁到小核 + 缓存冷 + 排队”，处理超时，声卡就会出现一段空隙，人听到的就是爆音、卡顿。

### 2. VAD 判停时刻前后飘

VAD 靠一帧一帧的概率判断 “用户什么时候说完”。如果帧到达时刻忽早忽晚，“静音 100 ms 判停” 的计时基准就不稳，可能把句中的停顿误判成说完，也可能多等一截。

### 3. 平均没问题，但尾巴很长

衡量抖动不看平均值，看分位数：把每帧耗时从小到大排队，p50 是正中间那帧（典型水平），p95 是 95% 位置那帧（95% 的帧都比它快），最大值是最慢的一次。实时系统最怕的是尾巴 ——p95、p99、最大值，因为体验由最慢的那一次决定。

### 4. 模型流水线：一个 token 慢，整句晚出声

大模型吐字是逐 token 串行的，一个 token 等一个 token。如果某个 token 的分词、采样线程恰好被迁核拖慢，这一拍的间隔就拉长，整句出声跟着晚。

### 对照实麦链路的现状

《端侧半双工语音链路选型与实麦闭环》里：



* 听帧 p50 2 ms、p95 4 ms、最大 4.6 ms，离 32 ms 预算很远 —— 目前很从容，但这是**顺序执行、模型段不并发抢核**时测的；

* 三轮预填 281 / 243 / 217 ms，第一轮最慢，已归因于 DDR 从 528 MHz 升到 1848 MHz 的等待 —— 这不是核迁移造成的，但它展示了 “非稳态” 长什么样：**频率抖动和核迁移抖动在现象上几乎无法区分**，不先绑核，将来一次慢到底是哪种原因，根本分不清；

* 下一步若做 “吐字与声码器叠跑”，CPU 争用加剧，调度器搬线程的概率会明显上升，听帧的尾巴会先变大。

## 五、怎么绑：从一条命令到独占核

### 第一步：taskset 启动时绑定（零成本）



```
# 大模型常驻子进程钉在 A76（单核性能关键）
taskset -cp 4-7 <大模型进程PID>

# 或启动时直接绑
taskset -c 4-7 python3 deploy/voice/profile_serve.py
```

### 第二步：代码内绑线程

把采音线程、VAD 线程分别钉到固定核（Python 用 ctypes 调 libc）：



```
import ctypes
libc = ctypes.CDLL("libc.so.6")
# 当前线程绑 cpu1：掩码 bit1 = 0x2
mask = (ctypes.c_char * 8)(bytes([0x2, 0, 0, 0, 0, 0, 0, 0]))
libc.sched_setaffinity(0, 8, mask)
```

### 第三步：给实时线程独占核（做产品时）

在内核启动参数里隔离核（如 `/boot/extlinux/extlinux.conf`）：



```
isolcpus=1,2 rcu_nocbs=1,2 nohz_full=1,2
```

被隔离的核不接普通任务，采音 + VAD 独占它们，彻底避开系统干扰。

### 验证



```
# 实时调度延迟基线，绑核隔离后最大值应明显下降
cyclictest -m -t1 -p 99 -i 1000 -l 100000

# 最直接：复用每帧埋点，对比绑定前后 p50/p95/最大值是否收敛
```

## 六、一句话记住

**核数是 “算力总量”，大小核是 “算力分档”，绑定是 “让线程别在档位之间来回跳”。** 不绑定，干活的人一帧在壮汉手里、一帧在骑手手里，还得搬着文件换楼层 —— 活没多干，时间却忽长忽短。定频消除的是 “同一核内的频率抖动”，绑核消除的是 “跨档迁移抖动”，两件事都做了，实时链路的耗时才可复现。
