# Qwen3-TTS-0.6B 双环境部署基线报告

## 摘要

在局域网主机（i7-13700 + GeForce 8 GB）和阿里云 ECS（RTX 4090 46 GB，与 Qwen3.5-35B LLM 共存）上，分别使用 vLLM-Omni v0.20.0 部署 Qwen3-TTS-12Hz-0.6B-CustomVoice。本机单路 warm 首帧延迟约 84–118 ms，但 8 GB 显存仅支撑约 1 路真并行；云端公网首帧约 259–280 ms（含网络 RTT），4090 在 `gpu-memory-utilization=0.10` 约束下可支撑约 5–6 路真并行。两套环境均以 WebSocket 双向流为最优实时播报协议，推荐并发上限分别为 1–2 路（本机）和 4–6 路（云端）。

## 2. TTS 部署配置

两套环境配置基本一致，核心差异在于显存利用率上限：

| 项目 | 局域网主机 | 阿里云 ECS |
|---|---|---|
| 容器镜像 | `vllm/vllm-omni:v0.20.0`（~32 GB） | `vllm/vllm-omni:v0.20.0`（~32.3 GB） |
| GPU 设备 | `CUDA_VISIBLE_DEVICES=0` | `CUDA_VISIBLE_DEVICES=0` |
| 显存利用率上限 | 默认（未限制） | `--gpu-memory-utilization 0.10`（让路给 LLM） |
| 共享内存 | 4 GB | 4 GB |
| 默认音色 | `vivian` / Chinese | `vivian` / Chinese |
| 音频格式 | PCM 24 kHz，16-bit，单声道 | PCM 24 kHz，16-bit，单声道 |

vLLM-Omni 对 Qwen3-TTS 启用 **2 个 Stage 引擎**：Stage 0 为 Talker（0.6B 语言模型），Stage 1 为 Code2Wav 声码器。两个进程同时驻留 GPU，实际显存远超权重文件大小（约 2.4 GB）。

## 3. 资源占用对比

### 3.1 GPU 显存

| 项目 | 局域网主机（8 GB） | 阿里云 ECS（46 GB） |
|---|---|---|
| TTS 总占用 | ~7.4 GB（占 GPU 约 90%） | ~9.7 GB（占 GPU 约 21%） |
| Stage 0 Talker | ~2.6 GB | ~5.1 GB |
| Stage 1 Code2Wav | ~4.3 GB | ~4.7 GB |
| Stage 0 权重 | 1.74 GiB | 1.74 GiB |
| Stage 1 权重 | 0.45 GiB | 0.45 GiB |
| KV cache（Talker） | **0.44 GiB** | **2.5 GiB** |
| 最大 KV tokens | 4,128 | 23,408 |
| KV 并发上限（@4096 tok/req） | **~1 路** | **~5–6 路** |

关键结论：Talker 的 KV cache 大小直接决定并发能力。本机 8 GB 卡在不限制显存利用率时，TTS 已占用 90%，剩余 KV cache 仅支撑 1 路；4090 即便以 10% 显存配合 LLM 共存，KV cache 仍有 2.5 GiB，并发能力是本机的 5–6 倍。

### 3.2 内存与磁盘

两套环境内存均充裕，不构成瓶颈。模型权重约 2.4 GB，Docker 镜像约 32 GB（镜像是主要磁盘开销）。

### 3.3 启动耗时

| 阶段 | 局域网主机 | 阿里云 ECS |
|---|---|---|
| Stage 0 权重加载 | ~0.9 s | ~0.8 s |
| Stage 0 引擎初始化（含 compile） | ~17 s | ~23 s |
| Stage 1 权重加载 | — | ~4.6 s |
| 全引擎就绪 | ~1 分钟 | ~1–2 分钟 |

两套环境冷启动至 healthy 均需 3–5 分钟（含 torch.compile 与 CUDA Graph 构建），线上部署应避免频繁重启。

## 4. 延迟与吞吐实测

### 4.1 单路首帧延迟（TTFA，warm）

| 协议 | 测试文本 | 局域网主机（回环） | 阿里云 ECS（公网） |
|---|---|---|---|
| HTTP 流式 | `你好，这是延迟测试。` | **~118 ms**（110–147 ms） | **~280 ms**（256–367 ms） |
| WebSocket 首帧 PCM | `你好。今天天气不错。我们开始测试。` | **~84 ms**（81–89 ms） | **~259 ms**（236–289 ms） |
| WebSocket audio.start | 同上 | 1–8 ms（合成开始信号） | 39–69 ms（合成开始信号） |

云端公网延迟约为本机回环的 2–3 倍，主要差值来自公网 RTT（通常数十毫秒），并非模型推理变慢。两套环境 WebSocket 均优于 HTTP 流式（约快 10–20 ms）。

官方参考值为 ~97 ms（理想条件），本机回环实测已接近该值（84–118 ms）。

### 4.2 并发能力对比

**局域网主机（8 GB）：**

| 场景 | 并发数 | TTFA | 说明 |
|---|---|---|---|
| 单路 HTTP 短句 | 1 | ~118 ms | 正常 |
| 双路 HTTP 短句 | 2 | ~142 ms / 路 | 出现排队，wall time ~1.3 s |
| 推荐并发上限 | **1–2 路** | < 200 ms | WebSocket 双向流 |

**阿里云 ECS（RTX 4090）：**

| 场景 | 并发数 | TTFA（mean / max） | 端到端 wall | 说明 |
|---|---|---|---|---|
| 单路 HTTP 短句 | 1 | ~280 ms | — | 公网基线 |
| 双路 | 2 | ~296 ms | ~0.61 s | 轻微排队 |
| 四路 | 4 | ~297 ms / ~313 ms | ~1.25 s | 正常完成 |
| 六路 | 6 | ~327 ms / ~349 ms | ~2.29 s | 开始明显排队 |
| 八路 | 8 | ~363 ms / ~410 ms | ~4.42 s | 延迟显著上升 |
| 推荐并发上限 | **4–6 路** | < 400 ms | HTTP / WS 均适用 |

### 4.3 官方参考 vs 实测

| 来源 | HTTP 首帧 | WS 首帧 PCM |
|---|---|---|
| 官方参考（理想条件） | ~97 ms | — |
| 局域网主机（回环） | ~118 ms | ~84 ms |
| 阿里云 ECS（公网） | ~280 ms | ~259 ms |

## 5. 部署场景建议

| 场景 | 推荐配置 | 原因 |
|---|---|---|
| 机器人单路实时对话 | 局域网本机，WebSocket | 延迟最低（84 ms），无公网 RTT |
| 多路并发播报 / 内容生产 | 阿里云 4090，HTTP 流式 | KV cache 充足，4–6 路可接受延迟内完成 |
| LLM + TTS 联合推理 | 阿里云 ECS 共存配置 | 4090 显存充裕，10% 给 TTS 已足够 5–6 路并发 |
| 成本敏感 / 边缘场景 | 本机独占，限制 1 路 | 避免 KV cache 溢出导致排队 |

**协议选型：** 实时流式播放首选 **WebSocket 双向流**，延迟最低、交互性最好；批量/后台合成可用 **HTTP 流式**，实现更简单。

## 6. 注意事项与已知问题

1. **本机 Driver Not Loaded**：报告撰写时局域网主机 NVIDIA 内核模块未加载，容器无法启动。需排查 `nvidia-driver-580-open` 驱动加载状态，可能需要重启或重新初始化内核模块。
2. **冷启动延迟**：首个请求可能额外增加数百毫秒至数秒（torch.compile CUDA Graph 未命中），生产环境应实现 warm-up 机制。
3. **LLM 流式分句影响**：LLM 流式按句输出时，TTS 首句出声需等待上游凑齐第一句文本，总延迟通常在 100–500 ms（不含公网 RTT），取决于 LLM 吐字速度。
4. **8 GB 卡并发限制根本原因**：Talker Stage KV cache 不足（0.44 GiB），并非 Code2Wav 声码器瓶颈。如需提升本机并发，可尝试限制 `--max-model-len` 或升级 GPU。
5. **公网 RTT 基准**：阿里云公网测试含客户端到服务器的网络往返，绝对延迟数值不应与本机回环直接对比；并发容量与显存数据更具跨环境参考价值。
