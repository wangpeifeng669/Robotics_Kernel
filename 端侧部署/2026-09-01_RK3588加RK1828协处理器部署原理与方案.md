# RK3588加RK1828协处理器部署原理与方案

> **解决的问题**：RK3588 片内 6 TOPS NPU 跑不动 7B 级 LLM 时，如何理解并落地「主控 + RK1828 协处理器」这套异构方案，以及官方宣称的 27B 支持到底是什么意思。

**核心摘要**：RK1828 不是另一颗 3588，而是瑞芯微给 RK3588/RK3576 外挂的 AI 协处理器（贡嘎系列，丝印 RK1820/RK1828）。它不跑 Linux，靠 PCIe 挂在主控下，用 3D 合封 DRAM 把 LLM 做成近存计算。单卡 5GB 只够 W4A16 的 7B/8B；官方「支持 Qwen3.8-27B」是多卡张量切分，四张卡内存并不共享。机器人语音交互的可落地方案是：一块 3588+1828 常驻 Qwen2.5-7B，另一块常驻 Qwen3-TTS-12Hz-1.7B，板间只流式传文本 chunk。

---

## 一、先分清两套「协处理器」

口语里的「3588 协处理器」会指两件完全不同的东西。混在一起，后面所有内存账都会算错。

| 说法 | 实际是什么 | 算力 / 内存 | 软件栈 |
|---|---|---|---|
| 3588 **片内**协处理器 | SoC 里相对 ARM CPU 的 NPU / GPU / VPU / ISP | NPU 3 核共 6 TOPS INT8，和 CPU 抢 LPDDR（约 34–51 GB/s） | **RKNN-Toolkit2** |
| 「3588 协处理器」扩展卡 | 独立芯片 **RK1828**（RK1820 为 2.5GB 低配） | 约 20 TOPS INT8 + **私有 5GB 3D DRAM** | **RKNN3**（两套不能混） |

RK3588 本身是完整 SoC：4×A76 + 4×A55 跑 Linux，片内 NPU 擅长 YOLO 一类 CNN。7B 级 decode 卡在 **共享 LPDDR 带宽**，不在「有没有 NPU」——片内 NPU 喂不进权重，NPU 就在空转。

RK1828 的定位是：**主控继续管 OS、相机、网口、业务；协处理器专职推理**。瑞芯微 2025–2026 年把它叫 AI Co-processor，和 Hailo 那种「插 M.2 的加速卡」同类，不是第二块电脑。

---

## 二、RK1828 原理：拆的是内存墙，不是再堆 TOPS

7B 稠密 LLM 的 decode 几乎每一步都要把一层权重从内存读进计算单元。算力再高，总线喂不进数据就空转。3588 片内 NPU 只有 6 TOPS，更致命的是和 CPU/GPU/ISP 抢同一条 LPDDR。

RK1828 的解法是三件事叠在一起：

1. 专用 NPU（INT8 峰值约 20 TOPS，支持 INT4 / FP8 / FP16 / BF16；LLM 常用 **W4A16**）
2. **DRAM 3D 堆在 NPU 逻辑晶圆上**（1828 为 5GB，1820 为 2.5GB；营销口径理论带宽约 1 TB/s）
3. 主控只通过 PCIe/USB 传输入和结果，权重与 KV Cache 常驻协处理器内存

```text
                    ┌─────────────────────────────────┐
  RK3588 主控       │            RK1828               │
  OS / 相机 / 网络  │  RISC-V 固件核（调度、预处理）   │
         │ PCIe DMA │         ↓ 下发微码              │
         └─────────►│  NPU 矩阵 / Attention 引擎      │
                    │         ↕ 垂直过孔（TSV）        │
                    │  3D 合封 DRAM（权重 + KV Cache） │
                    └─────────────────────────────────┘
```

片内还有 3 颗 64 位 RISC-V：**1×SRV 做调度，2×VRV 带 128-bit 向量做前后处理**。它们是固件核，不能 SSH 上去跑 Python。NPU 仍是静态流水线：模型必须离线编成 `.rknn`，运行时不能随意改控制流。

**20 TOPS 不是 7B 快的主因，合封带宽才是。** 权重住在 5GB 里，decode 每一步都是片内近存取数，不再穿过 3588 的内存总线。公开对比里会出现 Orin NX 理论 TOPS 更高、7B decode 却不一定赢——decode 是带宽活。

规格要以手上模组为准：常见 M.2 是 **PCIe 2.1 ×1**（单向大约 400 MB/s）；功耗区分芯片典型几瓦和模组跑 7B 时平均十瓦级、峰值可到近 30W（常需外供 12V）。

## 三、3588 和 1828 怎么通信

物理上 1828 是 **PCIe Endpoint**，3588 是 **Root Complex**。PCI Device ID 常见为 `1d87:182a`（1820/1828 相同）。Linux 绑瑞芯微驱动 `pcie-rkep`，再灌固件（如 `/lib/firmware/rknn3_rk1820.img`）。灌完之前 1828 听不懂 RKNN3 命令，它自己不跑 Ubuntu。

```text
业务 / rkllm3-server          ← OpenAI 兼容 HTTP，或自写 C API
        │
librknn3_api.so               ← 用户态 Runtime
        │ ioctl / DMA
pcie-rkep.ko                  ← 内核驱动
        │ PCIe TLP + DMA
RK1828 固件 + NPU + 5GB DRAM
```

「零拷贝」(`RKNN_MEM_DMA_ZERO_COPY`) 的含义是：3588 申请物理连续 DMA 缓冲，1828 的 DMA 引擎自己来搬，省掉用户态 `memcpy`。这是 **3588 ↔ 这一张卡** 的通道，不是多卡共享内存。

手动绑驱动（调试用，量产走 SDK 安装包）：

```bash
# 以实际 lspci 地址为准
echo pcie-rkep | sudo tee /sys/bus/pci/devices/0000:01:00.0/driver_override
echo 0000:01:00.0 | sudo tee /sys/bus/pci/drivers/pcie-rkep/bind
sudo setpci -s 01:00.0 COMMAND=0x0406   # 打开 BusMaster
```

Runtime 调用链：`rknn3_init` → `find_devices` → `load_model` → `session_init` → `session_run` / `run_async` → `destroy`。日常可直接起 `rkllm3-server`，对内仍是这一套，对外是 `/v1/chat/completions`。

备选互联是 USB 3.0；主路径仍是 PCIe。转换在 x86 上用 **RKNN3-Toolkit**，`target` 填 `rk1828` / `rk1820`，**不能填 `rk3588`，也不能拿 Toolkit2 的 `.rknn` 上卡。**

## 四、如何处理一个 LLM（以 Qwen2.5-7B 为例）

职责切开：3588 管系统与字符串，1828 管矩阵。

| 步骤 | 在 3588 | 在 1828 |
|---|---|---|
| `.rknn` 文件 | 放 eMMC/NVMe | — |
| **启动加载（一次）** | 把约 3.5GB 权重 DMA 过去 | 写入合封 DRAM，常驻到关机 |
| Tokenizer | CPU：字符串 → token ID | 一般不跑 BPE |
| Prefill | 只送 prompt 的 ID 列表（几 KB） | 整段 Transformer，**KV 写在自己 DRAM** |
| Decode 每一步 | 送 1 个 token ID（或「继续」） | 读 KV + 算下一层，采样出下一个 ID |
| Detokenizer | CPU：ID → 字，SSE/推 TTS | — |

中间激活、Attention、FFN **都不回 3588**。若每层搬特征图，×1 的 PCIe 会把 50 token/s 打成个位数。

```text
用户文本
  → 3588 tokenizer → token ids（DMA，几 KB）
  → 1828 Prefill（TTFT 公开口径约 0.2–0.4s）KV 留在 5GB
  → DMA 回 1 个 token id
  → 3588 detokenize 先吐字
  → 循环 Decode：每步只搬 4～8 字节级的 id
  → EOS 结束 session
```

**Prefill** 是计算受限，prompt 越长 1828 越忙，PCIe 几乎不是瓶颈。**Decode** 每秒往返几十次，载荷极小，延迟来自 NPU 算一层。Session 对应一次对话上下文；不要每个 token 新建 session，也不要把整表 logits 搬回主控采样。

公开性能口径（W4A16、短上下文，集成商数据有 52～70 token/s 波动，以自己板子 `rknn-smi` + demo 为准）：

| 模型 | 单卡 1828 | 单卡 1820（2.5GB） |
|---|---|---|
| Qwen2.5-3B | 能跑，且与 1820 接近 | 主场 |
| Qwen2.5-7B | 权重 ≈3.5GB，常驻得下 | 装不下，会 swap，不可用 |
| Qwen3-8B | 单卡上限附近，上下文不能拉太长 | 否 |

纯 3588 片内 NPU 跑同一 7B，公开对比大约十几 token/s，对话会结巴。7B 生产路径就是 **3588 + 一张 1828**。

## 五、5GB 怎么「支持」Qwen3.8-27B

单卡 5GB **装不下** 27B。官方新闻标题是「RK1828 **多卡级联**支持 Qwen3.8-27B」，主语是整机，不是一颗芯片。

Qwen3.8-27B 是**稠密**模型（不是 MoE 只激活 3B）。W4A16 权重 ≈ **13.5GB**，加 KV 与运行时大约 **17GB**。

| 配置 | 合封 DRAM | 27B 全量常驻 |
|---|---|---|
| 1×1828 | 5GB | 否 |
| 2×1828 | 10GB | 仍不够 |
| 4×1828 | 20GB | 内存账能盖住 |

做法是 RKNN3 的 **张量切分（Tensor Parallel）**：每一层大矩阵切开，每张卡只存自己那一份，永远住在各自 5GB 里。「20GB 聚合」是软件分片，**不是四卡熔成一块共享显存**。

```text
                    RK3588 主控（OS + LPDDR 中转）
                         │
              PCIe 根端口 / 板上 Switch
              ┌──────┼──────┼──────┐
              ▼      ▼      ▼      ▼
           1828#0  #1     #2     #3
           各 5GB 私有 DRAM（地址不通、无缓存一致性）
```

卡与卡 **没有 P2P**。每层激活同步路径是：卡 A DRAM → PCIe → 3588 内存 → PCIe → 卡 B。片内 1TB/s 只在单卡内部有效，跨卡立刻掉到几百 MB/s，还要四卡抢总线。所以 27B 公开方案大约 **十几 token/s**，和单卡 7B 的 50+ 不是同一体验。

硬件约束：3588 原生 PCIe lane 有限（约 1× PCIe3.0×4 + 若干×1，还和 SATA/USB 复用）。四卡盒子要么 PHY 拆成 4×1，要么板上加 Switch。多数量产 3588 板只有 1～2 个 M.2；四卡要专门载板、独立 12V 和风道。RK1820 不要拿来级联 27B。

SDK 另有 **流式权重加载**：权重放 3588 内存/SSD，按层灌进 5GB。单卡能「演示」27B，但每层都在搬权重，交互基本不可用。Day0 方案走的是多卡常驻，不是这条。

机器人单板：**按 7B 选型，不要冲 27B。**

## 六、推荐落地：一板 LLM、一板 TTS

两个模型不要塞进同一张 1828，也不要跟 27B 四卡切分混为一谈。这是 **任务并行**：一卡（或一板）一个常驻模型。

| 板 | 硬件 | 模型 | 体积 |
|---|---|---|---|
| 板 A | 3588 + 1×1828 | **Qwen2.5-7B** W4A16 | ≈3.5GB，单卡主场 |
| 板 B | 3588 + 1×1828 | **Qwen3-TTS-12Hz-1.7B** | Talker ~1GB 量级 + 轻量声码器 |

TTS 不是单网络，而是 Talker（12Hz 多码本语音 token）→ Code2Wav / speech_decoder。RKNN3 Model Zoo 拆成 talker、code_predictor、speech_decoder 等多份 `.rknn`。**生产用 1.7B，不要用 0.6B**：有实测在 RKNN3 V1.0.4 上 0.6B 量化后 EOS 塌掉。

```text
板 A：Qwen2.5-7B 流式吐字（每 3～8 字或一个标点）
        │  以太网：只传 UTF-8 chunk + 会话 id（TCP/QUIC）
板 B：Qwen3-TTS 流式合成 PCM → 喇叭
```

- LLM 必须流式，禁止等整段生成完再 POST 给 TTS，否则首包会多出几十到上百毫秒。
- 音频若还要送到第三块板，走 UDP/RTP + VPU 编码，不要和底盘控制挤同一条 TCP。
- 两板很近、只为降首包：也可以 **同一块 3588 插两张 1828**（1828#0 跑 7B，#1 跑 TTS），少一跳网线，供电散热仍按双卡设计。

不要做的事：两块裸 3588 都不挂 1828 硬跑 7B；TTS 用 0.6B 图省内存；两板 mmap 同一份权重（没有共享内存，各加载一份）。

## 七、转换与验证

**PC 侧（x86）**

```text
HuggingFace / ModelScope 权重
  → RKNN3-Toolkit（与板端 Runtime 同版本，如 1.0.4 / 1.1.x）
  → target=rk1828，LLM 用 w4a16
  → 生成 .rknn（TTS 为多组件）
```

**板侧**

1. `lspci -nn | grep 182a` 能看到设备；`lsmod | grep rkep` 驱动在。
2. `rknn-smi` 看固件、温度、链路（常见 5 GT/s ×1）。
3. 先跑 SDK 自带 `rknn3_llm_demo` / `rknn3_session_test`，再挂 `rkllm3-server`。
4. 用本机 `base_url=http://127.0.0.1:8000/v1` 打一条流式 chat，记 TTFT 和 token/s。
5. TTS 板用 1.7B-Base 或 CustomVoice，确认能正常 EOS、首包 PCM 可播。

**验证清单**

| 项 | 通过标准 |
|---|---|
| 7B 常驻 | `rknn-smi` 显示模型在 1828 上，不再反复从盘加载 |
| 对话 | 短 prompt TTFT < 0.5s 量级，decode 明显快于纯 3588 NPU |
| 双板语音 | LLM 未说完 TTS 已出声；LLM 长 prefill 时 TTS 首包不跟着炸 |
| 负例 | 单卡灌 27B 应 OOM 或走流式加载后吞吐不可用，这才说明内存模型没理解错 |

## 八、踩坑

1. **Toolkit2 的 `.rknn` 不能上 1828**；反过来 RKNN3 产物也不能当片内 NPU 模型用。
2. `max_context_len` 在转换时钉死，运行时改不了。Agent 需要长上下文就一次转够。
3. 多卡 27B 的「流畅」是相对云端 RTT，不是相对单卡 7B。多数 3588 板插不满四卡。
4. 6 TOPS + 20 TOPS **不能**把同一个模型拆开加总。YOLO 仍走 3588 片内；LLM 走 1828。
5. 中断别打在跑业务的 A76 上；PCIe ASPM 打开会抖延迟。
6. 模组要独立 12V 时，只靠 M.2 槽供电会降频、掉卡。
7. 固件、`librknn3_api.so`、Toolkit、模型必须同一 SDK 版本。

**一句话选型**：机器人语音交互用 **3588 + 单 1828 跑 7B**，TTS 换板或换卡隔离；只有边缘盒子、明确要 27B 离线知识库时，才上四卡级联，并接受十几 token/s 和主控转发的同步开销。
