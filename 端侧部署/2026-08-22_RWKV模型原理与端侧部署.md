# RWKV模型原理与端侧部署

**核心摘要**：RWKV 通过数学等效变换，把 Transformer 的 Self-Attention 改写成线性循环递推形式，推理时是纯 RNN（显存与单 Token 延迟恒定，无需 KV Cache），训练时又展开成矩阵并行。它精准击中了端侧"长对话爆内存、首字慢、功耗高"三大痛点，在 RK3588 / 地瓜 S100P 上跑 0.4B–3B 模型即可达到实时语音交互门槛。结论：RWKV 不会取代 Transformer，而是成为端侧高频流式交互场景的主流架构之一，与 Transformer 形成分工。

---

## 一、RWKV 是什么：把 Transformer 写成线性 RNN

**RWKV（Receptance Weighted Key Value，接收加权键值）** 是一种把 RNN 的推理效率与 Transformer 的并行训练能力结合起来的 LLM 架构。

它的核心做法一句话概括：**通过数学等效变换，把 Self-Attention 里的 Softmax 展开，改写成类似 RNN 的线性循环递推形式**。结果得到两个关键性质：

- **推理期 $O(1)$ 时间与空间复杂度**：传统 Transformer 的 KV Cache 随上下文长度线性/二次增长；RWKV 推理时是完全的 RNN，上下文多长，显存占用与单 Token 延迟都保持恒定。
- **训练期 $O(N)$ 并行度**：训练时又能展开成全矩阵并行运算，规避了传统 RNN 无法高效利用 GPU 并行算力的致命缺陷。

---

## 二、核心原理：R/W/K/V 四向量与 WKV 公式

RWKV 借用了 Transformer 的 Key-Value 概念，但重新定义了交互方式，引入四个核心向量：

| 向量 | 全称 | 作用 | 类比 |
| :--- | :--- | :--- | :--- |
| **R** | Receptance（接收向量） | 经 Sigmoid 缩放，控制对当前 Token 信息的"接收程度"（门控门限） | 类似 Query |
| **W** | Weight（衰减权重） | 位置与时间的指数衰减率，越久的历史衰减越多 | RWKV 独有 |
| **K** | Key（键向量） | 提炼当前输入的关键特征，与 W 共同决定历史信息在 State 中的累积权重 | 类似 Key |
| **V** | Value（值向量） | 实际承载的信息载体 | 类似 Value |

其核心计算表达式（Time-Mix 的时间混合）：

$$o_t = \sigma(r_t) \odot \frac{\sum_{i=1}^{t} e^{-(t-i)w + k_i} v_i}{\sum_{i=1}^{t} e^{-(t-i)w + k_i}}$$

注意关键点：**分子分母都是对历史信息的加权求和，而权重是指数衰减的**。这正是"距离越远的历史，对当前输出的影响越小"的数学表达。

---

## 三、双模式：同一公式，训练推理走两条计算图

RWKV 的突破在于——**同一个数学公式，训练和推理时用完全不同的计算图执行**。

### 3.1 训练模式：并行 Transformer（Parallel Mode）

传统 RNN 无法并行训练，是因为 $h_t$ 强依赖 $h_{t-1}$。RWKV 把 Attention 的 Softmax 展开后，发现分子与分母都能写成**无状态依赖的线性卷积形式**，于是训练阶段可以一次性对整句输入做全矩阵乘法（类似 Causal Conv），实现 GPU 全满载并行训练。

### 3.2 推理模式：递推 RNN（Recurrent Mode）

自回归生成时，RWKV 把公式展开为递推的分子 $a_t$ 与分母 $b_t$：

$$a_t = e^{-w} a_{t-1} + e^{k_t} v_t$$
$$b_t = e^{-w} b_{t-1} + e^{k_t}$$
$$wkv_t = \frac{a_t}{b_t}$$

在这一阶段，模型**完全不需要保留历史上所有 Token 的 KV Cache**，只需更新两个固定大小的向量（State）。这就是恒定显存占用与恒定生成延迟的来源。

### 3.3 模块构成：Time-Mix 与 Channel-Mix

每个 RWKV 层（Block）由两个子模块组成，替代 Transformer 的 Self-Attention 与 FFN：

- **Time-Mix（时间混合）**：捕获时间轴（上下文）信息。引入 **Token Shift（时间偏移）** 机制，把当前 Token 与上一个 Token 的 Embedding 按比例线性插值（$\mu x_t + (1-\mu) x_{t-1}$），用极低开销实现局部上下文融合。
- **Channel-Mix（通道混合）**：在特征通道（维数）间做非线性映射与提炼，同样应用 Token Shift，结合 Squared ReLU / GELU 门控单元做特征变换。

## 四、为什么 RWKV 天然适合端侧

端侧的核心约束是：内存小（2GB–16GB）、功耗敏感、带宽有限。传统 Transformer 在这三个维度全面吃瘪，RWKV 恰好精准命中：

| 评估维度 | RWKV 端侧表现 | 传统 Transformer 端侧表现 |
| :--- | :--- | :--- |
| **显存/内存占用** | 极低且恒定（只存固定大小的 Hidden State，1.5B 模型 State 仅几 MB） | 随上下文暴涨（KV Cache 极易 OOM） |
| **内存带宽消耗** | 极低（瓶颈只在权重加载，无 Dynamic Attention 读写） | 极高（Attention 矩阵频繁读写内存） |
| **NPU/边缘芯片适配** | 友好（都是固定 Shape 的矩阵乘法与循环状态更新） | 复杂（需专门优化 Softmax 和动态 KV Cache 管理） |
| **长对话推理** | 首 Token 与续写延迟一致，无性能衰减 | Context 变长后延迟与显存显著增加 |

两个最直观的工程收益：

1. **不爆内存**：Transformer 对话越长 KV Cache 越大，4G/8G 板卡极易 OOM；RWKV 的 State 尺寸恒定，连续聊几天内存消耗不增加。
2. **低延迟首 Token（TTFT）**：即便长上下文，首字响应仍恒定毫秒级，适合结合离线 ASR/TTS 做低延迟机器人对话。

## 五、RK3588 与地瓜 S100P 能跑多大

两块板卡都能跑 RWKV，且效率优于同参数量级的 LLaMA / Qwen。核心限制还是**内存容量 + NPU 算力/带宽**。

### 5.1 RK3588（瑞芯微，6 TOPS INT8，4×A76 + 4×A55）

| 模型规模 | 内存占用 | 推理速度 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 0.1B–0.4B | — | 100+ tokens/s（毫秒级） | VAD、意图识别、轻量分类 |
| 1.5B（INT4/INT8） | 约 1.2–1.8GB | 10–20 tokens/s | **实时语音交互门槛** |
| 3B（INT4） | 约 2.5–3.2GB | 3–7 tokens/s | 勉强可用，延迟感明显 |

### 5.2 地瓜 S100P（约 128 TOPS，BPU 架构，对矩阵并行优化极高）

| 模型规模 | 内存占用 | 推理速度 | 适用场景 |
| :--- | :--- | :--- | :--- |
| 1.5B / 3B | — | 30+ tokens/s | 机器人本地大模型 Agent 决策 |
| 7B（INT4） | 4GB+（需 16GB 以上板载内存） | 3–8 tokens/s | 极限，带宽成新瓶颈 |

关键判断：**RK3588 的甜点位在 0.4B/1.5B，S100P 的甜点位在 1.5B/3B**。RWKV 没有动态 Attention 和巨量 KV Cache，在这类边缘 NPU 上比同参数量级 Transformer 效率显著更好。

## 六、部署落地路径

分两条路，按"先跑通、再优化"的顺序推进：

1. **CPU 极速部署（推荐先测）**：用开源项目 **`rwkv.cpp`**。RWKV 的矩阵乘法在 CPU ARM Neon 指令集上优化极好，RK3588 纯 CPU 跑 1.5B 就有不错速度，开箱即用、开发成本最低。

2. **NPU 硬件加速（追求极限功耗/性能）**：
   - **RK3588**：把 RWKV 的 Core Block（线性 Recurrence 算子）导出 ONNX，用 `RKNN-Toolkit2` 量化为 `.rknn` 移交 NPU。
   - **地瓜 S100P**：用地瓜官方 **地平线天工开物（OE）/ BPU SDK** 把 ONNX 编译成模型镜像。

> 踩坑提示：相比 LLaMA 生态，部分边缘 NPU 官方编译器对 RWKV 算子融合（如 Custom WKV Kernel）的现成支持可能需少量手动打通。这正是端侧部署的常规操作——参考本目录下"算子填坑"相关笔记。

## 七、RWKV 会成为端侧主流吗

结论：**有主流相，但更大概率是"特定端侧场景的杀手锏"，而非覆盖全局的"唯一主流"。**

### 7.1 为什么极具主流相

它精准击中了端侧两大痛点——打破"内存墙"（State 恒定，无限轮本地对话不 OOM）与极低 TTFT/功耗（无 Softmax 与 dynamic attention，低算力 NPU/CPU 也能快速吐字，延长便携设备续航）。

### 7.2 阻碍它统治端侧的三个壁垒

1. **混合架构强敌环伺**：Mamba / SSM 快速崛起，苹果、Google、Meta 主推"Transformer + SSM 混合架构"（关键层保留少量 Attention 保精确记忆，其余层用线性 Recurrence 提速）。
2. **长文本精确检索（Needle in a Haystack）上限**：所有历史信息压缩进固定维度 State，做"读 30 页文档精确提取一个电话号码"这类严苛 Look-up 任务时，略逊于 Full-Attention Transformer。
3. **芯片厂生态惯性**：高通、联发科、苹果已针对 Transformer（Softmax、KV Cache 压缩、FlashAttention）做大量 ASIC 算子固化，RWKV 的工具链广度与深度仍需时间追赶。

### 7.3 未来格局：分化与共存

- **RWKV 主场**：实时语音交互设备（智能音箱、机器人主控）、极低功耗 MCU/嵌入式 SoC（1–2GB 内存，Transformer 进不去的死角）、7×24 常驻 Agent 与传感器流处理。
- **Transformer/混合架构主场**：高端 PC / 旗舰手机的复杂代码生成、大篇幅 PDF 分析、多模态高精度理解等重度推理场景。

---

## 八、对机器人场景的结论

结合我们自己的研发方向（RK3588 / S100P + ASR/TTS + 本地 Agent），RWKV 的价值点很清晰：

1. **机器人语音交互是 RWKV 的典型主场**：流式对话、低延迟首字、长会话不爆内存，这三条正好对应我们当前 Transformer 方案最头疼的问题。RWKV 1.5B（RK3588）或 3B（S100P）就能跑进实时门槛。
2. **长文本检索仍是短板**：如果未来要做"读整本说明书并精准引用"的 RAG 强检索场景，RWKV 的固定 State 压缩会吃亏，需靠 RAG 召回补充，而非靠模型本身硬记。
3. **选型建议**：高频流式交互走 RWKV/SSM，重度复杂推理走 Transformer，两者在端侧会长期共存。落地时可先用 `rwkv.cpp` 纯 CPU 快速验证效果，再决定是否投入 NPU 算子适配成本。

> 一句话：**RWKV 是"端侧轻量化、高实时性"场景的主流架构之一，但它解决的是"快和轻"，不是"准和深"——选它前先想清楚你的场景到底要哪个。**
