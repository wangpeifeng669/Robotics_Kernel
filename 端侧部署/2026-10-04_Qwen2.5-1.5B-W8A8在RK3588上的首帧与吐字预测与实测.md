# Qwen2.5-1.5B-W8A8在RK3588上的首帧与吐字预测与实测

**核心摘要**：W8A8 的 Qwen2.5-1.5B 在 RK3588 上，吐字的屋顶是内存带宽：20 GB/s ÷ 1.5 GB 约 13 token/s。128 token 首帧有两笔——权重搬运约 80 ms、乘加算力约 56 ms，边搬边算取 80 ms，先搬完再算取 140 ms。LubanCat-4 实测首帧 459 ms、吐字 12.33 token/s，两条屋顶都没碰到。调 DDR 时钟从 1068 MHz 到 1848 MHz 后，首帧 611→412 ms、吐字 9.20→14.57 token/s，吐字涨幅正好是带宽比的 92%——首帧不是纯带宽账。

结构数字以《LLM部署选型参数怎么看-以Qwen2.5-1.5B为例》为准，本包的量化、核数和上下文以 `export_qwen25_1_5b.py` 为准。

> **环境与口径**
> 板子：Embedfire LubanCat-4（RK3588S，4×A76 + 4×A55，NPU 6 TOPS，7.7 GiB）
> 模型：W8A8 rkllm，2,044,785,228 字节（1.90 GiB），`max_context=4096`，3 核全开
> 运行时：rkllm-runtime 1.3.0 / rknpu 0.9.8 / 模型内 rkllm-toolkit 1.2.1
> 频率：A55 1.8 GHz、A76 2.352 GHz、NPU 1.0 GHz（均为本板最高档）
> DDR：推理时定频，本板频率表 1068 MHz 与 1848 MHz 两档
> 口径：对齐瑞芯微 `rknn-llm` v1.3.0 的 `benchmark.md`。Prefill 总时间当首 token，Generate 的 token/s 当吐字，Peak Memory 取进程 VmHWM，三次取中位数
> 输入：128 token（含模型内置 chat template），`max_new_tokens=64`，第一个输出 token 计进 Prefill，Generate 统计其余 63 个

---

## 一、账面结论

| 项 | 预测 | 含义 |
|---|---|---|
| 吐字 | 约 **13 token/s** | 20 GB/s ÷ 1.5 GB。每生成 1 个 token 要把全部权重再读一遍，更快就要更高的有效带宽 |
| 满 4096 上下文时的吐字 | 约 **12 token/s** | 同一条带宽账，多读约 112 MiB 的 KV |
| 短提示首帧（128 token），边搬边算 | 最快约 **80 ms** | 搬运 80 ms，运算 56 ms。运算包在搬运里面，再快就要在 80 ms 里把 1.5 GB 读完 |
| 短提示首帧（128 token），先搬完再算 | 约 **140 ms** | 80 ms + 56 ms。算力在权重全部到达之前空等 |
| 首帧随输入变长 | 见第六节 | 边搬边算取较大值；先搬完再算则两笔相加 |

128 token 指这一次前向吃进去的上下文总长度（系统提示 + 历史 + 本轮输入），不是要生成 128 个 token，也不是本包 4096 的上下文上限。中文在这个词表上大约 1 个 token 对应 1 到 2 个汉字，13 token/s 大约是每秒十几个到二十几个字，快过朗读。

## 二、代入的数

| 项 | 值 | 来源 |
|---|---|---|
| 层数 / 隐藏维 / Q 头 / KV 头 / head_dim | 28 / 1536 / 12 / 2 / 128 | head_dim = 1536 ÷ 12 |
| FFN 中间维 | 8960 | SwiGLU 三矩阵 1536×8960 |
| 词表 / 权重绑定 | 151936，输入输出共用一份 embedding | — |
| 一层矩阵参数 | 4679 万 | 见第三节 |
| 28 层线性参数 | 13.10 亿 | 不含 embedding |
| 总参数 | 约 1.54B | 28 层 + 一份 embedding |
| 量化 | W8A8，权重按 1 字节 | 导出脚本 `QUANTIZED_DTYPE` |
| INT8 权重体积 | 约 1.5 GB | 1.54B × 1 字节 |
| NPU 标称算力 | 6 TOPS | 一次乘加计两次运算，有效 3 TMAC/s |
| 带宽 | 20 GB/s | LPDDR4x 规划口径 |
| KV | 每 token 28 KiB，每 1K token 约 28 MB | 4096 满窗约 112 MiB |

sysfs 和 loader 打印的 MHz 都是 DRAM 时钟，不是数据速率。LPDDR4 每个时钟传两次，数据速率约为时钟的两倍。本板最高档 1848 MHz 对应约 3696 MT/s，靠近 LPDDR4-3733；官方定频脚本写的 2112 MHz 也是时钟，对应约 4224 MT/s，本板频率表里没有这一档。空闲时钟 528 MHz。

W8A8 若把 cache 也量化成 INT8，KV 会再小一档；相对 1.5 GB 权重，这点体积改不动吐字的数量级。

## 三、4679 万里面是什么

每一层只有注意力 4 个矩阵和 FFN 3 个矩阵，28 层都一样。

| 矩阵 | 形状 | 参数量 |
|---|---|---:|
| Wq | 1536×1536 | 236 万 |
| Wk | 1536×256 | 39 万 |
| Wv | 1536×256 | 39 万 |
| Wo | 1536×1536 | 236 万 |
| FFN 三矩阵（gate / up / down） | 1536×8960 ×3 | 4129 万 |
| 合计 | | **4679 万** |

K、V 的宽度是 256，因为 GQA 把 12 组键值压成 2 组，每组 `head_dim=128`。FFN 占这一层的 88%。RMSNorm 和 Q/K/V 的 bias 一层只有几千个数，词表 embedding 的 2.33 亿是全模型单独一份，都不在这 4679 万里。

28 层线性参数 = 4679 万 × 28 = **13.10 亿**。首帧的乘加几乎全在这 13.10 亿上。

## 四、吐字怎么估

Decode 每出一个 token，都要把全部权重重新从 DDR 读一遍。算力在这一步是富余的：1.54B 次乘加即使只跑到 6 TOPS 的一个零头，也远快过把 1.5 GB 搬进 NPU。所以吐字卡带宽。

\[
吞吐 = 带宽 / 每\ token\ 搬运量 = 20\ GB/s \div 1.5\ GB \approx 13\ token/s
\]

4096 长度上还要再读已经写好的 KV，约 112 MiB。分母变成 1.5 GB + 0.11 GB，吞吐降到约 12 token/s。语音对话常见的 2K 以内，KV 相对权重可以忽略，仍按 13 token/s。

两条前提要钉住：激活量化不减少权重搬运，所以 W8A8 的吐字按 INT8 权重算，选型文档里 INT4 约 20 token/s 那一档对这个包不适用；文件本体 1.90 GiB，若运行时每个 token 把整个映射区都扫一遍，上限降到约 10 token/s。缩放表和文件头通常不会整段重读，账面仍按 1.5 GB 记 13 token/s。

## 五、首帧怎么估

首帧指模型已经加载完成之后，从开始推理到第一个输出 token 可以出来。这段时间里有四件事：

1. 28 层对整段输入做前向；
2. 前向过程中从 DDR 读权重、读写激活和 KV；
3. 层与层之间的提交和同步；
4. 最后一次词表 logits，并采样出第一个 token。

账面公式只覆盖第 1 件的乘加次数，以及第 2 件里「权重整份读一遍」。第 3 件在公式里是 0。第 4 件是一次 151936×1536 的矩阵向量乘，约 2.3 亿次乘加，相对 128 token 的 1691 亿可以忽略。从存储读入 rkllm、runtime 初始化不在首帧里，那是进程启动时单独的一笔，测的时候要和首帧分开记。

### 乘加分两笔

线性层每个权重对每个输入 token 做一次乘加：

\[
线性 = 13.10亿 \times N
\]

注意力每个 query 头做两块矩阵乘，Q×K 和分数×V。Q 头 12，`head_dim` 128，GQA 只压缩 K、V 的存储和投影，12 个头的打分仍然都要算：

\[
一层 = 2 \times 12 \times 128 \times N^2 = 3072 \, N^2
\]

\[
28\ 层 = 86016 \, N^2
\]

词表查 embedding、RMSNorm、SwiGLU 的逐元素运算不进这张账。

### 128 token 的算术

\[
线性 = 13.10亿 \times 128 = 1677亿
\]

\[
注意力 = 86016 \times 128^2 = 14亿
\]

\[
合计 = 1691亿次乘加
\]

按 3 TMAC/s（6 TOPS，一次乘加计两次运算）：

\[
1691亿 \div 3万亿次每秒 = 56\ ms
\]

同一段前向还要把 1.5 GB 权重从 DDR 送到 NPU。按 20 GB/s 读一遍要 75 ms，取整约 80 ms。80 ms 只含搬运，56 ms 只含运算，两笔都要计入，但是否相加取决于它们能不能同时发生。

NPU 片上缓冲放不下一整份 1.5 GB，权重是分块进来的。算当前这块时，下一块可以已经在路上，这时 56 ms 的运算发生在那 80 ms 的搬运里面，首帧取较大值约 **80 ms**。把两笔再加一次，会把已经重叠的时间算两遍。

只有一种情况要把它们相加：整份 1.5 GB 先搬完，搬运期间算力完全空等，搬完才开始算。128 token 就是 80 ms + 56 ms ≈ **140 ms**。板上没有能放下整模的片上缓存，这条是串行假设下的账，比边搬边算更慢。128 token 时注意力只占 1691 亿的不到 1%，运算时间几乎全是 28 层矩阵乘。

### 为什么短提示用带宽、长提示用算力

INT8 矩阵乘里，每个权重字节大约被复用 N 次，运算强度大约是每字节 2N 次运算。6 TOPS 对 20 GB/s 的拐点大约在每字节 300 次运算，也就是 N 大约 150。

- N 小于拐点：边搬边算时运算还没填满搬运的时间，首帧约 80 ms，提示再短也不会低于这一档。先搬完再算还要加上那笔运算。
- N 大于拐点：运算时间更长。边搬边算时首帧改由乘加时间决定；先搬完再算则在乘加时间上再加约 80 ms。

这个拐点只在 6 TOPS 真的吃满时成立。NPU 吃不满时，短提示也会一直卡在计算和调度上，80 ms 碰不到。选型文档写「首响卡算力」，指的是这种实际运行，不是上面这条峰值屋顶。

## 六、按输入长度的首帧屋顶

| 输入总长度 N | 乘加 | 运算（吃满 6 TOPS） | 权重读一遍 | 边搬边算（取较大值） | 先搬完再算（相加） |
|---|---|---|---|---|---|
| 128 | 1691 亿 | 56 ms | 80 ms | **约 80 ms** | **约 140 ms** |
| 256 | 3410 亿 | 114 ms | 80 ms | **约 110 ms** | **约 190 ms** |
| 512 | 6934 亿 | 231 ms | 80 ms | **约 0.23 s** | **约 0.31 s** |
| 1024 | 1.43 万亿 | 477 ms | 80 ms | **约 0.48 s** | **约 0.56 s** |
| 2048 | 3.04 万亿 | 1.01 s | 80 ms | **约 1.0 s** | **约 1.1 s** |
| 4096 | 6.81 万亿 | 2.27 s | 80 ms | **约 2.3 s** | **约 2.4 s** |

若把 6 TOPS 理解成 6 TMAC/s（一次乘加只计一次运算），512 token 以上的运算时间大约减半，80 ms 这条底还在。

## 七、这套预测上板后会在哪里偏离

公式把三件做不到的事当成了已经发生。

1. **6 TOPS 是三核 INT8 的芯片峰值。** 128 token 的前向是 28 层、每层多块矩阵，逐块提交。小形状矩阵乘吃不满峰值，层间同步的时间在 56 ms 里是 0。
2. **80 ms 假设 128 个 token 合成一次大矩阵乘，每份权重只从 DDR 读一遍。** 运行时是算一块、再取下一块，权重被重复读取时 80 ms 不再是耗时。
3. **吐字这条硬一些。** 每 token 必须重读全部权重，和实现是否把 prompt 合成一个大 GEMM 无关。上板吐字应落在 13 token/s 附近或更低。**若明显高于 13 token/s，说明这块板的有效带宽高于本文用的 20 GB/s，而不是乘加公式算少了。**

因此：13 token/s 可以作为吐字的对照上限，短提示首帧的最快对照是 80 ms、串行对照是 140 ms。两列都还是吃满峰值、权重只读一遍的账，都不能当成预期耗时。第九节的两档 DDR 数据会把这个对照再收紧一次。

## 八、基准档实测

| 项 | 记录 |
|---|---|
| 日期 / 板子 / 内存 | 2026-10-04 / LubanCat-4（RK3588S）/ 7.7 GiB |
| DDR | 推理时升到本板最高时钟 1848 MHz（约 3696 MT/s） |
| rkllm 的 optimization_level | 运行时不打印。导出脚本记录为 1。官方表要求转换成 0 |
| 输入 / 生成 token 数 | 128（Prefill）/ 63（Generate） |
| 模型加载 + init | 冷启动 6954 ms；文件已在页缓存时 1906 ms |
| 首帧 | **458.70 ms**（三次 464.82 / 453.23 / 458.70） |
| 吐字 | **12.33 token/s**（三次 12.17 / 12.33 / 12.35） |
| 进程内存 | **1781.83 MB**（`max_context=4096`）。同模型把窗口改成 512 时是 1681 MB |
| 备注 | 官方表：378.31 ms / 16.69 token/s / 1689.21 MB。本板首帧慢 21%，吐字是官方的 74%，内存多约 93 MB |

和第六节的屋顶比：128 token 首帧实测 459 ms，边搬边算的 80 ms 和先搬完再算的 140 ms 都没碰到，慢在没吃满 6 TOPS。吐字 12.33 token/s 落在「约 13 token/s 或更低」这一侧。按 1.5 GB 权重反推，有效带宽约 18.5 GB/s，和 20 GB/s 的规划口径同一量级。

### 和官方表为什么不同

速度差拆成两笔。

1. **带宽档。** 官方定频脚本写 2112 MHz，本板频率表最高 1848 MHz，时钟比 87.5%。按这个比例把官方数折过来：吐字约 14.6 token/s，首帧约 432 ms。实测 12.33 和 459。带宽档吃掉吐字差距的大约一半、首帧差距的大约三分之二。64 位总线下 1848 MHz 的峰值带宽约 29.6 GB/s，若把 1848 误当成 MT/s，峰值只剩 14.8 GB/s，低于实测反推的 18.5 GB/s，对不上。
2. **导出档，剩下那截。** 官方 `benchmark.md` 要求 `optimization_level=0`，本文件由 toolkit 1.2.1 导出、脚本记的是 level 1，运行时不打印。扣掉带宽之后吐字还差约 16%（14.6 → 12.33），首帧还差约 6%（432 → 459 ms）。吐字每出一个 token 都要把权重再读一遍，level 1 的核更碎，重复读对吐字更重。

内存多出来的约 93 MB 不解释变慢。那是 `max_context=4096` 把 KV 按满窗预留了。同一模型窗口改成 512 时是 1681 MB，和官方 1689 MB 只差 8 MB；4096 比 512 多约 101 MB，折合每个 token 约 28 KB，与 FP16 KV 一致。生成开始时上下文只有 128 token，KV 约 3.5 MB，相对 1.5 GB 权重可以忽略。

1848 比 2112 低不是芯片新旧。鲁班猫 4 的主控是 RK3588S，NPU 仍是 6 TOPS，内存控制器仍是四通道。2112 MHz 是内存颗粒和 `ddr.bin` 的选配，野火规格书默认 1560 MHz 颗粒，2112 MHz 需要另定。本机频率表最高停在 1848 MHz，换一颗更新的 RK3588 不会改这张表。

## 九、调 DDR 时钟的首帧与吐字：把屋顶当预言来验

前八节把 20 GB/s 当成一个固定的数，第八节的 1848 MHz 只是碰巧落在本板最高档。同一块板、同一模型、同一 128 token 口径，把 DDR 时钟在频率表的两档之间对调一次，就能看出前八节那套账对不对。

| DDR 时钟 | 数据速率 | 峰值带宽 | 首帧（128 token） | 吐字 |
|---|---|---|---|---|
| 1068 MHz | 约 2136 MT/s | 约 17.1 GB/s | 611 ms | 9.20 token/s |
| 1848 MHz | 约 3696 MT/s | 约 29.6 GB/s | 412 ms | 14.57 token/s |
| 比值 | 1.73× | 1.73× | **快 1.48×** | **快 1.58×** |

### 吐字：一阶就够

时钟比 1.73×，吐字快 1.58×，涨幅是带宽比的 **92%**。剩下 8% 不是零。把每 token 时间拆成 `t = F + 1000×1.5 / 峰值带宽`，用两档解出 F ≈ **13.7 ms/token**（约 13%），等效流量 **1.62 GB**，比 1.5 GB 权重多出约 8%——多出来的是每 token 都要重读的文件头、缩放表和 KV。

两档各按 1.5 GB 反推有效带宽：

| DDR 档 | 吐字 | 反推有效带宽 | 占该档峰值 |
|---|---|---|---|
| 1068 MHz | 9.20 token/s | 约 13.8 GB/s | 81% |
| 1848 MHz | 14.57 token/s | 约 21.9 GB/s | 74% |

低频档的峰值占用反而更高（81% vs 74%）。这说明 DRAM 侧的时序开销随频率上升而变大，低频档没有那么多固定开销要摊进搬运时间里；不是低频档跑得更省。无论哪一档，第四节的 13 token/s 都偏保守。

### 首帧：不是纯带宽账

首帧只快 1.48×，比吐字慢一档。这 1.48× 里，权重的搬运只占很小一块：1.5 GB 在两个档的峰值下分别是 88 ms 和 51 ms，只差 37 ms，而实测差了 199 ms。

把首帧写成 `T = C + 1000·V / 峰值带宽`，用两点反解：

\[
611 = C + 1000V / 17.1 \qquad 412 = C + 1000V / 29.6
\]

得 C ≈ **139 ms**（与 DDR 频率无关），V ≈ **8.1 GB**（等效 DDR 流量）。权重 1.5 GB 只占这个流量的 19%。剩下 6.6 GB 是首帧期间真正在 DDR 上走的东西——按峰值带宽折算的等效量，含权重重读、激活与 KV 的往返、CPU 侧 runtime 的调度和采样、DRAM 访问效率损失放大的部分。具体成分要 profiler 拆，两个点只能定出量级。

结论落在第九节开头那句话：吐字是纯带宽账，一阶就解释得下；首帧是复合账，第七节第 2 条「权重被重复读取时 80 ms 不再是耗时」在板上是真的，而且比想象的严重。

### 和第八节的 12.33 token/s 不一致

第八节 1848 MHz 档记的是 12.33 token/s，本节同档记 14.57 token/s，差 18%。本节这组是把 DDR 时钟作为唯一变量对照测出来的，两档同一口径；两组数不在同一轮次、其余条件未逐项对齐，差异只能记为待复测的开放项，不在正文里替它编原因。要拿 14.57 去对官方表，得先把口径统一。

| DDR 档 | 首帧 | 吐字 | 相对 1068 MHz |
|---|---|---|---|
| 1068 MHz | 611 ms | 9.20 token/s | 基准 |
| 1848 MHz | 412 ms | 14.57 token/s | 首帧 1.48×，吐字 1.58× |

**验收口径**：吐字涨幅应落在带宽比的 85% 以上（这条成立，92%）；首帧涨幅应低于吐字涨幅（这条也成立，1.48 < 1.58）。若哪天首帧涨幅追上或超过吐字，说明它已经退化成纯搬运问题，第五节那两笔的加法就可以直接用。

> 实测：1848 MHz 档首帧 459 ms、吐字 12.33 token/s。DDR 从 1068 MHz 提到 1848 MHz（带宽比 1.73×）后，首帧 611→412 ms（1.48×）、吐字 9.20→14.57 token/s（1.58×，等于带宽比的 92%）。吐字卡带宽这条得到验证；首帧只跟上 1.48×，两点反解出与 DDR 无关的固定开销约 139 ms、等效 DDR 流量约 8.1 GB，权重只占 19%。
