# RK1828与S100P大模型解码性能底层对比

**核心摘要**：同样是跑 7B 模型，地瓜 S100P 标称 80–128 TOPS 却只有 5–6 token/s，RK1828 仅 20 TOPS 却能到约 50 token/s，差距约一个数量级。根因不在算力，而在三层硬件事实：存储层次（共享 LPDDR vs 独占堆叠 DRAM）、量化配方（Q8 约 7GB vs W4A16 约 3.5GB）、计算阵列形态（视觉 GEMM 友好 vs Transformer 解码友好）。结论是语音全套应走 RK3588 主控 + RK1828 只跑 LLM 的异构拆分，而非单卡塞满。

> 数据口径说明：S100P 数据来自本知识库已落地的实测基准；RK1828 数据来自公开评测，尚未在本环境实测。

---

## 一、问题：标称 TOPS 高，为什么出字反而慢

当前链路是两端分体：LubanCat RK3588 负责采音 / VAD / 播放；推理机 S100P（8.3 GB 共享内存）同机跑 ASR（SenseVoice）、TTS（WeTTS/Piper/MOSS）、LLM（Qwen2.5-7B Q8）。

实测瓶颈有三条：

| 瓶颈 | 实测数据 |
|---|---|
| LLM 解码吞吐 | 仅 **5–6 token/s**（Q8，chunk=256，cache=2048） |
| Prefill 切块代价 | 每多一块 256 token，TTFT 约 **+654 ms**（658→1312→1967 ms），是 BPU 映射约束而非文本本身贵 |
| 三服务抢内存 | ASR 独占时 TTFR 约 400 ms，与 LLM/TTS 同跑漂到 **1.8–2.0 s** |

对话体感差的主因是「出字慢 + 带宽被抢」，不是 ASR/TTS 引擎选错——WeTTS 短句首包 90–250 ms，已经跟手。

核心结论一句话：**端侧对话的快慢，不看标称 TOPS，也不看内存容量（GB），而看每生成一个 token，能不能尽快把整份 7B 权重从存储扫进计算单元。**

| 决定项 | S100P（现状） | RK1828 |
|---|---|---|
| 存储角色 | 8.3 GB 系统 LPDDR，CPU/BPU/ASR/TTS 共用 | 5 GB 片上 3D 堆叠 DRAM，NPU 独占 |
| 7B 配方 | Q8，权重约 7 GB / token 扫描量 | W4A16，权重约 3.5 GB / token 扫描量 |
| 解码形态 | BPU 偏视觉 / 分块 Prefill | NPU 按 Transformer 解码设计 |
| 短句 TTFT | 实测约 658 ms | 公开约 160–334 ms |
| 解码吞吐 | 实测 5–6 token/s | 公开约 50–52 token/s |

## 二、原理：解码为什么是带宽墙

一次 Transformer 前向 = 权重矩阵 × 输入激活。对话分两段，算力密度完全不同：

| 阶段 | 输入形态 | 运算 | 瓶颈 |
|---|---|---|---|
| Prefill | 整句 prompt 一次送入 | 矩阵×矩阵（GEMM），算术密度高 | 算力（TOPS） |
| Decode | 每次只追加 1 个 token | 矩阵×向量（GEMV），读完权重只做极少乘法 | **访存带宽** |

生成第 N 个字时，几乎要把整份权重再扫一遍。粗算 7B 一次解码：

```text
计算量 2×7e9 乘加 ÷ 100 TOPS ≈ 0.14 ms   ← 计算上限
搬运 7 GB 权重 ÷ 42 GB/s    ≈ 167 ms     ← 访存下限 → 约 6 token/s
```

时间钉死在访存下限上。**把 TOPS 再翻一倍，出字速度几乎不动；把有效带宽翻倍，或把权重减半，才会线性变快。**

### 存储和计算为什么必须搬运

芯片里两种硅职能分家：

- **DRAM（内存颗粒）**：只会按地址读写比特，不会做乘法。S100P 是封装外 LPDDR；RK1828 是堆叠在 NPU 旁边的 3D DRAM，仍是「存」。
- **MAC 阵列（NPU/BPU 里的乘法器网格）**：做 `a×b+c`，但只看自己门口寄存器里的数。片上 SRAM 只有 MB 级，物理上放不下 3.5–7 GB 的整模。

所以推理必须切成「DRAM → 总线搬运 → 片上 SRAM → 寄存器 → MAC 阵列」的流水，不搬过来，乘法器面前是空的。S100P 的 80–128 TOPS、RK1828 的 20 TOPS，数的都是这张网格的 INT8 乘加吞吐——**视觉 CNN/YOLO 是高密度卷积，BPU 为此设计；逐字对话的 GEMV 不是同一类负载**。两家都不是存内计算，仍是「先搬后乘」，差别只在搬运路径有多短、带宽有多高。

## 三、快慢由三层决定

### 第一层：物理带宽（最关键）

| | S100P 8.3 GB | RK1828 5 GB |
|---|---|---|
| 类型 | SoC 外挂 LPDDR，走封装外总线 | 3D 堆叠 DRAM，贴在 NPU 旁边 |
| 服务对象 | Linux + CPU + BPU + ASR + TTS | 仅该 NPU 上的模型 |
| 峰值量级 | 典型几十 GB/s，还被多主设备分 | 标称 TB/s 级，有效数百 GB/s 档 |

用实测和公开吞吐反推有效带宽：

```text
有效带宽 ≈ 解码 token/s × 每个 token 必须扫描的权重大小

S100P ：  6 token/s × ~7 GB（Q8）  ≈  42 GB/s
RK1828： 52 token/s × ~3.5 GB（W4）≈  180 GB/s
```

有效搬运差约 **4 倍**——存储离计算更近、总线独占、专为反复扫权重的 GEMV 铺带宽，这是硬件上最硬的一条。

### 第二层：每个 token 要搬多少字节（量化）

写法 WnAm：W = 权重比特数，A = 激活比特数。

| 配方 | 权重存储 | 激活计算 | 7B 权重约 | 位置 |
|---|---|---|---|---|
| Q8 | 约 8 bit | 接近 INT8 乘 | ~7 GB | S100P 保效果 |
| W4A16 | 4 bit 存储 | 解回 16 bit 再乘 | ~3.5 GB | RK1828 跑 7B 标配 |

两个关键认知：

1. **W4A16 不是整个网络用 4 bit 算**。4 bit 只有 16 档，只负责把静态权重塞进 5 GB；乘法仍在 16 bit 上做，避免激活里的 outlier 打歪整层。
2. **换 W4A16 是用精度换容量**，不是「4 bit 比 8 bit 更准」。Q8 的 7 GB 物理上放不进 RK1828 的 5 GB（还要扣 KV cache）。

同样 50 GB/s 总线：扫 7 GB 约 7 字/秒，扫 3.5 GB 约 14 字/秒。公开的 ~50 token/s 里，**约一半来自权重更瘦，一半来自总线更快**。KV cache 同住一块内存，W4A16 的 7B 装进 5 GB 后上下文通常只能开 1k–2k token；再往同卡塞 ASR/TTS 会直接 OOM。

### 第三层：计算单元是为谁画的

S100P BPU 的视觉痕迹写在基准里：Prefill 必须 256 token 一块提交，短句 TTFT 钉在 ~658 ms 与字数无关——这是「一次喂一厚叠、吃满阵列」的 GEMM 友好切法；轮到 Decode 输入变成宽度 1 的向量，阵列利用率塌掉，只剩带宽。

RK1828 的 NPU 按 LLM/VLM 协处理设计：权重常驻高带宽片上、INT4/FP16 混合、反复做 GEMV。CNN 类任务公开对比里往往不如 RK3588 自带的 6 TOPS——它适合当「对话加速卡」，不适合当通用视觉 NPU。

软件栈也顺着硬件走：地瓜是 XLM/OpenExplorer，RK1828 是 **RKNN3**（与 RK3588 的 RKNN2 不是同一套），现有 `.hbm`、SenseVoice GGUF、WeTTS `libtts.so`、MOSS ONNX **不能直接搬过去**。

### 三层叠乘 ≈ 10 倍

```text
带宽比     ~180 / 42 ≈ 4.3×
每字字节比  7 / 3.5  ≈ 2.0×
────────────────────────
解码吞吐比          ≈ 8～10×
```

与「5–6 → 50–52 token/s」一致。没有第四个神秘加速器：就是**更近的存储 + 更少的搬运 + 对准 GEMV 的阵列**。

## 四、正确用法：异构拆分，不是单卡塞满

RK1828 只有 5 GB，7B W4A16 约 3.5 GB，剩余空间只够 KV，不够再常驻 ASR + TTS；公开 CNN 成绩也不支持把识别模型放上去。「更适合部署语音大模型」指的是拆：

```text
RK3588 CPU     VAD / 采播 / WebSocket / 打断
RK3588 NPU     ASR（RKNN）+ 轻量 TTS（Piper / Matcha，首包约 140 ms）
RK1828 DRAM    仅 7B 对话（W4A16，独占带宽）
```

相对现状的收益：

1. LLM 从 5–6 token/s 提到约 50 token/s，第一句能立刻推 TTS
2. 8.3 GB 上的三模型争抢消失，ASR/TTS 用 RK3588 自己的内存和 6 TOPS
3. 端侧本就是 RK3588，加速卡插 M.2/PCIe 后采音和推理收成一块板，少一跳局域网

### TTS 是否需要第二张 RK1828

默认不需要：

- RK3588 上 Piper/Matcha 首包约 **140 ms**，与当前 WeTTS 同档，体积仅百 MB 级
- Qwen3-TTS 1.7B 在 RK1828 上公开约 **1.1 s 首包、常驻 ~1.9 GB**，音质更好但更慢；与 7B（~3.5 GB）相加超 5 GB，同卡放不下
- 公开同卡共存方案是 **4B + TTS 1.7B ≈ 4.6 GB**，且单 NPU 必须串行，LLM 出词与 TTS 合成不能同时
- 第二张卡只在「必须 7B 且必须大模型 TTS 同时常驻」时才有硬件意义；多卡官方叙事是切分更大的 LLM，不是「一卡聊天、一卡发音」
- MOSS-TTS-Nano 这类自回归 + 自定义算子转 RKNN 风险高，短中期要音质应评估 Qwen3-TTS，不是硬搬现有 ONNX 上 NPU

## 五、换板必须接受的代价

- **精度**：W4A16 相对 Q8，指令遵循、数字、代码可能变差，要业务回归，不能默认「更快且一样准」
- **上下文**：5 GB 硬顶，长 RAG 会先碰到 KV 而不是算力
- **工具链**：RKNN2（3588）与 RKNN3（1828）两套，转换在 x86 主机做，板端只跑 runtime
- **S100P 不该被整机替换**：Cortex-R52 运动闭环、视觉大算力、HoloBrain 类具身仍是它的主场；语音盒可以是 RK3588+RK1828，机器人大脑留 S100P

## 六、选型对照

| 目标 | 建议 |
|---|---|
| 压对话延迟、量产语音盒 | RK3588 + 1×RK1828 只跑 7B；TTS 用 Piper/Matcha |
| 更自然的大 TTS，可接受 3B/4B 对话 | 1×RK1828 同卡 4B + Qwen3-TTS（已有共存数据） |
| 必须 7B 且大 TTS 常驻 | 再评估 2×RK1828（插槽、12V、散热、双进程调度自建） |
| 视觉 + 运动 + 语音一体 | 保留 S100P；LLM 可迁走，不必整机替换 |
| 最不该做 | 三模型都塞 RK1828；或指望 3588 的 6 TOPS 单独跑 7B |

---

## 七、一句话总结

**S100P 用大容量共享 LPDDR 喂给偏视觉的高 TOPS BPU；RK1828 用小容量、高带宽、独占的堆叠内存喂给解码用的 GEMV。** 语音交互的 LLM 落在第二种形态上，所以同样 7B，出字能快一个数量级；而容量决定「塞不塞得下」，带宽和是否独占才决定「每个字出得有多快」。
