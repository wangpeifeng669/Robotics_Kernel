# Qwen3-TTS-0.6B 公司主机 4090 独占部署效果验证

## 摘要

此前在阿里云 ECS（RTX 4090）部署 Qwen3-TTS-0.6B 时，因与 Qwen3.5-35B LLM 共用同一块 GPU，TTS 首帧延迟劣化至 ~280 ms（公网），严重影响实时播报体验。本次在公司主机（同型号 RTX 4090）上以 TTS 独占 GPU 方式重新部署并测试，单路 HTTP 首帧降至 **68 ms**、WebSocket 首帧 PCM 降至 **46 ms**，1–6 路短句并发首帧均在 200 ms 以内。数据证实：消除 LLM 竞争后，4090 上 TTS 延迟回归官方参考水平，8 路以上瓶颈来自引擎流水线而非算力或显存。

---

## 一、背景与问题回顾

### 1.1 阿里云 ECS 部署的问题

此前在阿里云 ECS（Xeon Gold 6462C + RTX 4090 46 GB）上部署 Qwen3-TTS-12Hz-0.6B-CustomVoice（vLLM-Omni v0.20.0），同卡还运行 Qwen3.5-35B LLM。为让路给 LLM，TTS 的 `--gpu-memory-utilization` 被限制为 0.10。

实测 TTS 首帧延迟：

| 指标 | 官方参考 | 阿里云 ECS（TTS + LLM 共存） | 劣化幅度 |
|------|----------|------------------------------|----------|
| HTTP 流式首字节 | ~97 ms | ~280 ms | +183 ms |
| WebSocket 首帧 PCM | — | ~259 ms | — |

**根因**已在 [三类模型部署策略](./2026-06-10_asr-llm-tts-三类模型部署策略.md) 中详细分析：LLM Prefill 阶段算力霸占（Compute-Bound）+ Decoding 阶段显存带宽绞杀（Memory-Bound），叠加公网 RTT，导致 TTS Kernel 在 CUDA 工作队列中长期排队挨饿。直觉上 4090 算力远超本地 8 GB 小卡，TTS 应更快——实测恰恰相反，算力过剩并不能免疫资源争抢。

### 1.2 本次验证目标

在公司主机（同型号 RTX 4090）上以 **TTS 独占 GPU**（无 LLM 共存）方式部署，回答两个问题：

1. 消除 LLM 竞争后，TTS 首帧延迟能恢复到什么水平？
2. 独占模式下，`gpu-memory-utilization` 默认值与 0.10 对延迟和并发有何差异？

## 二、部署环境对比

| 维度 | 公司主机（`qb`） | 阿里云 ECS（对比） |
|------|------------------|-------------------|
| GPU | RTX 4090（49140 MiB） | RTX 4090（46 GB） |
| GPU 共存负载 | **TTS 独占** | TTS + Qwen3.5-35B LLM |
| 推理引擎 | vLLM-Omni v0.20.0 | vLLM-Omni v0.20.0 |
| 访问路径 | `127.0.0.1:8091` 回环 | 公网 IP:8091 |
| 网络 RTT | ~0 ms（回环） | 20–60 ms（公网单程） |

两台主机 GPU 型号一致，核心差异是：公司主机 TTS 独占 GPU 且走回环网络，阿里云 ECS 则 TTS 与 LLM 共存且走公网。这构成了天然的对照实验——隔离 LLM 竞争这一变量，观察 TTS 延迟的变化。

## 三、gpu-memory-utilization 基准对比

为隔离参数影响，先在 TTS 独占条件下对比默认值（~0.9）与 0.10 两种配置。完整基准数据详见 [原始测试报告](C:/Users/wangp/Downloads/GPU_MEMORY_UTILIZATION_BENCHMARK.md)。

### 3.1 引擎 KV cache 对比

| 配置 | gpu-memory-utilization | KV cache | 理论最大并发（4096 tokens/req） | TTS 空闲显存占用 |
|------|------------------------|----------|-------------------------------|------------------|
| 默认 | ~0.9 | 12.26 GiB | 28.03× | ~20.2 GB |
| 低显存 | 0.10 | 2.8 GiB | 6.39× | ~10.5 GB |

降低 `gpu-memory-utilization` 主要压缩 Talker Stage 的 KV cache 池，空闲时显存从 ~20 GB 降至 ~10 GB，为同卡部署 LLM 留出 ~10 GB 余量。

### 3.2 单路首帧延迟（TTFA）

首帧 = 收到第一块可播放 PCM 的时间（Time To First Audio）。

| 指标 | 默认 (~0.9) | 低显存 0.10 | 差值 |
|------|-------------|-------------|------|
| HTTP 流式首字节 | **68** ms (67–70) | **69** ms (67–73) | +1 ms |
| WS audio.start | **3** ms | **3** ms | 0 ms |
| WS 首帧 PCM | **46** ms (44–52) | **48** ms (45–55) | +2 ms |

**结论**：单路 warm 状态下，两种配置首帧延迟几乎一致（±2 ms 以内）。`gpu-memory-utilization` 主要控制 KV cache 容量，对无排队的单用户首帧影响有限，符合预期。

### 3.3 并发压测

并发场景使用 HTTP 流式短句，每路独立 POST `/v1/audio/speech`。

| 并发路数 | 默认 TTFA mean | 0.10 TTFA mean | 推荐场景 |
|----------|----------------|----------------|----------|
| 1 ✅ | 68 ms | 70 ms | 实时播报基线 |
| 2 ✅ | 110 ms | 106 ms | 双路实时 |
| 4 ✅ | 144 ms | 129 ms | 短句批处理 |
| 6 | 184 ms | 166 ms | 短句批处理上限 |
| 8 ⚠️ | 964 ms | 955 ms | 超出真并行，严重排队 |

**观察**：

- **1～6 路**：两种配置 TTFA 均在 70～184 ms 区间，差异在测量噪声范围内
- **8 路**：两配置 TTFA mean 均飙升至 ~955 ms，wall time 2.4～2.8 s
- **理论 KV 并发上限**：默认 28.03× vs 0.10 仅 6.39×；但短句压测在 6 路内仍未触顶，8 路断崖来自引擎流水线瓶颈而非 KV cache 耗尽

## 四、消除 LLM 竞争后的效果验证

### 4.1 单路首帧延迟：三环境横评

| 环境 | GPU 负载 | 网络 | HTTP 首帧 | WS 首帧 PCM |
|------|----------|------|-----------|-------------|
| 官方参考 | 理想条件 | — | ~97 ms | — |
| 局域网主机（8 GB 小卡） | TTS 独占 | 回环 | ~118 ms | ~84 ms |
| **公司主机（4090 独占）** | **TTS 独占** | **回环** | **~68 ms** | **~46 ms** |
| 阿里云 ECS（4090 共存） | TTS + LLM 共存 | 公网 | ~280 ms | ~259 ms |

公司主机 4090 独占部署后：

- HTTP 首帧 **68 ms**，比阿里云共存方案的 280 ms **快 4.1 倍**，甚至低于官方参考 97 ms（回环无网络开销）
- WS 首帧 PCM **46 ms**，比阿里云共存方案快 **5.6 倍**
- 已逼近 4090 独占条件下的理论下限

### 4.2 延迟改善归因

从 ~280 ms 降至 ~68 ms，~212 ms 的改善来自三个层面：

| 改善来源 | 贡献估计 | 说明 |
|----------|----------|------|
| 消除 LLM Prefill 算力霸占 | ~80–120 ms | TTS Kernel 不再在 CUDA 队列中排队等待 LLM Prefill 占满 SM |
| 消除 LLM Decoding 带宽绞杀 | ~60–100 ms | TTS 权重读取不再被 35B 模型高频搬运阻塞 |
| 回环替代公网 RTT | ~20–60 ms | 无网络往返开销 |

三者叠加解释了延迟改善的量级。其中前两项是 LLM 竞争消除的直接收益，第三项是部署位置变更的附带收益。

### 4.3 并发能力对比

| 并发路数 | 阿里云 ECS（TTS+LLM 共存）TTFA | 公司主机（TTS 独占）TTFA | 改善倍数 |
|----------|-------------------------------|--------------------------|----------|
| 1 路 | ~280 ms | ~68 ms | 4.1× |
| 4 路 | ~297–313 ms | ~129–144 ms | ~2.2× |
| 6 路 | ~327–349 ms | ~166–184 ms | ~1.9× |

> 注：阿里云 8 路数据为公网+共存条件下 ~363–410 ms，公司主机独占 8 路为 ~955–964 ms。两者测试条件不同（公网 RTT 摊薄了排队感知），不具备直接可比性。公司主机 8 路的断崖式延迟来自引擎流水线瓶颈，详见第五章。

## 五、8 路断崖式延迟的根因

独占模式下 1–6 路表现优异，但 8 路时 TTFA 骤升至 ~955 ms，两种 `gpu-memory-utilization` 配置表现一致。这不是算力或显存不足，而是 **vLLM-Omni 引擎流水线调度触顶**。

### 5.1 两阶段流水线架构

Qwen3-TTS 在 vLLM-Omni 中为两阶段串行流水线（容器内 `qwen3_tts_uniproc.yaml`）：

```text
Stage 0 Talker (0.6B)  →  生成 speech tokens
        ↓ SharedMemory 异步 chunk
Stage 1 Code2Wav       →  tokens 转 PCM
```

| Stage | 组件 | max_num_seqs | max_num_batched_tokens |
|-------|------|--------------|------------------------|
| 0 | Talker | 10 | 512 |
| 1 | Code2Wav | **1** | 65536 |

- Talker 最多 10 路并行，8 路未触顶
- **Code2Wav 同一时刻只处理 1 路**（架构设计，与 gpu-memory-utilization 无关）
- 首帧 PCM 需 Talker 产出首批 token **且** Code2Wav 完成首次 vocode

### 5.2 断崖成因

8 路短句同时到达时，prefill 总量可能超过 Talker 的 `max_num_batched_tokens=512`，需多轮 batch 才能完成全部 prefill。在首轮 prefill 完成前，任何一路都出不了首帧 PCM。叠加 Code2Wav 单槽排队，首帧集体延迟至 ~1 s。

粗算：

```text
4 路 × ~100 tokens ≈ 400  < 512  → 一轮 prefill，首帧快
6 路 × ~100 tokens ≈ 600  > 512  → 至少两轮，开始变慢
8 路 × ~100 tokens ≈ 800  > 512  → 多轮 prefill + Code2Wav 单槽排队 → 首帧 ~1 s
```

| 并发 | TTFA mean | 现象 |
|------|-----------|------|
| 1 | ~68 ms | 无排队 |
| 2–4 | ~110–144 ms | 轻微排队 |
| 6 | ~166–184 ms | 各路 TTFA 开始离散（132–259 ms） |
| **8** | **~955 ms** | 全部 900–1075 ms，集体变慢 |

8 路时各路 TTFA 均在 927～1075 ms，说明不是「几路快、几路慢」，而是**所有请求一起在等同一轮调度/流水线排空**。

### 5.3 为何调低 gpu-memory-utilization 无济于事

8 路断崖的瓶颈来自 Stage 配置中的硬限制（`max_num_seqs`、`max_num_batched_tokens`、Code2Wav 单槽），**与 KV cache 大小无关**。`gpu-memory-utilization` 只影响长序列 KV 容量，不改变上述调度参数。

| 说法 | 是否成立 |
|------|----------|
| 模型无法生成 8 路音频 | ❌ 8 路均成功返回 |
| 引擎无法低延迟支持 8 路实时 | ✅ 首帧 ~1 s，不满足实时 |
| 0.6B 算力不够 | ❌ 4090 上非算力瓶颈 |
| Code2Wav 单路 + prefill batch 限制 | ✅ 主因 |

**结论**：模型能处理 8 路，但当前 vLLM-Omni Qwen3-TTS 部署配置下，8 路同时到达不适合低延迟实时播报。若要突破 8 路以上低延迟并发，需调整引擎层参数（如 `--max-num-seqs`、`max_num_batched_tokens` 或 Code2Wav 多实例），而非继续调 `gpu-memory-utilization`。

### 5.4 短句压测为何测不出 KV cache 差异

启动日志中的 `Maximum concurrency for 4,096 tokens per request: 6.39× / 28.03×` 含义是：假设每路请求占满 4096 tokens 时 KV cache 能同时容纳多少路。本次压测句子实际 token 远小于 4096（粗估几十～几百 token）：

| 每路实际 token | 0.10 配置 KV 层面可撑路数 |
|----------------|--------------------------|
| ~100 tokens | ~260 路 |
| ~500 tokens | ~52 路 |
| **4096 tokens** | **6.39 路** ← 日志数字 |

因此 1–6 路短句并发时，两种配置的 KV cache 均未触顶。需使用长文本（每路 3000+ 字 × 7 路并发）才能测出 KV cache 差异。

## 六、gpu-memory-utilization 选型建议

| 部署场景 | 推荐 gpu-memory-utilization | 理由 |
|----------|----------------------------|------|
| TTS **独占** GPU（公司主机 4090） | 默认（不指定） | 首帧相同，KV cache 更大，长文本并发更高 |
| TTS 与 **LLM 同卡**共存（阿里云 ECS） | **0.10** | 节省 ~10 GB 显存；短句 1–6 路首帧无明显损失 |
| 单路/双路实时播报 | 0.10 或默认均可 | 首帧 ~50–70 ms，满足低延迟 |

**核心认知**：`gpu-memory-utilization` 影响的是「KV cache 能同时容纳多少路**长序列**」，不是「短句能低延迟并发多少路」。本次短句压测未打满 KV cache，故首帧几乎无差异。

## 七、对比总结

| 维度 | 阿里云 ECS（TTS+LLM 共存） | 公司主机（TTS 独占） | 改善 |
|------|---------------------------|----------------------|------|
| 单路 HTTP TTFA | ~280 ms | ~68 ms | 4.1× |
| WS 首帧 PCM | ~259 ms | ~46 ms | 5.6× |
| 空闲 GPU 显存 | ~10 GB（0.10 限制） | ~20 GB（默认） | 独占可用满 |
| KV cache 容量 | 2.8 GiB / 6.4× | 12.26 GiB / 28× | 独占更大 |
| 实时并发（TTFA < 200 ms） | 1–6 路（公网含 RTT） | 1–6 路（回环） | 绝对延迟更低 |
| 8 路短句 | ~363–410 ms | ~955 ms | 引擎瓶颈，不可直接比较 |

---

## 八、总结

1. **消除 LLM 竞争是 TTS 低延迟的前提**：4090 独占部署后首帧从 ~280 ms 降至 ~68 ms，验证了此前根因分析——算力霸占 + 带宽绞杀是共存方案延迟劣化的主因，而非 4090 算力不足。
2. **独占模式下 1–6 路可满足实时播报**：短句 TTFA < 200 ms，WebSocket 首帧 PCM 低至 46 ms，优于官方参考值。
3. **8 路瓶颈在引擎流水线，不在硬件**：Code2Wav 单槽 + prefill batch 上限 512 是天花板，需引擎层调参突破，与 `gpu-memory-utilization` 无关。
4. **gpu-memory-utilization 对短句首帧无感**：默认与 0.10 差异 ±2 ms；选型取决于是否需要与 LLM 共存，而非延迟优化。
