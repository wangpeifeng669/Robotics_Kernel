# RK3588模型打包工具链选型

核心摘要：RK3588 上没有一把万能锤子，模型类型不同，走的打包工具链完全不同。核心分界线只有一条——是不是自回归 LLM：LLM 走 rknn-llm 产 `.rkllm`；常规网络走 RKNN-Toolkit2 产 `.rknn`；算子有缺口的复杂模型（TTS/ASR 全流水线）拆图，NPU 段用 Toolkit2、CPU 段留 ONNX。本文给出三条工具链对照、背后原因，以及一个模型到手后的五步决策顺序。

---

## 一、三条工具链对照

| 模型类型 | 转换工具（PC 端） | 产物 | 板上运行时 |
|---|---|---|---|
| LLM（Qwen/Llama/DeepSeek 等自回归生成式） | **rknn-llm**（独立工具链） | `.rkllm` | librkllmrt / rkllm-server |
| CNN / ViT / 常规网络（视觉、VAD、音频特征提取、embedding） | **RKNN-Toolkit2** | `.rknn` | librknnrt（C/C++）或 rknn-toolkit-lite2（Python） |
| 算子有缺口的复杂模型（TTS/ASR 全流水线） | 拆图：能上 NPU 的子图用 Toolkit2，其余留在 CPU 跑 ONNX | 混合（`.rknn` + `.onnx`） | 板上 C/Python 串联调度 |

三个产物文件互不通用：`.rkllm` 只能被 librkllmrt 加载，`.rknn` 只能被 librknnrt / toolkit-lite2 加载。选错工具链的典型症状是"转出来了但板上加载报格式错误"，此时不是模型的问题，是线走错了。

## 二、为什么 LLM 必须单独一条线

Toolkit2 是"整图一次性编译"的思路：图定死、权重定死、一次推理一次输出。而 LLM 解码是另一种计算形态：

- **GEMV 逐 token 循环**：解码阶段每吐一个 token 都要把全部权重过一遍，算子形态与 CNN 的 GEMM 批处理完全不同；
- **KV Cache 逐帧读写**：缓存随对话增长，需要运行时动态管理显存/内存，这是"编译期定死"的 Toolkit2 管不了的；
- **LLM 专属量化配方**：W4A16 等格式与 Toolkit2 的 w8a8 系列是两套体系（详见《RKNN-Toolkit2-2.3.2-量化打包类型与选型》）。

所以瑞芯微把 LLM 拆成独立项目 rknn-llm。这不是 Toolkit2 版本新旧问题，试图用 Toolkit2 转 LLM 本身就是方向错误。RK3588 8GB 内存上跑 LLM（如 Qwen2.5-1.5B INT4），直接走 rknn-llm。

## 三、一个模型到手后的五步决策顺序

### 第 1 步：判断类型

自回归文本生成（输入 token 序列、输出下一个 token）→ rknn-llm，决策结束。其余全部继续往下走。

### 第 2 步：导出 ONNX，对算子支持表

用 Toolkit2 的算子支持表逐个核对 ONNX 图里的算子：

- **算子全支持 + 形状可定死** → 整图转 `.rknn`，结束。Silero VAD 走的就是这条，FP16 一把过（见《SileroVAD在RK3588上的CPU与NPU实测对比》）。
- **有缺口算子**（样条查找、NonZero、CumSum、GatherND、Range 等常出现在音频生成类模型）→ 进入第 3 步拆图。

### 第 3 步：拆图，CPU/NPU 分工

判据只有两条：**算子在支持表里、动态 shape 能冻死**。VITS 转换就是典型：整图 4896 节点无法单收一个 rknn，最终 text_encoder + 时长预测留 CPU 跑 ONNX，flow + decoder 收成 flow_decoder.rknn 上 NPU，板上串联调度（见《vits-zh-aishell3转RKNN实测》《RK3588上VITS切分推理与原生ONNX对比》）。

### 第 4 步：选量化档

RK3588 的菜单里只有 **FP16 / w8a8 / w16a16i** 三档可放行（w8a16、w4a16 是 RK3562/RK3576 的）。选型顺序：

1. 默认 FP16 起步，先保证精度闭环；
2. 体积或带宽敏感再降 w8a8，但必须过误差预算（余弦相似度、最大绝对误差双指标）；
3. w8a8 被精度拒绝时试 w16a16i，仍不行就说明该模型对量化敏感，接受 FP16 或换模型。

细账见《RKNN-Toolkit2-2.3.2-量化打包类型与选型》。

### 第 5 步：选板上运行时

- **C/C++ 部署**（产品化）→ librknnrt.so，性能最好，进主程序无 Python 依赖；
- **快速验证 / Python 环境**（Python≥3.7 可用）→ rknn-toolkit-lite2，注意它**只管推理不管转换**，转换永远在 PC 端 Toolkit2 做。

## 四、一条速记

> **LLM 走 rknn-llm，常规网络走 Toolkit2，转不动的拆图 CPU/NPU 分工。**

配套记忆：量化档位看芯片放行矩阵，板上运行时按 C++/Python 分。这条链路与 9 月底的 VAD 实测、量化选型、VITS 拆图三篇正好拼成完整的 RK3588 落地路径：**选线（本文）→ 转换与量化（量化选型篇）→ 拆图实操（VITS 篇）→ 性能判决（VAD/HiFiGAN 实测篇）**。

## 延伸：非 Transformer 架构的例外

RWKV 这类线性 RNN 没有独立工具链，也不适合直接整图转 RKNN——恒定 State 的递推形态既不是 CNN 的静态图，也不是标准 LLM 的 KV Cache。实际路径是 rwkv.cpp（CPU）或 ONNX 分段转 RKNN（见《RWKV模型原理与端侧部署》）。遇到新架构时，判断依据仍是同一条：**计算形态决定工具链，而不是模型名气决定工具链**。
