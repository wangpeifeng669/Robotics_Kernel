# 端侧语音交互部署差异与 NPU/BPU 架构解析

**核心摘要**：PC 端部署语音交互（ASR + LLM + TTS）追求表现力与大模型能力，端侧部署则在算力、内存、功耗的硬约束下做平衡。端侧引入 NPU/BPU 是为了在功耗墙、内存墙、成本墙的夹击下获得可用的神经网络推理效率，但其高度定制化的算子支持也构成了模型移植的生死线。

---

## 一、PC 端与端侧部署的核心差异

### 1.1 算力与生态

| 维度 | PC 端部署 | 端侧部署（RK3588 / 地瓜 S100P） |
| :--- | :--- | :--- |
| 典型算力 | 数十至上百 TFLOPS（FP16/FP32） | RK3588 约 6 TOPS@INT8；地瓜 S100P 十几至几十 TOPS@INT8 |
| 主力生态 | CUDA、PyTorch、TensorRT、vLLM、Ollama | RKNN-Toolkit2（瑞芯微）、Hobot Toolchain（地瓜） |
| 异构分工 | GPU 一统天下 | CPU 负责调度/音频前处理/VAD/通信，NPU/BPU 负责矩阵推理，GPU 偶尔参与前后处理 |

端侧的关键特征是：**算力以 INT8/INT4 为主，FP16 能力极弱**。这直接决定了模型选择和量化策略。

### 1.2 语音 Pipeline 各段差异

#### ASR

- **PC 端**：可跑 Whisper Base/Large FP16，连续流式识别，对延迟容忍度较高。
- **端侧**：多用 FunASR（Paraformer）或 Whisper.cpp 量化版，必须通过 `rknn-toolkit2` 等工具固化并量化为 INT8。VAD 必须精准，否则无效触发会大量浪费端侧算力。

#### LLM

- **PC 端**：7B、14B 模型可轻松运行，FP16 或 INT4/INT8 AWQ 量化，Streaming 可达数十 Token/s。
- **端侧**：RK3588 通常只能承载 1.5B–3B 模型（如 Qwen2.5-1.5B/3B、Phi-3），且需 INT4 量化。首字延迟（TTFT）受 Prefill 阶段内存带宽限制，必须严格控制上下文窗口和 RAG 召回文本量。

#### TTS

- **PC 端**：可用 CosyVoice、ChatTTS 等生成式大模型，表现力极强。
- **端侧**：生成式 TTS 很难实时，通常回归 VITS、Sherpa-onnx（Matcha-TTS）或轻量化剪枝模型。为了掩盖推理延迟，需要 Chunk-based 推理，LLM 每输出 3–5 个字就触发 TTS 吐音频流，甚至引入语气词垫音。

### 1.3 全维度对比

| 维度 | PC 端部署 | 端侧部署 |
| :--- | :--- | :--- |
| 典型模型组合 | Whisper-Base + Qwen-7B + CosyVoice | FunASR/Whisper-Tiny + Qwen-1.5B（INT4）+ VITS |
| 精度损失 | 几乎无损 | INT4/INT8 量化后指令遵循与长文本逻辑会下降 |
| 内存/显存 | 8GB–24GB+ 独立显存 | 共享内存，RK3588 顶配 16GB/32GB，极易 OOM |
| 首字感官延迟 | 可 < 800ms | 优化极限约 1.0s–1.5s |
| 功耗与散热 | 200W–500W+，主动风扇 | 5W–15W，可被动散热 |
| 网络依赖 | 离线/云端混合皆可 | 核心卖点是纯离线、零网络开销、高隐私 |

## 二、为什么端侧需要 NPU/BPU

### 2.1 传统架构的困境

CPU 和 GPU 并非为深度学习设计：

- **CPU**：控制单元与多级缓存占据大量面积，真正用于计算的 ALU 占比小，跑神经网络效率低。
- **GPU**：面向图形渲染的 FP32/FP16 并行计算，通用性强但单位面积效率不如专用架构。

神经网络的本质是大量 **MAC（乘加运算）**，端侧又大量采用 INT8/INT4 量化。NPU/BPU 正是为这种负载定制的流水线工厂。

### 2.2 三大痛点倒逼专用架构

1. **功耗墙**：PC 级 GPU 方案 100W–300W，无法用于电池供电、被动散热的机器人。NPU/BPU 每瓦算力效率可达 4–6+ TOPS/W，功耗控制在 3W–15W。
2. **内存墙**：深度学习推理最耗时的是 DDR 数据搬运。NPU/BPU 通过片上 SRAM 做数据复用，并原生支持 INT8/INT4，把内存带宽压力降低数倍。
3. **成本与集成度**：RK3588 等 SoC 将 CPU、GPU、NPU、视频编解码、ISP、音频 Codec 集成在一颗芯片内，量产成本可降至几百元级别。

### 2.3 与 GPU 的关系

NPU/BPU 可以看作**“砍掉多余功能、极度特化的 GPU”**：

- 硬件电路上直接固化 MAC 阵列；
- 采用脉动阵列（Systolic Array）数据流，数据在计算单元间直接传递，减少寄存器读写；
- 在标准卷积、全连接/GEMM 等经典矩阵运算上效率极高。

## 三、算子支持：端侧部署的生死线

### 3.1 算子支持率决定成败

NPU/BPU 针对特定算子做了硬件级优化（如标准 Conv2d、Pooling、ReLU/SiLU 等）。如果模型中使用了编译器不认识的算子，通常会出现两种结果：

1. **编译失败**：工具链直接报错 `Unsupported Operator: xxx`，必须改写模型源码做等价替换。
2. **回退到 CPU**：数据在 NPU 与 CPU 之间反复搬运，延迟暴涨、吞吐量崩盘，是最隐蔽的工程陷阱。

### 3.2 端侧移植的避坑原则

1. **做减法，不追新**：优先使用经典结构（标准 Transformer、RMSNorm、SiLU/SwiGLU），避免最新的冷门 Attention 变体。
2. **先查厂商算子白皮书**：立项前确认 ASR、LLM、TTS 的每一层都在支持列表内。
3. **重写特定层再导出 ONNX**：将官方代码中的自定义 CUDA 算子用基础 PyTorch 算子重写，得到干净通用的模型后再喂给 NPU 编译器。

## 四、总结

- **PC 端部署**玩的是**高度与表现力**：模型更大、声音更拟真、业务逻辑更复杂。
- **端侧部署**玩的是**边界与平衡**：在 6–10 TOPS 算力和共享内存的约束下，精雕细琢每一毫秒延迟。
- **NPU/BPU**不是替代 CPU，而是作为高效率的算力挂件：CPU 负责管家与调度，NPU/BPU 负责低功耗、高吞吐的矩阵计算。两者的结合，才让机器人具备纯离线的具身智能成为可能。
