# RK3588 NPU 三核架构：为什么它为 INT8 而生

**核心摘要**：RK3588 里有 **3 个独立的 NPU 核**（Core 0/1/2），合计 **6 TOPS@INT8**，平均每个核 2 TOPS。每个核内部是一片 MAC 乘加阵列 + 384 KB 片内 SRAM + 一个 Cortex-M0 协处理器，三核再共享 1 MB 内存。程序不是必须绑核：默认 AUTO 是 “每次推理找一个空闲核”，`CORE_0_1_2` 才是把多核同时给同一个模型。需要说清楚的是，NPU 不是 “只能跑 INT8”，而是**把晶体管和功耗预算主要押在 INT8 通路上**—— 一个 FP16 乘法器约占 4 个 INT8 乘法器的面积，FP16 数据又占 2 字节、搬运量翻倍，而推理（区别于训练）量化成 INT8 后精度通常只掉 1～2%。三笔账合起来，决定了 NPU 天然以 INT8 为主：FP16 峰值算力约减半，实测延迟普遍 2 倍左右，遇到算子回落 CPU 时会到 3 倍以上。

## 一、NPU 是什么：CPU 旁边的 “矩阵工厂”

神经网络不管看起来多复杂，落到计算上其实只有一件事：**海量的乘加运算（MAC，Multiply-Accumulate）**—— 把一组数两两相乘，再把乘积加起来。卷积是这样，全连接、注意力也是这样。

CPU、GPU、NPU 都能做乘加，但做法完全不同，打个比方：



* **CPU** 像几个经验丰富的教授：什么都会算，还能处理复杂的逻辑判断，但 “人数” 少，同时铺开的计算有限；

* **GPU** 像上千个普通学生：每人只会简单的算术，但人多势众，适合一起算大量重复的数；

* **NPU** 像一条专门算矩阵的流水线工厂：整条流水线只会干 “乘加” 这一件事，但把这件事做到了极致，单位电耗下的产量最高。

端侧设备（机器人、开发板）靠电池或小电源供电、被动散热，能给 AI 的功耗只有几瓦到十几瓦。用 CPU 跑矩阵太慢，用 GPU 又太费电，于是就专门划出一块硅片做 NPU：**它存在的唯一目的，就是在极低功耗下把矩阵乘加算得又快又省。**

## 二、几个核、多少算力

### 三核，6 TOPS

RK3588 的 NPU 不是一整块，而是 **3 个相互独立的 NPU 核**，叫 Core 0、Core 1、Core 2：



| 项目      | 规格                                       |
| ------- | ---------------------------------------- |
| NPU 核数  | 3 个（Core 0 / Core 1 / Core 2）            |
| 总算力     | **6 TOPS@INT8**                          |
| 单核算力    | 2 TOPS@INT8                              |
| 支持的数据类型 | INT4 / INT8 / INT16 / FP16 / BF16 / TF32 |
| 协作方式    | 三核协同、双核协同、独立工作，三种都支持                     |

**TOPS** 是算力单位，指 “每秒能完成多少万亿次操作”（Tera Operations Per Second）。一次乘加 = 一次乘法 + 一次加法，算 2 个操作，所以 6 TOPS 意味着每秒能做约 3 万亿次乘加。

注意 “6 TOPS” 后面一定跟着 **@INT8**：这是用 INT8 数据、在理想满载下的峰值，相当于汽车的 “最高时速”，实际跑模型还要打折扣。

### 三个核怎么配合

硬件上三种用法都支持：



1. **三核协同**：一个模型的计算切到三个核上一起算，追求单次推理最快；

2. **双核协同**：用其中两个核算一个模型，剩下一个核干别的；

3. **独立工作**：三个核各跑各的，比如同时跑三个不同的模型。

在板子上可以直接看 NPU 的负载和频率：



```
sudo cat /sys/kernel/debug/rknpu/load    # 三核各自占用率
sudo cat /sys/kernel/debug/rknpu/freq    # 当前 NPU 频率
```

## 三、核里面长什么样

把一个 NPU 核放大，里面的结构并不神秘：



```
              ┌───────────────────────────────────────────────┐
              │         RK3588 内置 NPU（RKNPU v2）            │
              │       6 TOPS@INT8 = 3 核 × 2 TOPS             │
              ├──────────────┬──────────────┬────────────────┤
              │ NPU Core 0   │ NPU Core 1   │ NPU Core 2    │
              │ ┌──────────┐ │ ┌──────────┐ │ ┌──────────┐   │
              │ │MAC 乘加  │ │ │MAC 乘加  │ │ │MAC 乘加  │   │
              │ │阵列(卷积/│ │ │阵列(卷积/│ │ │阵列(卷积/│   │
              │ │矩阵乘法) │ │ │矩阵乘法) │ │ │矩阵乘法) │   │
              │ ├──────────┤ │ ├──────────┤ │ ├──────────┤   │
              │ │384KB SRAM│ │ │384KB SRAM│ │ │384KB SRAM│   │
              │ │Cortex-M0 │ │ │Cortex-M0 │ │ │Cortex-M0 │   │
              │ └──────────┘ │ └──────────┘ │ └──────────┘   │
              ├──────────────┴──────────────┴────────────────┤
              │          共享内存 1 MB（三核共享）             │
              └─────────────────────┬─────────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────────┐
              │   RKNN Runtime / RKLLM  →  rknpu 驱动         │
              └─────────────────────┬─────────────────────────┘
                                    │
              ┌─────────────────────┴─────────────────────────┐
              │   DDR 内存：权重 / KV Cache / 中间张量          │
              └───────────────────────────────────────────────┘
```

各部分的分工：



| 部件                          | 作用                                    |
| --------------------------- | ------------------------------------- |
| **MAC 乘加阵列**                | 核的主力，真正做卷积和矩阵乘法的地方，由成排的乘加器组成          |
| **384 KB 片内 SRAM**          | 核自己的 “小桌子”，把正在反复用的数据放在手边，不必每次都去 DDR 取 |
| **Cortex-M0**               | 核内的小管家（MCU），负责调度这一核上的计算任务             |
| **1 MB 共享内存**               | 三个核之间共享的数据区（框图口径）                     |
| **rknpu 驱动 + RKNN Runtime** | 上层程序通过它把任务派发给某个核                      |

**为什么核里要放 SRAM？** 因为去 DDR 取数据又慢又费电。卷积算一块区域时，相邻数据会被反复使用，把它们留在片内 SRAM 上 “数据复用”，是 NPU 高效的关键之一。

## 四、程序要不要绑核

### 四种 core\_mask

程序通过 **core\_mask（核心掩码）** 告诉 NPU 这个模型在哪些核上跑：



| core\_mask                 | 含义                  | 一次推理占几个核  |
| -------------------------- | ------------------- | --------- |
| `AUTO`                     | 自动调度，运行在**当前空闲**的核上 | 1 个（动态分配） |
| `CORE_0 / CORE_1 / CORE_2` | 固定在某一个核上            | 1 个（固定）   |
| `CORE_0_1`                 | 两个核协同算同一个模型         | 2 个       |
| `CORE_0_1_2`               | 三个核协同算同一个模型         | 3 个       |

Python 里一行就能设置：



```
from rknnlite.api import RKNNLite
rknn = RKNNLite()
rknn.load_rknn('model.rknn')
rknn.init_runtime(core_mask=RKNNLite.NPU_CORE_AUTO)   # 或 NPU_CORE_0 / NPU_CORE_0_1_2
```

### 澄清一个常见误解

**“不绑核（AUTO），是不是同一时刻三个核都给同一个模型用？”—— 不是。**



* `AUTO` 是**任务级调度**：每次推理调用时，runtime 看哪个核空闲，就把这一次推理派给哪个核。一次推理通常只落在一个核上，而且同一个模型的连续多次推理，可能这次在核 0、下次在核 2。

* 真正 “多个核同时给同一个模型” 的，是 `CORE_0_1_2` 多核协同：它把单个模型的 Conv 等算子切开分摊到多核，属于**单模型加速**。

* 多核协同只对 Conv、DepthwiseConvolution、Add、Concat、Relu 类等算子有效，不支持的算子会回落核 0。

### 多模型想并行，正确做法

三个核物理上确实可以同时各跑一个模型，但要满足两个条件：



1. 用**多线程或多进程**，每个持有**独立的 RKNN context**；

2. 最好把它们**分别绑到不同的核**（A 绑核 0、B 绑核 1、C 绑核 2），或都设 AUTO 让 runtime 分散。

一个坑要避开：**多个模型如果都设成多核模式（0\_1\_2）并同时触发，会互相争抢 NPU，实测可能内存越界、直接崩溃。** 所以 “多模型并行” 和 “单模型多核加速” 是两条路，不能混着用。

> 大模型走 RKLLM 通道，用 
>
> `num_npu_core`
>
>  选核（RK3588 可选 1/2/3，默认 3），它的线性层并行逻辑和普通 RKNN 模型不是同一套。

## 五、为什么 NPU 为 INT8 而生

这是最核心的问题。先纠正一个说法：NPU 不是 “只能跑 INT8”，FP16、BF16 都能跑；它之所以**把主力通路押在 INT8 上**，是三笔账算下来的结果。

### 账一：乘法器的 “地皮”—— 一个 FP16 顶约四个 INT8

芯片上每一块电路都要占硅片面积、都要耗电。



* **INT8 乘法器**做的是整数乘法：8 位 × 8 位，电路简单，就是把部分积累加起来；

* **FP16 乘法器**做的是浮点乘法：要先处理**符号位**、把**指数对阶**、再做**尾数相乘**、最后**规格化**，步骤多得多。

工程上，一个 FP16 乘法器大约要占 4 个 INT8 乘法器的面积（量级口径）。同样一块硅片、同样的功耗预算：



```
   INT8 方案：能塞 32 个乘加器            FP16 方案：只能塞 8 个
  ┌──┬──┬──┬──┬──┬──┬──┬──┐            ┌────────┬────────┐
  ├──┼──┼──┼──┼──┼──┼──┼──┤            │ FP16   │ FP16   │
  ├──┼──┼──┼──┼──┼──┼──┼──┤            ├────────┼────────┤
  ├──┼──┼──┼──┼──┼──┼──┼──┤            │ FP16   │ FP16   │
  └──┴──┴──┴──┴──┴──┴──┴──┘            └────────┴────────┘
   32 个简单工位同时开工                 8 个复杂工位
```

打个比方：同样的预算，INT8 是买 32 个塑料板凳，坐的人多；FP16 是买 8 个真皮沙发，单个舒服但数量少。NPU 追求的是 “同时开工的工位数量”，自然选 INT8。

### 账二：数据搬运 ——FP16 每个数占两字节



* INT8 每个数占 **1 字节**；

* FP16 每个数占 **2 字节**。

这意味着同样一个模型，FP16 的**权重、片内 SRAM 占用、DDR 搬运量全部翻倍**。以 1.5B 参数的大模型为例：



| 口径          | INT8 / W8A8 | FP16   |
| ----------- | ----------- | ------ |
| 每个数占字节      | 1           | 2      |
| 1.5B 模型权重   | 约 1.5 GB    | 约 3 GB |
| 同样带宽下每秒能搬的数 | 2 倍         | 1 倍    |

RK3588 上的大模型本来就是**带宽瓶颈**（每吐一个 token 要把权重从 DDR 重读一遍，实测约 12 token/s）。FP16 让搬运量翻倍，等于直接卡住脖子 —— 这一项甚至比 “算力减半” 更致命。

### 账三：推理不需要那么大的动态范围



* **训练**时要算梯度、不断更新参数，数值可能极大或极小，需要浮点的大范围，所以训练用 FP32/BF16；

* **推理**时模型已经训好，权重和每一层的输出数值范围都比较固定，用一个**缩放因子 scale** 就能把它们映射到 INT8 的 256 个格子里：



```
  浮点数轴：  -1.0 ──────────── 0 ──────────── +1.0
                │              │               │
                ▼              ▼               ▼
  INT8 格子： [-128 ... -1]  [0]  [1 ... 127]   （共 256 级）

  量化：  x_int8 = round(x_fp / scale) + zero_point
  计算：  全部在整数域做 INT32 累加
  还原：  x_fp   = (x_int8 - zero_point) × scale
```

视觉、语音类任务对这点量化误差并不敏感，**训练后量化（PTQ）成 INT8，精度通常只掉 1～2%**，用户几乎无感。既然损失这么小、换来的速度和省电又这么多，就没有理由在推理时坚持用浮点。

### 三笔账合起来



| 对比项         | INT8   | FP16             |
| ----------- | ------ | ---------------- |
| 单个乘法器占面积    | 1 份    | 约 4 份            |
| 每个数占字节      | 1      | 2                |
| 权重体积        | 1 倍    | 2 倍              |
| RK3588 峰值算力 | 6 TOPS | 约一半（3 TFLOPS 量级） |
| 推理精度        | 掉 1～2% | 基本无损             |

**NPU 不是 “为 INT8 设计”，而是 “为推理这一类负载设计”，而推理恰好可以用 INT8 高效完成。** 这是硅面积、数据带宽、精度三者共同决定的必然结果。

## 六、FP16 慢多少，什么时候还得用

### 实测：约 2 倍起步



| 模型 / 平台            | FP16       | INT8     | FP16 慢几倍 |
| ------------------ | ---------- | -------- | -------- |
| YOLO11n（Radxa 实测）  | 64.3 ms    | 18.74 ms | 3.4×     |
| 视觉模型纯推理（RKNPU 同架构） | 51.2 ms    | 25.2 ms  | 2.0×     |
| RK3588 规格峰值        | 约 3 TFLOPS | 6 TOPS   | 算力约减半    |

纯计算部分接近 2 倍（算力减半 + 搬运翻倍）；YOLO11n 之所以到 3.4 倍，是因为 FP16 额外的搬运开销，以及部分算子不支持、回落 CPU。**判断一个模型 FP16 慢多少，先确认它有没有 CPU fallback。**

### 什么时候还得用 FP16



* **量化后精度或音质崩掉的模型**：比如我们链路里的 VITS 声码器，W8A8 保不住音质，只能用 FP16，接受约 2 倍代价；

* **数值小、动态范围怪的层**：个别归一化、输出层，INT8 后掉点明显。

实操上不必 “全模型二选一”，RKNN 支持**混合量化**：整体先量化成 INT8，只对掉点明显的少数层（声码器、输出层）保留 FP16，在精度和速度之间取平衡。

### 对照我们的语音链路

《端侧半双工语音链路选型与实麦闭环》里：Qwen 大模型用 W8A8（省带宽、保吐字速率），VITS 声码器用 FP16（保音质），VAD 干脆放 CPU——**每一段都选了自己最划算的精度，而不是一味追求 INT8**。这正是理解 NPU 后的正确用法：INT8 是主力档位，但不是唯一档位。

## 七、一句话记住

**核数是 “工厂数量”，TOPS 是 “总产能”，核内的 MAC 阵列和 SRAM 是 “流水线和手边料架”，绑核是 “规定哪条流水线接哪单”。** 而 NPU 之所以把产能押在 INT8 上，是因为 INT8 的乘法器便宜（约 1/4 面积）、数据量小一半、推理量化后精度几乎不掉 —— 同样的电，能算出最多的活。FP16 不是不能用，而是 “占着更多流水线、搬着两倍数据”，适合声码器这类实在降不得精度的环节。
