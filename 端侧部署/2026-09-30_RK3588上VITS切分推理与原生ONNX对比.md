# RK3588上VITS切分推理与原生ONNX对比

**核心摘要**：VITS 整图 ONNX 在 RK3588 上拆成 CPU 前段 ONNX 加 NPU 后段 RKNN（FP16）：短句加速约 2.6 倍、贴近 160 帧上限的中句约 5.6 倍，加速几乎全来自声码器。配对波形相关系数中位 0.998、信噪比约 23 dB，听感同一说话人。当前硬限制是 RKNN 静态 160 帧（5.12 秒）输入上限，文末给出帧数按档位变化的改造方案。

> **环境与口径**
> 板子：Embedfire LubanCat（RK3588，4×Cortex-A76 @ 2.35 GHz + 4×Cortex-A55 @ 1.80 GHz，RKNPU v2）
> 模型：`board_pkg/model.onnx`（29.1 MiB，官方未切分全图）、`board_pkg/front.onnx`（10.7 MiB）、`board_pkg/flow_decoder.rknn`（13.0 MiB，FP16）
> 运行时：ONNX Runtime 1.23.2；rknn-toolkit-lite2 2.3.2，librknnrt 2.3.2，驱动 0.9.8，编译器 2.3.2，目标平台 rk3588
> 语句：短句「今天天气不错」（20 个音素 id），中句「欢迎使用鲁班猫开发板进行中文语音合成」（56 个音素 id）。说话人 `sid=21`（`SSB0241`）
> 采样参数与 `infer_board.py` 一致：`noise_scale=0.667`，`noise_scale_dur=0.8`，`speed=1.0`。采样率 8000 Hz，一帧 256 点
> 日期：2026-09-30，东八区，板上实测

结论先写。短句上，8 核线程池里的整图 ONNX 中位 123 ms，切分链路中位 47 ms，大约 2.6 倍。中句能塞进 160 帧时，整图 282 ms，切分仍是 51 ms，大约 5.6 倍。加速几乎全来自声码器：前段 ONNX 只有 8–13 ms，NPU 上的 FP16 声码器稳定在 38 ms 左右，因为输入被钉死在 160 帧。

同一句、同一次随机采样下，两条链路的波形相关系数中位 0.998，信噪比中位约 23 dB，对数谱距离大约 4–6 dB。听感是同一句话、同一个说话人。误差摊在整句上，来自 FP16 声码器的舍入；尾部补零没有把失真堆在句尾。可听的一对在 `board_pkg/native_onnx.wav` 和 `board_pkg/onnx_rknn.wav`。

中句有个硬限制。时长噪声开着的时候，20 次采样里有 14 次超过 160 帧，切分链路直接退出。160 帧是 5.12 秒。这个上限是导出 RKNN 时收死的，ONNX 全图里没有 160 这个常数。要让帧数跟着句子走，按第六节把若干档位编进同一个 RKNN，运行时补到最近的一档。

## 一、两条链路各算什么

模型是 icefall 导出的中文 VITS，`model_type=vits`，174 个说话人，采样率 8000。全图 `model.onnx` 一次吃进音素 id，吐出波形。切分之后，CPU 上的 `front.onnx` 负责文本编码、时长预测和长度扩展，输出潜变量 `(1, 96, frames)`、mask `(1, 1, frames)` 和说话人条件 `(1, 256, 1)`。`flow_decoder.rknn` 接过这三样，里面是 flow 和后面的转置卷积声码器，三层步长 8×8×4，所以一帧仍是 256 个采样点。

RKNN 不接受变化的帧数。脚本把潜变量和 mask 右侧补零到 160 帧，算完再按真实帧数裁掉尾部。160×256/8000 = 5.120 秒。短句真实长度只有大约 2 秒，NPU 仍按 5.12 秒的张量算。

全图 4896 个节点。前段留下 4438 个。两处 `RandomNormalLike` 都在前段：一处给时长预测，一处给潜变量。flow 和声码器侧的卷积、转置卷积、LeakyReLU、Tanh 不在前段里。

| 算子 | 全图 | 前段 | 留在后段 |
| --- | ---: | ---: | ---: |
| Conv | 147 | 52 | 95 |
| ConvTranspose | 3 | 0 | 3 |
| LeakyRelu | 34 | 0 | 34 |
| Tanh | 17 | 0 | 17 |
| Sigmoid | 40 | 24 | 16 |
| RandomNormalLike | 2 | 2 | 0 |

后段编成 RKNN 之后是 332 个节点，全部 float16。324 个在 NPU，8 个在 CPU：3 个输入、4 个 Slice、1 个输出。工作负载记在 NPU core0 上。`NPU_CORE_AUTO` 这次仍把整张图放在单核。

| 算子 | 节点数 | 设备 |
| --- | ---: | --- |
| Add | 63 | NPU |
| Conv | 58 | NPU |
| Split | 52 | NPU |
| Mul | 48 | NPU |
| ConvAdd | 18 | NPU |

| LeakyRelu | 16 | NPU |

| ConvTanh | 1 | NPU |

| InputOperator | 3 | CPU |
| OutputOperator | 1 | CPU |

层日志里的微秒是按默认 1000 MHz 估的周期，而且读不到真实 NPU 频率。下面的速度只用 `session.run` 和 `runtime.inference` 的墙钟，不含模型加载。冷加载大约是全图 0.92 s、前段 0.76 s、RKNN 0.32 s。

## 二、对照前提：锁住同一套噪声

时长噪声和潜变量噪声都没有在 ONNX 里写 seed。同一次进程里，每个 InferenceSession 各自数调用次数，同一序号抽到的是同一套随机数。所以「先跑一遍全图，立刻跑一遍前段」得到的帧数和潜变量是对齐的，波形可以逐样本相减。

隔开两次全图调用，抽到的是下一套噪声。时长会从大约 1.9 秒漂到 2.4 秒，波形相关系数掉到 0 附近，信噪比是负的。这个差距来自两次采样，声码器误差要另算。第四节的音质数字都来自锁步配对。速度用同一次运行的墙钟，取中位数。

实时率 = 计算时间 / 这条音频的时长。小于 1 就是快于实时。

## 三、速度实测

短句 8 次都落在 160 帧以内，帧数 60–74，音频 1.92–2.37 秒。中句只统计塞得进 160 帧的 6 次（150–160 帧，4.80–5.12 秒）。整图用默认线程池（`intra_op_num_threads=0`，8 个核一起参与）。单线程是另一组参照，只跑了短句。

|  | 短句中位 | 中句中位 |
| --- | ---: | ---: |
| 真实帧数 | 68 | 157 |
| 音频时长 | 约 2.2 s | 约 5.0 s |
| 整图 ONNX，8 核线程池 | 123 ms | 282 ms |
| 前段 ONNX | 8.8 ms | 12.8 ms |
| RKNN 声码器 | 37.7 ms | 38.0 ms |
| 切分端到端 | 46.9 ms | 50.8 ms |
| 相对整图的倍数 | 2.6× | 5.6× |
| 整图实时率 | 0.061（约 16 倍实时） | 0.056（约 18 倍实时） |
| 切分实时率 | 0.023（约 43 倍实时） | 0.010（约 100 倍实时） |

短句把整图限制成 1 个 intra 线程时，中位 295 ms，实时率 0.129。同样的短句，切分链路仍是 47 ms，大约是单线程整图的 6 倍。

NPU 时间不随句子变长。短句和顶满 160 帧的中句都是 38 ms，因为每次都在算 `(1, 96, 160)`。整图的卷积跟真实帧数走，所以句子越长，切分的优势越大。短句的 47 ms 里，大约八成花在一段本来只有 2 秒、却被补成 5.12 秒的声码器上。

中句的速度只代表「刚好不超过 160 帧」的那些采样。20 次里 14 次是 161–178 帧，`infer_board.py` 会直接退出，这 14 次没有 NPU 时间。

## 四、音质实测

配对之后比的是浮点波形，还没量化成 16-bit PCM。信噪比以整图为参考。对数谱距离是 512 点 FFT、帧移 128 的幅度谱，按 `20·log10` 做均方根，单位 dB。

|  | 短句 8 次中位 | 中句 6 次中位 |
| --- | ---: | ---: |
| 相关系数 | 0.998 | 0.998 |
| 信噪比 | 23.2 dB | 23.1 dB |
| 对数谱距离 | 5.5 dB | 3.8 dB |
| 最大绝对误差 | 0.057 | 约 0.08 |

短句信噪比落在 21.0–29.6 dB。两次独立的整图采样，相关系数大约 0，信噪比大约 −2 dB。23 dB 的配对误差远小于换一次随机采样带来的差别。

已经写成 wav 的那一对是「今天天气不错」，17408 点，2.176 秒。存成 16-bit 之后再读回来：相关系数 0.998，信噪比 24.7 dB，对数谱距离 4.6 dB，最大绝对误差 0.031。

| 文件 | 链路 |
| --- | --- |
| `board_pkg/native_onnx.wav` | `model.onnx` 整图 |
| `board_pkg/onnx_rknn.wav` | `front.onnx` + `flow_decoder.rknn` |

把这 2.176 秒切成三段，误差 RMS 分别是 0.0026、0.0025、0.0007。尾部绝对误差更小。最后 100 ms 信噪比掉成负数，是因为那里已经接近静音，分母里的信号本身就没了。补零到 160 帧没有在句尾堆出一段失真。

和同板上的 HiFi-GAN v1 FP16 比，那里相对 ONNX 有 48 dB 信噪比。这里只有 23 dB，因为后段不只是卷积声码器，还有一串 Sigmoid、Tanh 的 flow 耦合，FP16 的误差会乘开。波形仍然对齐，说话人和句子都还在。

## 五、使用时怎么选

句子明显短于 5 秒、而且必须落在 160 帧以内时，切分链路更快，短句大约 2.6 倍，贴近上限时大约 5.6 倍。音质保持在相关系数 0.998 这一档。

整图没有 160 帧上限，时长噪声把句子拉长也不会中途退出。它也慢，但 8 核上仍有大约 16 倍实时，交互场景不是算不过来。

现在这份静态形状把短句的 NPU 时间钉在 38 ms，也把长于 5.12 秒的句子挡在外面。帧数改成按档位变化的做法在第六节。

## 六、改进攻略：帧数按档位变化

160 只出现在当前这份 RKNN 的输入形状里：`latent (1, 96, 160)`、`mask (1, 1, 160)`。`model.onnx` 的权重和常量里没有 160，输出长度仍是符号维 `T`。后段沿时间的卷积、三层转置卷积（步长 8、8、4）都会跟着输入帧数变长。限制来自转换时把动态维收成了一个静态形状，运行时再把短句补到这个形状。

RKNN Toolkit2 2.3.2 的动态输入是一组编译期形状。每一组都生成一套 NPU 指令，权重仍是一份。推理时 `RKNNLite.inference` 用输入 ndarray 的形状去对组。对上了就跑那一组；对不上会失败。因此运行时做不到「来多少帧就建多少宽的张量」，要先向上补到已经登记的档位。这和现在补到 160 是同一件事，只是档位从 1 个变成一组，短句补得少，长句也有地方去。

板上只有 rknn-toolkit-lite2，能跑不能转。转换放在 x86，`rknn-toolkit2` 锁 2.3.2，和板上 `librknnrt` 一致。转换用的 flow decoder ONNX 必须保留动态时间维。先把 `frames` 收成 160 再转换，动态输入无处可挂。

三个输入的顺序跟现在的 RKNN 一致：`latent`、`mask`、`speaker_embed`。变的只有帧数。说话人条件始终是 `(1, 256, 1)`。档位取 32 的倍数，和现有的 160 对齐，也给 NPU 的宽度对齐留余量。

| 帧 | 补齐后的音频 | 覆盖 |
| ---: | ---: | --- |
| 64 | 2.048 s | 极短句 |
| 96 | 3.072 s | 本次短句的 60–74 帧落在这里 |
| 128 | 4.096 s |  |
| 160 | 5.120 s | 现在唯一的形状 |
| 192 | 6.144 s | 本次中句溢出到的 178 帧落在这里 |
| 256 | 8.192 s |  |
| 320 | 10.240 s |  |
| 384 | 12.288 s |  |
| 512 | 16.384 s | 建议的产品上限 |

9 档够用。再密，指令会一份份加上去，体积相对现在的 13.0 MiB 会涨，涨完再量。再稀，短句又要多补一截。超过 512 帧就改走整图 ONNX，把句子说完，不要截断波形。

转换骨架：

```python
BUCKETS = (64, 96, 128, 160, 192, 256, 320, 384, 512)

rknn.config(
    target_platform="rk3588",
    dynamic_input=[
        [[1, 96, frames], [1, 1, frames], [1, 256, 1]]
        for frames in BUCKETS
    ],
)
rknn.load_onnx(model="flow_decoder.onnx")
rknn.build(do_quantization=False)  # 保持现在的 FP16
rknn.export_rknn("flow_decoder_dyn.rknn")
```

`load_onnx` 不要再传写死的 `input_size_list`。量化继续关掉。动态形状若走 INT8，各档共用一套 scale，帧数差得远时比现在的 FP16 更容易掉音质。这条链路的音质预算已经在 23 dB 这一档，不要为了动态帧数再换量化。

板端把 `infer_board.py` 里固定的 160 换成选档。潜变量和 mask 一起补，说话人条件不动。算完仍按真实帧数乘 256 裁尾。

```python
def choose_bucket(frames: int) -> int:
    for size in BUCKETS:
        if frames <= size:
            return size
    return 0  # 调用方改走 model.onnx
```

每种档位第一次调用会把对应指令装进去，启动时把会用到的档各热一次，再记墙钟。

这次层日志里落在 CPU 的 4 个 Slice 是 `/flow/flows.1`、`flows.3`、`flows.5`、`flows.7`。它们的轴是通道维（axis = 1），步长 −1，也就是把通道翻转，时间维原样进出。动态帧数不用改这 4 个节点。真正随帧数变长的是后面的时间卷积和三层 `ConvTranspose`。

flow 的卷积核会看到邻帧，转置卷积还会把一帧展开成 256 个采样点。按句子从中间切开、两段分别进 NPU 再拼接，接缝上的样本会对不齐。补零只放在句尾，和现在这份 160 帧模型的边界是同一类。

改完用同一套锁步采样复测，不要只看「能出声」：

1. 短句补到 96 帧、中句补到 192 帧，相对整图的相关系数和信噪比仍应落在 0.998 和大约 23 dB 附近。某一档突然塌掉，就是这一档的编译结果坏了，先拿掉这一档。
2. 以前直接退出的 161–178 帧，应走 192 档并写出整句 wav。
3. NPU 墙钟应随档位变。96 档应低于现在的 38 ms，256 档应高于 38 ms。不会严格按帧数比例缩放：层日志里有一批说话人条件上的 1×1 卷积，输入是 `(1, 256, 1)`，和帧数无关。时间维上的卷积和三层转置卷积才是大头。
4. `RKNN_LOG_LEVEL=4` 再看一遍。通道翻转可以继续留在 CPU。时间维上的 Conv、ConvTranspose 仍应在 NPU。

预期的使用差别：短句少补一大段 160，NPU 时间从固定的 38 ms 降下来；中句不再因为 178 帧退出。整图 ONNX 只留给超过 16.384 秒的句子。数字要以复测为准，本节没有新的板上计时。
