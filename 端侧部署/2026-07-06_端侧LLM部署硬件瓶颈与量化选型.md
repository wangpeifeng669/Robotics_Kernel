# 端侧 LLM 部署硬件瓶颈与量化选型

**核心摘要**：端侧 LLM 推理存在一个反直觉的铁律——首帧延迟看算力架构，吐字速度死死卡在内存带宽上。INT4 量化之所以成为行业默认选择，不是因为精度损失可以接受，而是因为它恰好踩中了端侧硬件的物理黄金平衡点：4.5GB 模型体积 + 100GB/s 内存带宽 = 20+ Tokens/s 的丝滑体验。本文从开发板选型、两阶段推理瓶颈、量化精度与硬件适配四个维度，给出端侧 LLM 部署的完整决策框架。

---

## 一、端侧开发板硬件矩阵

在开始量化选型的讨论之前，先拉齐目前端侧跑 LLM 最主流的三款开发板的硬件底牌：

| 维度 | 地瓜 RDK S100P | Jetson Orin Nano Super (8GB) | Jetson Orin NX (16GB) |
| :--- | :--- | :--- | :--- |
| 内存 | 24GB LPDDR5 | 8GB LPDDR5 | 16GB LPDDR5 |
| 算力 | 128 TOPS（BPU Nash 架构） | 67 TOPS | 100 TOPS |
| 内存带宽 | ~100 GB/s | 102 GB/s | 102 GB/s |
| 价格区间 | 中端 | ~2000-2500 元 | 4500-5500 元 |
| 核心优势 | 24GB 内存容下更大模型 | 英伟达入门门槛 | 具身智能黄金线 |

关键认知：**宣传单上的 TOPS 算力，通常是 INT8/INT4 下的峰值算力**，跑 CNN 视觉模型（YOLO 之类）确实飞快，但跑 LLM 完全是另一回事——大模型的推理瓶颈不在算力，而在内存带宽。

---

## 二、推理过程的两阶段瓶颈：算力 vs 带宽

要理解为什么 TOPS 算力对 LLM 吞吐的参考价值有限，必须先将推理过程拆为两个阶段。

### 2.1 Prefill（预填）阶段——决定首帧延迟（TTFT）

Prefill 阶段将输入的 Context（比如 2048 个 Token）一次性全部吃进去，计算初始 KV Cache。

以 Qwen2.5-7B（INT4）在 Jetson Orin NX 上为例：
- **访存量**：搬运 4.5GB 模型权重进入核心，约 **44ms**（102GB/s 带宽下）
- **计算量**：4.5GB 权重 × 2048 Token 复用 = **约 18000 亿次浮点运算**
- **结论**：计算耗时（200-300ms）远大于访存耗时（44ms），这是一个**计算受限（Compute-bound）**阶段

**首帧快不快，看算力架构**：核心 CUDA/BPU 矩阵单元多不多、有没有 Transformer 硬件加速算子。

### 2.2 Decoding（解码）阶段——决定吐字速度（Tokens/s）

Prefill 之后，进入自回归解码：每吐一个字，需要重新搬运整个模型权重做计算。

- **访存量**：每吐一个字，重新搬运 4.5GB 模型权重，约 **44ms**
- **计算量**：只有 1 个新 Token × 4.5GB 权重 = **约 90 亿次运算**（几微秒即可完成）
- **结论**：芯片 95% 以上时间在"等快递"（等内存带宽），这是一个**带宽受限（Memory-bound）**阶段

**吐字快不快，不看算力，死死卡在内存带宽（GB/s）上。**

### 2.3 直观对比：为什么首帧感觉"慢"而吐字感觉"快"？

| 维度 | Prefill（首帧） | Decoding（吐字） |
| :--- | :--- | :--- |
| 单步任务量 | 18000+ 亿次计算 | 90 亿次计算 |
| 单步物理耗时 | 200-400ms | ~44ms |
| 用户感知 | 一段"空白等待" | 字与字之间 44ms，看起来"丝滑" |

首帧的 300ms 是一段完整的等待空白期，如果 Context 设到 8K，首帧会飙到 1.2-1.6 秒，用户会感觉机器人"死机了"。而吐字的 44ms 间隔（对应 22 Tokens/s）对人眼来说完全无感知——只要大于 10 Tokens/s，看起来就是连贯的。

## 三、量化方案的物理账本：FP16 → INT8 → INT4

把推理瓶颈搞清后，量化方案的选择就变成了一个纯粹的算数题。

### 3.1 三种精度的内存与带宽对比（以 Qwen2.5-7B 为例）

| 量化精度 | 模型体积 | 单字搬运耗时 | 极限吐字速度 | 工程可行性 |
| :--- | :--- | :--- | :--- | :--- |
| FP16 | ~15 GB | ~150ms | 3-5 Tokens/s | 不可行（首帧数秒，吐字 PPT） |
| INT8 / Q8 | ~8 GB | ~80ms | 10-12 Tokens/s | 勉强及格（内存告急，适配差） |
| INT4 | ~4.5 GB | ~40ms | 20-25 Tokens/s | 黄金甜点位 |

### 3.2 为什么 FP16 在端侧直接宣判死刑？

三项死刑判决：

1. **内存踩红线**：15GB 模型 + 2GB KV Cache + 2GB 系统 ≈ 19GB+，Orin NX 16GB 直接 OOM
2. **带宽判死刑**：每吐一字运 15GB 数据需 150ms，吞吐仅 6.6 Tokens/s——"机器人回话像老年人挤牙膏"
3. **算力降级**：BPU 的 128 TOPS 是纯定点数算力，FP16 浮点单元极其孱弱（几个 TFLOPS），首帧可达数秒甚至十几秒

### 3.3 为什么 INT8/Q8 反而不如 INT4？

这是一个反直觉但极其重要的工程真相：**INT8 大模型在地瓜 BPU 上不如 INT4，不是因为硬件算不动 INT8，而是软件工具链没适配。**

地瓜 S100P 的 BPU 硬件电路完完全全支持标准 INT8 矩阵乘法——跑传统 CNN 视觉模型（YOLO，几年前就已经完美适配）效率极高。但大模型（LLM）的 Transformer 算子是动态的、长短可变的，和 CNN 的固定输入分辨率完全不同。

工具链团队把有限的人力全部砸在了 INT4/混合低比特的大模型算子优化上，而 INT8 大模型的"翻译字典"（算子映射规则）根本没跟上。编译器遇到不会翻译的算子，触发 **Fallback 回退机制**：把算子从 BPU 踢给 ARM CPU 去硬抗，同时数据在 BPU 和 CPU 之间来回拷贝，内存带宽开销比计算本身还慢百倍。这就是为什么你跑 Q8 模型首帧飙到 500ms+ 的真正原因。

## 四、AWQ 底层原理：乘法结合律魔术

很多人担心降到 INT4 模型会变傻。前几年确实会（粗暴量化导致精度雪崩），但 2026 年的量化技术已经用一套巧妙的数学方法解决了这个问题。

### 4.1 异常值问题：为什么标准 INT8/INT4 直接量化会失败？

大模型运行时，99% 的数据都在 0-1 之间，但极个别通道会突然飙到几万（称为**激活值异常值/Activation Outliers**）。

如果用一个统一的缩放因子强转成 INT4/INT8：
- 为了塞下大数字，缩放比例必须调得很大
- 99% 的小数字被压缩后四舍五入变成了 0（数据"死掉"）
- 机器人直接变成白痴或无限复读

### 4.2 AWQ 的解法：乘法结合律平滑

AWQ（Activation-aware Weight Quantization，激活感知权重量化）用了一个巧妙的方法，用小学数学就能解释。

回顾乘法结合律：$$A \times B = (A \times 10) \times (B \div 10)$$

在模型编译阶段，工具链做两件事：
1. **削平激活端（B）**：预测到哪个通道会产生大数字，提前除以一个系数，把异常值拉回正常范围
2. **补偿权重端（A）**：对应的权重乘以同样的系数，保证整体计算结果不变

做完这套"等比缩放"后，两边的数据全部变成了平平凡凡的普通数字，这时再用一个统一的缩放比例转成 INT4——小数字不会变成 0（智商保住），所有数据规则一致（BPU 硬件最喜欢的整齐格式）。

这就是业界默认选 INT4 的底气所在：**用几乎不可查的 2-3% 精度损失，换取内存不崩溃、首帧不卡顿、说话不结巴的商用级体验。**

## 五、BPU 对 INT4 的底层优化到底做了什么？

地瓜 S100P 对 INT4 的"偏心"，体现在硬件和软件两个层面的深度优化。

### 5.1 硬件层面：专用的量化/解量化 Scale 单元

BPU 的矩阵乘法器旁边，紧挨着一个硬连线的数学计算器。它可以在数据刚被搬进芯片的零点几纳秒内，在纯硬件电路里自动完成 `INT4 权重 × 缩放系数` 的操作，完全不占用任何软件计算时间。这套软硬一体的设计，是专门为 INT4 大模型量身定制的。

### 5.2 软件层面：工具链的算子映射字典

芯片厂商写编译器（工具链）是一件极度耗费人力的工作。要把大模型里几十种复杂的 Transformer 算子翻译成 BPU 看懂的底层机器码，需要资深底层工程师一行一行手写极致指令集优化。

因为业界默认端侧大模型就是 INT4，地瓜的编译器团队把 Qwen、Llama 等模型的 INT4 算子图拆解、指令排布、内存对齐优化到了极致——只要喂给它标准的 INT4 权重，编译器里有完美的 1 对 1 映射规则，直接生成一条龙不减速的 BPU 硬件流水线。

而 INT8 大模型的"翻译字典"因为优先级低，大量算子缺少 BPU 映射规则。编译器为了保护程序不崩溃，启动 Fallback 机制，将不会译的算子踢给 ARM CPU 执行——这不仅是 CPU 承担了本不该承受的重担，更致命的是 BPU 和 CPU 之间的数据来回拷贝把内存带宽彻底打爆。

### 5.3 商业逻辑：为什么偏爱 INT4？

不只是技术原因，更是商业理性的选择：
- **INT4 体积只有 INT8 的一半**：7B 模型从 8GB 缩到 4.5GB，意味着可以用更便宜的板子跑起来，意味着地瓜芯片的市场面更广
- **INT8 在物理上就被内存带宽判了死刑**：就算 BPU 算得再快，板子那 100GB/s 的带宽决定了最多只能吐 10 Tokens/s，用户体验已经不及格了
- **优化 INT4 = 让客户的跑分更好看**：20+ Tokens/s 对客户来说就是"这芯片真快"；反之优化 INT8 只能得到 10 Tokens/s——"这芯片不行啊太卡了"

## 六、Context 设置的工程真相

很多端侧开发者会设置 `max_model_len=2048` 这类参数，以为它规定了"每次算 2048 个 Token"。实际上这里有重要的动态行为和工程陷阱。

### 6.1 首轮对话：实际Token少，反应极快

第一轮你对机器人说"你好"（仅几个 Token），Prefill 阶段只需要算这几个 Token 的矩阵乘法——耗时约 40ms，秒回。

### 6.2 多轮对话：首帧越聊越慢

大模型的"记忆"不是凭空产生的。到了第 10 轮，虽然你只输入了几个字，但框架必须把前 9 轮积攒的历史记录（可能接近 2048 个 Token）全量打包重新做 Prefill——这才是为什么首帧从几十毫秒逐渐拉长到 300-400ms 的物理真相。

### 6.3 工程应对：滑动窗口 + 摘要压缩

```python
def get_llm_input(current_query, chat_history):
    # 只保留最近 3 轮对话作为上下文
    active_history = chat_history[-3:]
    # 总 Token 数永远压制在 500 以内
    return build_prompt(active_history, current_query)
```

通过滑动窗口策略，无论用户聊多久，首帧永远保持在第一轮的速度。

## 七、端侧 LLM 部署的终极决策框架

综合上面的分析，给出一张端侧 LLM 部署的一页纸决策框架：

### 7.1 硬件选型

| 场景 | 推荐平台 | 推荐模型规模 |
| :--- | :--- | :--- |
| 纯语音交互（商用导购、前台） | 地瓜 S100P（24GB 内存是核心优势） | 7B INT4 量化 |
| 具身智能（视觉+控制） | Jetson Orin NX 16GB（CUDA 生态无可替代） | 7B/8B INT4 |
| 极致成本（简单意图识别） | Jetson Orin Nano Super 8GB | 1.5B-3B INT4 |

### 7.2 量化选型铁律

> **在地瓜 S100P / Orin 这类端侧 BPU 平台上，INT4 + 混合低比特是唯一的满血通关密码。**

- INT4 体积 4.5GB，刚好踩中 16GB 内存板子的生存线
- INT4 吞吐 20+ Tokens/s，刚好超越人类阅读速度
- INT4 工具链适配 95%+ 算子映射率，首帧压到 200-300ms
- Q8/INT8 大模型因为工具链没适配，频繁 Fallback 到 CPU，首帧飙到 500ms+

### 7.3 性能调优核查清单

- [ ] 模型是否经过 INT4 或官方混量 PTQ 编译？
- [ ] Context Window 是否限制在 1024-2048 以内？
- [ ] 是否启用了滑动窗口或会话摘要压缩？
- [ ] 编译器日志中 BPU 算子映射率是否 ≥ 95%？
- [ ] 框架是否走了硬件加速路径（TensorRT-LLM / 自研工具链），而非退化为 llama.cpp 纯 CPU？
- [ ] ASR/TTS 是否与 LLM 做内存预算隔离，避免相互争抢导致 OOM？

## 八、总结

端侧 LLM 部署的核心矛盾，概括起来就是一句话：

> **首帧快不快，看算力架构；吐字快不快，死死卡在内存带宽上。**

INT4 量化之所以成为行业默认选择，不是因为它精度损失小，而是因为它恰好同时解决了端侧的三个物理死结：内存装得下、带宽运得快、硬件算得动。与之相对的，FP16 在端侧完全不具工程可行性，INT8 则陷入了"硬件能算但工具链没跟上"的尴尬境地——在地瓜 S100P 这类纯血端侧 BPU 上，跑 INT8 大模型反而不如 INT4，这是编译器生态优先级决定的物理现实，不是玄学。

理解了这层底层逻辑，端侧 LLM 的所有性能调优决策——从开发板选型、模型量化到上下文管理——都将回归为一个简单的算术题。
