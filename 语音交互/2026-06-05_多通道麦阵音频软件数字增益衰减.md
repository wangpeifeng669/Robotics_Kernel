# 多通道麦阵音频软件数字增益衰减：从削波问题到 C++ 实现

> 适用场景：嵌入式 Linux / Android 平台 + USB 麦阵（多路麦克风 + 回采参考），硬件无独立麦克风 Capture Volume 可调时，在应用层对采集到的多通道原始 PCM 做选择性通道衰减。  
> 典型配置：8ch interleaved S16LE（4 麦 + 2 占位 + 2 回采），16 kHz / 16 bit，进降噪 / AEC SDK 前插入衰减。

## 核心摘要

机器人在播放 TTS 时，内部麦克风因距离近、声压大导致 ADC 采样**满幅削波**（waveform flat-top at ±32767），AEC 算法基于线性假设无法拟合非线性失真，最终表现为"机器人自己的声音消不干净"。硬件层无独立麦克风增益可调（部分 UAC 设备仅有开关/AGC），退而在软件层对**多通道原始缓冲中的麦克风通道做选择性衰减**（回采通道保持不动）。本文从削波根因、PCM 数据格式、定点数运算细节、增益系数选取依据四个层面展开，给出可直接使用的 C++ 实现及配套调参方法。软件衰减的本质是将工作点拉回线性区，不能恢复已被硬削波丢失的信息。

## 1. 问题背景与现象

### 1.1 典型数据流

```text
USB 麦阵 (8ch S16LE)
    → 应用层采集读入 (interleaved 8-channel raw buffer)
        → [可选] 软件数字增益衰减 (仅 ch0~3 麦克风通道)
            → 通道规整 (4mic + 2ref 送入引擎)
                → 第三方降噪 / AEC SDK
                    → 输出 → ASR / 唤醒
```

### 1.2 波形特征（见题图）

| 轨道 | 含义 | 正常/异常判断 |
|------|------|--------------|
| **input\_origin\_1**（麦克风 ch0 原始） | 进 SDK 前某路麦信号 | **异常**：播报段峰值长期贴满 ±1.0，波形顶部/底部被「削平」，属典型的 **hard clipping（硬削波）** |
| **input\_origin\_6**（回采 ch6 参考） | 喇叭回路参考信号 | 正常：幅度约为麦的 1/5 ~ 1/3，无削波 |
| **work\_flow\_frontend\_chb5**（SDK 输出） | 经降噪/AEC 处理后的结果 | 异常表现：播报段仍残留明显能量，说明 AEC 未有效收敛 |

**关键观察**：麦克风轨削波越严重，AEC 输出的播报残留越大——这不是 AEC 参数不够强的问题，而是**输入信号已经破坏了算法的基本假设**。

### 1.3 已尝试路径及局限

| 尝试路径 | 结果 | 局限原因 |
|----------|------|----------|
| 提高 SDK 的 AEC 强度等级 | 改善不明显 | 削波引入非线性失真，自适应滤波器无法拟合；提高等级只会放大失真影响 |
| 降低 TTS 播放音量 | 有改善但不彻底 | 减轻了回声幅度，但人近距离讲话时麦克风仍然容易过载；且降低了用户体验 |
| `amixer` 调 Capture Volume | **不可用** | 该 UAC 设备的 mixer 控件中**没有独立的麦克风模拟/数字增益旋钮**，仅有全局开关和 AGC |

因此选择**软件层兜底方案**：在采集后、送入 SDK 前，仅对多通道缓冲中的麦克风通道做乘法衰减。

## 2. 削波根因：为什么 AEC 怕削波

### 2.1 AEC 的线性模型假设

AEC（Acoustic Echo Cancellation）的核心是一路**自适应滤波器**：

$$ d(n) = x(n) * h(n) + s(n) + v(n) $$

其中 $d(n)$ 是麦克风信号，$x(n)$ 是回采参考，$h(n)$ 是待估计的房间冲激响应，$s(n)$ 是近端语音，$v(n)$ 是噪声。AEC 通过 LMS / NLMS 等自适应算法不断更新 $h(n)$，使得 $x(n)*h(n)$ 尽可能逼近 $d(n)$ 中的回声成分，然后相减得到干净的近端语音。

**这个模型成立的前提是：系统近似为线性时不变（LTI）系统。**

### 2.2 削波如何破坏线性性

当麦克风 ADC 输出达到 16-bit 有符号整数范围边界时：

```
真实声压对应的理想采样值 = +35000
ADC 实际输出              = +32767   （被截断 / saturated）
```

这种**硬限幅（hard clipping）** 引入的非线性畸变包括：

| 非线性效应 | 对 AEC 的影响 |
|-----------|-------------|
| 幅值截断 | 滤波器输出无法匹配被截断的峰值，残差始终存在 |
| 谐波失真 | 产生原始信号中不存在的频率分量（奇次谐波为主），滤波器无法建模 |
| 动态范围压缩 | 大信号被压平、小信号相对不变，改变了信号的统计特性，NLMS 步长控制失效 |

直观理解：AEC 在尝试用一个"橡皮泥模型"去贴合麦克风里的回声形状，但回声的"头顶已经被刀削平了"——无论怎么捏橡皮泥，都捏不出那个本该存在的圆弧顶。

### 2.3 更上游的原因链

```
TTS 播放音量较大
    → 喇叭声压级高（尤其机器人腔体小、麦距喇叭近）
        → 麦克风振膜收到的声压超过 ADC 线性区上限
            → 16-bit 量化结果 saturate at ±32767
                → 硬削波 → AEC 失效 → 播报段消不干净
```

打断这条链条的最佳位置是**最前端**（降低声压或 ADC 增益），不得已才在末端（软件层衰减）做补救。

## 3. PCM 数据格式基础：理解代码操作的载体

### 3.1 关键参数

| 参数 | 值 | 含义 |
|------|---|------|
| 采样率 | 16000 Hz | 语音频带足够（Nyquist = 8 kHz） |
| 位深 | 16-bit signed | 每个采样值范围 **-32768 ~ +32767** |
| 字节序 | Little-Endian (S16LE) | 低字节在前；x86/ARM 默认字节序，直接 `reinterpret_cast` 即可 |
| 通道布局 | 8 channels interleaved | 一个 frame = 8 个连续的 int16_t，排列为 [ch0, ch1, ..., ch7] |
| 通道分配 | ch0~3=麦克风, ch4~5=占位(静默), ch6~7=回采参考 | 因设备而异，需对照文档或实测确认 |

### 3.2 交错排列的内存布局

```
帧 N:   [ch0_N] [ch1_N] [ch2_N] [ch3_N] [ch4_N] [ch5_N] [ch6_N] [ch7_N]
帧 N+1: [ch0_{N+1}] [ch1_{N+1}] ... [ch7_{N+1}]
...
```

每个 frame 占用 `8 × 2 = 16` 字节。访问第 i 帧、第 c 通道的索引公式：

```cpp
index = i * kChannels + c;   // kChannels = 8
sample = reinterpret_cast<int16_t*>(buffer)[index];
```

这就是代码中 `base = i * kChannels` 和 `in8[base + c]` 的由来。

### 3.3 dBFS 与线性幅值的换算

音频工程中常用 **dBFS（decibels relative to Full Scale）** 表示电平：

| dBFS | 线性系数（相对于满幅 32767） | 对应采样值（约） | 状态 |
|------|---------------------------|-----------------|------|
| 0 dBFS | 1.000 | 32767 | **满幅 / 削波临界** |
| -6 dBFS | 0.501 | 16400 | 偏高但有 margin |
| -9 dBFS | 0.355 | 11630 | **推荐工作点上限** |
| -12 dBFS | 0.251 | 8230 | 安全区间 |
| -20 dBFS | 0.100 | 3277 | 偏低 |

**目标**：TTS 播报时麦克风峰值落在 **-12 ~ -6 dBFS**（约 9000~16000），为瞬态尖峰留 headroom。

常用换算公式：

```
linear_gain = 10^(dBFS / 20)
// 例：-9 dB → 10^(-0.45) ≈ 0.355
```

## 4. 核心代码解析：`apply_8ch_mic_gain_s16le`

### 4.1 完整实现

```cpp
/// 仅衰减麦克风通道（默认 ch0~3），不改动回采 ch6~7，避免削弱 AEC 参考。
/// @param in8         多通道 S16LE interleaved 缓冲区指针
/// @param frames       帧数（非样本数；每帧含 kChannels 个采样）
/// @param gain         衰减系数，1.0=不变，0.35≈-9dB，建议范围 0.25~0.70
/// @param mic_channels 麦克风通道数（默认 4 路）
inline void apply_8ch_mic_gain_s16le(
  std::int16_t *in8,
  std::size_t frames,
  float gain,
  unsigned mic_channels = 4)
{
  // ---- 快速路径：无需处理的情况 ----
  if (!in8 || gain >= 0.999f) {
    return;
  }
  // ---- 参数安全约束 ----
  gain = std::clamp(gain, 0.01f, 2.0f);
  // ---- 逐帧逐通道处理 ----
  constexpr unsigned kChannels = 8;           // 固定 8 通道布局
  for (std::size_t i = 0; i < frames; ++i) {
    const std::size_t base = i * kChannels;   // 当前帧起始偏移
    for (unsigned c = 0; c < mic_channels && c < 4; ++c) {
      // 浮点乘法
      const float v = static_cast<float>(in8[base + c]) * gain;
      // 四舍五入到最近整数 + 饱和限幅（防止溢出）
      in8[base + c] = static_cast<std::int16_t>(
        std::clamp(static_cast<int>(std::lround(v)), -32768, 32767));
    }
    // ch4~7（含回采 ch6~7）原样保留，不做任何操作
  }
}
```

### 4.2 逐行设计决策解读

#### 为什么用 `float` 中间运算而非纯定点？

16-bit × float gain 的乘积需要**高于 16-bit 的中间精度**：

```cpp
const float v = static_cast<float>(in8[base + c]) * gain;
```

若直接用 `int16_t * int16_t >> 8` 这类定点方案：
- 当 gain 不是 2 的幂次时，定点近似会引入**舍入噪声**；
- 多帧累积后可能产生可闻的量化伪影（quantization artifact）。
float 运算在 ARM Cortex-A 上有硬件 FPU 支持，单通道单帧仅需 1 次乘法，性能开销可忽略（16kHz/8ch 下约 128k 次乘法/秒）。

#### 为什么用 `std::lround` 而非直接 `static_cast<int>` 截断？

```cpp
std::lround(v)   // 四舍五入到最近整数
// vs.
static_cast<int>(v)  // 向零截断（truncate toward zero）
```

截断会产生 **-0.5 LSB 的系统性直流偏移**（DC offset），虽然单次听不出，但在长音频中可能积累成低频噪声。`lround` 将量化误差均匀分布到四舍五入的正负两侧，统计期望为零。

#### 为什么需要 `std::clamp` 二次限幅？

理论上 `gain < 1.0` 时乘法结果不会溢出 int16_t 范围，但：
- `gain` 参数如果意外被设为 > 1.0（比如误操作或配置文件写错），`32767 * 1.5 = 49150`，直接转 int16_t 会**回绕（wrap around）**变成负数，产生爆音；
- `std::clamp` 作为**防御性编程**的安全网，确保输出永远在合法范围内。

#### 为什么限制 `mic_channels && c < 4`？

双重守卫：
- `c < mic_channels`：用户指定的麦克风数量（通常为 4）；
- `c < 4`：硬上限，即使 `mic_channels` 被错误地传为 8 或更大，也不会误改回采通道。

#### 为什么 `gain >= 0.999f` 时直接 return？

`gain = 0.999` 相当于 **-0.009 dB**，变化量远低于 16-bit 量化的 1 LSB（约 -96 dB 以下的精度），实际效果等同于 1.0。跳过可以省掉整个循环的计算开销。

### 4.3 性能评估

| 指标 | 数值 | 说明 |
|------|------|------|
| 每秒处理帧数 | 16000 帧（@16kHz） | 单通道采样率即帧率 |
| 每帧浮点乘法次数 | 4 次（仅麦克风通道） | 回采 4 通道跳过 |
| 每秒总浮点乘法 | ~64k 次 | 对现代 CPU 完全可忽略 |
| 内存访问模式 | 顺序遍历（sequential） | 对 CPU 预取友好，cache 命中率高 |
| 额外延迟 | **零**（原地 in-place 修改） | 无内存分配、无拷贝 |

**结论**：此函数不会成为性能瓶颈。即使在 RK3588 这种嵌入式平台上，64k FLOP/s 也仅占用极少量 CPU 资源。

## 5. 增益系数选取指南

### 5.1 从波形反推目标系数

步骤：

1. 导出一段包含 TTS 播报的多通道 raw PCM（未加衰减）；
2. 用 Audacity 或 sox 导入（16kHz / 16bit / 8 channel）；
3. 定位播报段，读取麦克风通道（ch0~3 任一）的**峰值采样值** `peak_raw`；
4. 目标 peak 约 12000~16000（-9 ~ -6 dBFS），计算系数：

```
target_peak = 14000          // 推荐起点
gain = target_peak / peak_raw
// 例：peak_raw = 32000 → gain = 14000/32000 ≈ 0.4375
```

### 5.2 系数速查表

| 原始峰值（约） | 衰减程度 | 建议 gain | 等效 dB |
|---------------|---------|----------|---------|
| > 31000 | 严重削波 | **0.30 ~ 0.35** | -10 ~ -9 dB |
| 28000 ~ 31000 | 明显过载 | **0.40 ~ 0.50** | -8 ~ -6 dB |
| 24000 ~ 28000 | 轻度过载 | **0.55 ~ 0.65** | -5 ~ -4 dB |
| 20000 ~ 24000 | 接近上限 | **0.70 ~ 0.80** | -3 ~ -2 dB |
| < 20000 | 基本安全 | **0.85 ~ 1.00** | -1 ~ 0 dB |

### 5.3 调参迭代流程

```
初次设定 gain = 0.35
    ↓
录一段「TTS 播放 + 人声」的测试音频（含 SDK 输出）
    ↓
检查：① 麦克风原始轨是否还有平顶？ ② 播报段输出轨是否接近静音？
    ↓
┌─ 有平顶 ──→ 继续降低 gain（步长 0.05）
└─ 无平顶但人声偏小 ──→ 适当提高 gain（步长 0.05）
    ↓
两者兼顾时的最小 gain 值即为最优解
```

**原则**：gain 能多大就多大（保留更多动态范围），只要不再削波即可。过度衰减（如 gain=0.15）虽能消除削波，但会把有用的人声也压得太弱，反而影响唤醒/识别灵敏度。

## 6. 插入位置与集成要点

### 6.1 Pipeline 中的正确位置

```
[USB Audio Device]
    │
    ▼
read() / ALSA capture callback     ← 在这里拿到 in8 缓冲
    │
    ▼
apply_8ch_mic_gain_s16le(in8, frames, gain)   ← 【插入点】
    │
    ▼
channel rearrangement (8ch → 6ch: 4mic + 2ref)
    │
    ▼
noise suppression / AEC SDK process()
    │
    ▼
output → ASR / VAD / Wake-up
```

关键原则：**在通道规整之前、采集回调的最早期执行**。原因：
- 此时缓冲还是原始 8ch 布局，通道语义明确；
- 衰减后的数据同时影响后续所有下游模块，无需多处修改；
- 若 SDK 有内部 AGC，衰减后的较低电平可减少 AGC 误推高的风险。

### 6.2 与 AGC 的关系

| 场景 | AGC 行为 | 建议措施 |
|------|---------|---------|
| SDK 内置 AGC 开启 + 未衰减 | 麦克风已削波，AGC 可能将已偏大的信号继续推高 | **关闭**或降低 SDK AGC，先解决削波 |
| SDK 内置 AGC 开启 + 已衰减 | 电平整体偏低，AGC 会自动补偿提升 | 通常**无害**，但需验证 AGC 不会把衰减后的信号重新推到削波 |
| 应用层自行接 AGC（如 WebRTC AGC） | 同上 | 确保 AGC 位于衰减**之后**，否则互相打架 |

最佳实践顺序：**硬件/软件降增益 → 关闭或降低内置 AGC → AEC → （可选）输出端温和 AGC**。

### 6.3 多线程注意事项

- 该函数是**纯计算、无锁、原地修改**的设计，线程安全性由调用方保证；
- 若采集回调在不同线程执行，确保 `in8` 缓冲在函数返回前不会被其他线程读写（典型情况下回调本身是串行的，不存在竞争）；
- `gain` 参数若运行时可配（如从配置文件加载），读取时应使用 `std::atomic<float>` 或加 mutex 保护。

## 7. 扩展：相关技术概念辨析

### 7.1 数字增益衰减 vs 模拟/硬件增益

| 维度 | 硬件增益（模拟/ADC） | 软件数字增益衰减 |
|------|--------------------|-----------------|
| 作用位置 | ADC 量化**之前** | ADC 量化**之后** |
| 对已削波信号的能力 | **从根本上消除削波**（信号不超线性区） | **无法恢复已削波的信息**（只能降低后续信号电平） |
| 动态范围 | 保持完整（SNR 由硬件决定） | 略有损失（有效比特数减少 log₂(gain) 位） |
| 噪声特性 | 量化噪声固定在底噪水平 | 衰减后重新量化时引入舍入噪声（但很小） |
| 灵活性 | 受限于硬件控件 | 可逐通道、逐帧动态调整 |

**结论**：硬件永远是首选。软件是"无可奈何"时的工程折中。

### 7.2 衰减（Attenuation） vs 限幅/压缩（Limiter/Compressor）

本文方案是**线性衰减（Linear Attenuation）**——对所有采样统一乘以相同系数。它不同于：

| 技术 | 操作方式 | 适用场景 |
|------|---------|---------|
| **线性衰减**（本文） | 所有采样 × α（常数） | 整体电平偏高，需要统一降低 |
| **软限幅 Soft Clipping** | 近峰值区用 tanh / cubic 曲线平滑过渡 | 需要消除硬削波的听觉刺耳感，但保留响度 |
| **动态压缩 Compressor** | 超过阈值的部分按比率压低 | 动态范围太大，想压低 peaks 同时抬升 quiet parts |
| **硬限幅 Hard Limiter** | 直接 clamp 到阈值 | 最后防线，宁可失真也不允许溢出 |

对于 AEC 场景，**线性衰减是最合适的**——我们需要保持波形形状不变（维持线性性），只是整体缩小。

### 7.3 Per-channel vs 全局衰减

代码选择了 **per-channel 选择性衰减**（只动 ch0~3），而非全 8 通道统一乘系数。这一选择的理由：

```
统一衰减（×α 全部通道）：
  麦克风电平 ↓ ✓
  回采参考电平也 ↓ ✗  → AEC 的参考信号变弱，信噪比恶化

选择性衰减（仅麦通道 ×α）：
  麦克风电平 ↓ ✓
  回采参考电平不变 ✓  → AEC 参考完整保留
```

在多通道音频处理中，**明确每个通道的语义并区别对待**是基本原则——尤其在 AEC 场景下，回采通道是算法的"参照物"，不应被连带削弱。

## 8. 验证方法

### 8.1 波形级验证

```bash
# 录制衰减前后的 raw PCM 进行对比（需在代码中添加 dump 开关）
# 衰减前：dump 原始 8ch 数据
# 衰减后：dump 处理后 8ch 数据

# 用 sox 拆分通道并查看
sox -t raw -e signed-integer -b 16 -r 16000 -c 8 input.raw output_ch0.wav remix 1
sox -t raw -e signed-integer -b 16 -r 16000 -c 8 input.raw output_ch6.wav remix 7
```

然后用 Audacity 打开 `.wav`，重点查看：

1. **衰减后的 ch0~3**：播报段峰值是否降到 ±12000~±16000 以内，无平顶；
2. **衰减后的 ch6~7**：应与衰减前**完全一致**（未被改动）；
3. **SDK 输出轨**：播报段能量是否显著降低。

### 8.2 主观评测

| 测试项 | 预期结果 |

| 仅播放 TTS（无人声） | SDK 输出接近静音或极低底噪 |

## 9. 局限性与下一步

### 9.1 当前方案的局限

1. **无法修复已发生的硬削波**：如果原始信号已经有宽幅平顶，乘以 0.3 只是把平顶从 ±32767 压到 ±9830，非线性畸变的"坑"仍在；
2. **牺牲了麦克风动态范围**：衰减后有效使用比特数减少约 1.5 bit（gain=0.35 时），极端安静场景下的微弱声音可能更难检出；
3. **固定系数不够自适应**：当前是静态 gain 值，不会根据实时电平自动调整——如果环境噪声或 TTS 音量发生变化，可能需要手动重调；
4. **不解决根本的声学设计问题**：麦距太近、腔体共振、喇叭无隔离等硬件层面的缺陷依然存在。

### 9.2 可选的增强方向

| 方向 | 思路 | 复杂度 |
|------|------|--------|
| **自适应增益** | 基于 RMS/Peak 检测动态调整 gain（类似简易 AGC，但要设置上界防削波） | 中 |
| **软限幅替代** | 对偶尔超限的采样用 tanh 曲线代替硬 clamp，减少刺耳感 | 低 |
| **硬件迭代** | 换用支持独立 Capture Volume 的声卡方案；或在板级增加 PGA/可调增益运放 | 高（需硬件变更） |
| **结构优化** | 麦克风物理移远、增加隔音棉、选用更低灵敏度的麦克风单元 | 高（需结构协同） |
