# 机器人表情标签分类器-从方案设计到训练落地

本文记录清宝机器人表情标签分类器的完整训练落地过程：从「LLM 生成回复 → 前缀截断 → 轻量分类器打标」的链路设计出发，覆盖模型选型梯度（FastText / Chinese-Electra-Small / 小 LLM 兜底）、基于 Qwen 大模型的语料合成与清洗策略、200 条/类冷启动够用性分析，以及线上低置信度数据回流飞轮的工程化实现。核心结论：规则快路径 + Electra-Small（ONNX）主路径 + neutral 强制兜底，端侧延迟 <20ms，2 天内可完成冷启动语料准备并训出首版模型。

---

## 一、问题背景

机器人在与用户交互时，除了播报 TTS 语音，还需要配合面部表情。原有方案中表情由主 LLM 在生成文本时一并输出，存在两个问题：

1. **长回复延迟**：LLM 生成完整回复后才输出表情标签，整句等待时间长
2. **标签耦合**：表情标签与 LLM Prompt 耦合，新增标签需改 Prompt，扩展性差

核心诉求：表情判断从主 LLM 链路中剥离，由独立分类器承担，整段回复只下发一个表情标签，且不阻塞 TTS 播报。

---

## 二、总体链路设计

```
用户问题 → 交互LLM → 完整回复text ──→ TTS播放
                        │
                        └→ 前缀截断 → 表情分类器 → expression
                        │                              │
                        └───────── 组装JSON ───────────┘
                                    │
                              机器人端执行
```

时序要点：

1. LLM 产出 `text` 后立即开 TTS，不等表情
2. 分类器与 TTS **并行**：用截好的前缀打标，表情 JSON 在 TTS 首包前后尽快下发
3. 分类超时则下发默认 `neutral`，不阻塞播报

### 前缀截断策略

分类输入 = `truncate(text)`，规则固定可配置：

| 规则 | 默认值 | 说明 |
|------|--------|------|
| 最大字符数 | 120~160 字 | 覆盖开场语气与情绪锚点 |
| 最大句数 | 前 1~2 句 | 按 `。！？…` 切句 |
| 最短可用 | ≥ 8 字 | 过短直接 `neutral` |

业务理由：整句表情看的是「这段话整体情绪基调」，开场句通常已定调，尾部补充说明对表情贡献小。

```python
def truncate_for_emotion(text: str, max_chars=140, max_sents=2) -> str:
    text = text.strip()
    if len(text) < 8:
        return ""
    # 按句切分，取前 max_sents 句，再截到 max_chars
    ...
```

## 三、表情标签体系

内部统一用英文 code，下发时映射为中文展示名。共 12 个标签：

| code | 中文名 | 典型触发 |
|------|--------|----------|
| `happy` | 愉悦 | 欢迎、夸奖、轻松闲聊 |
| `sad` | 悲伤 | 遗憾、安慰、损失 |
| `depressed` | 抑郁 | 低落、无力（置信度门槛更高） |
| `angry` | 生气 | 不满、责备（轻度） |
| `furious` | 愤怒 | 强烈谴责、爆发 |
| `surprised` | 惊喜 | 意外好消息 |
| `afraid` | 害怕 | 危险、惊吓 |
| `eyeroll` | 翻白眼 | 无奈、吐槽、嫌弃 |
| `awkward` | 尴尬 | 社交尴尬、打圆场 |
| `confused` | 疑惑 | 不解、反问 |
| `shy` | 害羞 | 被夸、不好意思 |
| `neutral` | 无 | 中性说明、百科、流程指引（默认） |

**相近标签消歧规则**：

- `angry` vs `furious`：强度词（「太过分」「气死」→ furious）
- `sad` vs `depressed`：短暂遗憾 vs 持续低落；不确定偏向 `sad`
- `surprised`：偏正面意外；负面意外走 `afraid`/`awkward`

扩展方式：只改标签枚举配置 + 分类器训练数据，JSON 字段名不变。

## 四、分类器选型梯度

### 选型矩阵

| 阶段 | 模型选型 | 预估端侧延迟(RK3588类) | 定位 |
|------|----------|----------------------|------|
| 第一阶段（冷启动） | 规则词典 + FastText | ~2ms | 跑通主链路，快速收集真实前缀语料 |
| 第二阶段（生产主力） | 规则词典 + Chinese-Electra-Small（ONNX） | 10~20ms | 提升相近标签消歧准确率，核心主路径 |
| 第三阶段（极端兜底） | 低置信度直接 neutral | 0ms | 保障 TTS 不卡顿 |

### 各梯度详细分析

**1. FastText / 线性分类器（极速低资源）**

- 延迟 1~3ms，内存几兆到几十兆
- 对「哈哈」「对不起」等强特征词效果极好
- 缺点：依赖显式词汇，「行吧，那就这样吧」这种依赖语境的句子泛化弱
- 适合做规则快路径与 Transformer 之间的过渡层

**2. Chinese-Electra-Small / TinyBERT（首选生产方案）**

- 参数量 20M~50M，CPU 单次推理 10~20ms；ONNX 部署可压到 5~15ms
- Attention 机制有效捕捉情绪锚点和微弱语义倾向
- 能区分 `sad` vs `depressed`、识别 `awkward` 社交语境
- 推荐模型：`hfl/chinese-electra-180g-small`（哈工大开源）

**3. Embedding + 线性分类头（复用方案）**

- 若管线中已常驻向量模型（如 RAG 检索用的 `bge-micro-v2`），可复用其输出向量
- 后端接 MLP 或 SVM 做多分类，节省整体内存

**4. 小 LLM 兜底（仅低置信度触发）**

- `Qwen2.5-0.5B-Instruct` 量化部署，强制枚举内选一
- 即便 INT4 量化，端侧 TTFA 仍可能 50~100ms
- 建议：非必要不触发，低置信度直接归流 `neutral`

**生产推荐组合**：规则快路径 → Electra-Small 主路径 → 低置信度 neutral 兜底。

## 五、训练数据合成与清洗

### 5.1 大模型语料合成方案

利用现有 Qwen2.5-32B 模型合成种子语料，核心挑战是**防止同质化**和**模拟真实前缀截断状态**。

**Prompt 设计要点**：

```text
你是一个智能机器人交互语料生成器。请为表情标签【翻白眼 / eyeroll】
生成 200 条用于训练的中文文本。

【标签定义】：用于表达无奈、吐槽、嫌弃、遇到无理要求的社交语境。
【核心要求】：
1. 必须是机器人说的话，或对用户奇葩问题的口语化回复。
2. 文本长度控制在 10~60 字，模拟一句话刚开头的状态。
3. 极力避免同质化！从以下维度交替生成：
   - 明显吐槽语气的短句（如："又来了..."、"行行行，你说的都对..."）
   - 委婉表达无语的长句
   - 带有反讽或冷幽默的回复
4. 每行一条，直接输出文本，不要带序号或解释。
```

**多轮 Prompt 变体打破思维定势**：

- 变体 A（日常闲聊）：机器人在跟用户瞎扯时感到无奈的前缀 50 条
- 变体 B（业务被刁难）：用户无理要求/重复提问时，礼貌中带嫌弃的前缀 50 条
- 变体 C（网络热梗）：使用年轻人吐槽词汇（「绝了」「无语子」「那不然呢」）50 条

### 5.2 语料清洗三步法

大模型生成语料通常有 20%~30% 脏数据，不能直接训练。

**第一步：去重去同质化（脚本过滤）**

大模型喜欢复用高频词（如 `happy` 标签全是「太棒了」「真高兴」）。用 Python 计算编辑距离或字符重合度，相似度 >80% 的句子直接删除。

**第二步：相近标签人工消歧**

`angry` vs `furious`、`sad` vs `depressed` 的边界样本必须人工过一遍：

- `angry`（生气）：带责备不满，语调可控（「你怎么又把这事给忘了？」）
- `furious`（愤怒）：强烈情绪词、破防谴责（「这太过分了！简直不可理喻！」）
- 模棱两可的直接删掉，不让垃圾数据污染边界

**第三步：模拟截断后遗症（关键）**

截断后情绪可能剧变，必须以截断后的文本作为最终输入标注：

| 原句 | 截断后 | 原标签 | 截断后应标 |
|------|--------|--------|-----------|
| 这个活动听起来确实不太吸引人，不过看在你的面子上我还是去看看吧 | 这个活动听起来确实不太吸引人。 | `awkward` | `eyeroll` 或 `sad` |
| 关于你刚刚提到的问题，我实在忍不住想吐槽一下 | 关于你刚刚提到的问题。 | `eyeroll` | `neutral` |

### 5.3 口语噪音注入

真实机器人回复包含大量语气词和标点情绪，在 Prompt 中强制要求加入：

- **语气词开头**：啊、呃、天哪、哈？、那个……
- **标点情绪**：感叹号（`！`）、问号（`？`）、省略号（`……`）

Transformer 模型对标点符号非常敏感，标点往往是开场情绪的强信号。

### 5.4 200 条/类够不够

| 阶段 | 数量评估 | 说明 |
|------|----------|------|
| 冷启动 | 200 条/类够用 | 短前缀文本特征集中，12 类 × 200 = 2400 条可拟合基础语义边界 |
| 业务演进 | 不够 | 场景变多后泛化遇瓶颈，每类需 500~1000 条真实线上数据才趋于稳定 |

## 六、防匹配错误的三道防线

### 第一道：差异化置信度阈值

不对所有表情一视同仁，高风险表情门槛更高：

| 标签类型 | 标签 | 阈值 | 策略 |
|----------|------|------|------|
| 默认兜底 | `neutral` | 无门槛 | 直接通过 |
| 正面低风险 | `happy` / `surprised` | ≥ 0.55 | 错了无伤大雅 |
| 负面高风险 | `angry` / `furious` / `depressed` | ≥ 0.80~0.85 | 不达标强制转 `neutral` |

### 第二道：规则黑白名单兜底

在模型前面挡一层硬编码规则：

- **白名单**：前缀含「哈哈」「太棒了」直接锁 `happy`，跳过模型
- **黑名单**：含百科词汇、客服术语、流程指引直接锁 `neutral`

### 第三道：低置信度数据回流飞轮

这是解决匹配错误的核心闭环：

```
线上运行 → 记录低置信度文本(confidence 0.5~0.75)
    → 大模型预审打分 → 工程师快速校对 → 合并训练集 → 自动重训 → 评测 → 发布
```

## 七、数据飞轮工程化实现

目标：工程师每周仅花 30 分钟完成「数据回流-校对-重训」闭环。

### 7.1 线上拦截与自动落盘（平时自动运行）

在主链路组装 JSON 时增加日志落盘逻辑，只捕获两类样本写入 `bad_cases.jsonl`：

1. **低置信度模糊样本**：`confidence ∈ [0.5, 0.75]`
2. **极端边界样本**：预测为高风险表情但被强制降级为 `neutral` 的文本

```json
{
  "text_prefix": "行行行，都听你的，我闭嘴总行了吧",
  "pred_label": "neutral",
  "confidence": 0.58,
  "timestamp": 1783857600
}
```

### 7.2 大模型预审 + 工程师校对（每周一 10 分钟）

**脚本预处理**：每周一自动化脚本将 `bad_cases.jsonl` 导出，调用本地 Qwen 大模型二次预测，作为高可靠参考答案。

**校对界面**（Excel 或 Streamlit Web）：

| 截断前缀文本 | 原模型预测 | 线上下发 | Qwen推荐 | 工程师确认 |
|-------------|-----------|---------|---------|-----------|
| 行行行，都听你的，我闭嘴总行了吧 | `neutral`(0.58) | `neutral` | `eyeroll` | [确认Qwen] 或下拉选择 |
| 真的太谢谢你了，帮了我大忙！ | `happy`(0.62) | `happy` | `happy` | [确认原判] |

工程师操作：90% 的低置信度数据只需扫一眼确认 Qwen 建议即可，几百条 10 分钟过完。

### 7.3 一键重训与评测（15 分钟）

校对完成后触发自动化脚本：

```bash
# 1. 合并新数据
cat weekly_corrected.jsonl >> ./data/all_training_data.jsonl

# 2. 去重与划分
python preprocess.py --input ./data/all_training_data.jsonl

# 3. 自动重训（千条规模几分钟完成）
python train.py --model_type electra --epochs 5

# 4. 自动评测：输出混淆矩阵和准确率变化
python eval.py
```

工程师只需看一眼混淆矩阵对比：准确率是否提升、上次错判标签的召回率是否改善、延迟是否达标。通过后 CI/CD 自动打包 ONNX 模型下发到端侧。

### 7.4 避坑：数据倾斜控制

线上回流数据中 `neutral` 和 `happy` 数量压倒性多，`furious` 极少。合并训练集时加**数量配额控制**：每周每种标签回流上限不超过 50 条，防止模型被高频表情「洗脑」导致泛化退化。

## 八、下发 JSON 协议

与现有 Speak 协议对齐：

```json
{
  "function": "Speak",
  "text": "今天天气真不错，我们出去走走吧。",
  "expression": "愉悦",
  "expression_code": "happy",
  "confidence": 0.91,
  "meta": {
    "source": "emotion_clf_v1",
    "truncation": "prefix",
    "used_chars": 18
  }
}
```

若表情与播报分开发送（TTS 已先起），用轻量补丁包：

```json
{
  "function": "SetExpression",
  "expression": "愉悦",
  "expression_code": "happy",
  "utterance_id": "uuid-xxx"
}
```

`utterance_id` 与本次 Speak/TTS 会话绑定，避免乱序。

约定：

- `expression`：机器人已支持的中文名（兼容现有 `愉悦/悲伤/害怕/生气/无`）
- `expression_code`：稳定机读码，便于扩展与日志
- `confidence`：低于阈值时强制改为 `neutral`
- 整段 `text` 只对应一个 `expression`，不做句内切换

## 九、模块职责边界

| 模块 | 职责 |
|------|------|
| 交互 LLM | 只产 `text` |
| 表情分类器 | 只产整句 `expression`，只读回复前缀，不读用户问题 |
| TTS | 播 `text` |
| 动作模块 | 另路标签，与表情并行下发，本方案不耦合 |

## 十、实施计划与时间线

| 步骤 | 内容 | 预估耗时 |
|------|------|----------|
| 1 | 固化标签枚举与 JSON Schema（含中英映射、默认值） | 0.5 天 |
| 2 | 实现 `truncate_for_emotion` + 规则快路径 + 分类器接口 | 1 天 |
| 3 | 用 Qwen 分批生成 12 类 × 300 条语料 | 1~2 小时 |
| 4 | 截断模拟 + 去重 + 人工消歧清洗 | 0.5 天 |
| 5 | 训练首版 Electra-Small，导出 ONNX | 半天 |
| 6 | 接入主链路：LLM →（TTS ∥ 打标）→ 组装 Speak JSON | 1 天 |
| 7 | 搭建日志落盘 + 校对界面 + 重训脚本 | 1 天 |
| 8 | 线上灰度，开启数据回流飞轮 | 持续 |

冷启动语料准备 2 天内可完成，首版模型从训练到上线约 1 周。
